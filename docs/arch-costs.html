Cost tracking & budgets

Every chat turn logs exactly what it spent. Those rows roll up into session and daily totals, surface prompt-cache telemetry, and gate the next round against your spend caps - all locally, in SQLite.

Cost tracking lives in server/costs/, a small self-contained package: tracker.py (pricing, logging, aggregation, cache telemetry, the API) and budget.py (cap enforcement). The chat pipeline calls into both. Remaining-capacity tracking lives outside this package, in the token-based context meter in server/chat/loop_hints.py (see below). Click a box below to trace the flow from a completed turn to the Costs panel.

Pricing: a per-model rate table

Cost is not measured, it is estimated from token counts and a per-model price table. estimate_cost(model_key, input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens, cached_in_input) returns a USD figure. The rates are file-sourced: the committed pricing.example.json at the repo root holds the authoritative default rates, and an optional gitignored pricing.json in the config dir overlays them per key (the same example-to-override split as config.example.json and config.json). The merged result is loaded once at import into _MODEL_PRICING in server/costs/tracker.py, so repricing applies on server restart. Rates are USD per 1M tokens, with four explicit rates per model: input, output, cache-read, and cache-write (prompt-cache creation), plus an optional per-model cached_in_input flag (set on all the OpenAI entries; see below).

There is deliberately no fallback bucket. An unknown model key bills $0 and logs an error rather than silently inheriting another model's rate, so a missing entry is loud instead of quietly wrong. Two cases are expected to be free and log at debug instead: on-device (local_*) models, which cost nothing, and the unknown placeholder a subagent row carries when no model was resolved. Adding or repricing a model is a JSON edit (an entry in pricing.example.json, or an override in pricing.json), not a code change.

On the read side only, _resolve_pricing() is more forgiving: a recorded model may carry a suffix (opus4.8_subagent), so it falls back to the longest prefix match, which is why sonnet5_subagent resolves to sonnet5 and never to sonnet. Billing itself stays exact-match.

Prices move, promotional discounts come and go, and your effective bill depends on your AWS account. Treat pricing.example.json (and your pricing.json overrides) as the source of truth, and see the Amazon Bedrock pricing page for the current list rates.

Two cache conventions, one function

Anthropic and OpenAI count cached tokens differently, and estimate_cost handles both through its cached_in_input flag:

  • Anthropic (cached_in_input=False, the default): input, cache-read, and cache-creation are three disjoint token buckets, each billed once at its own rate.
  • OpenAI (cached_in_input=True): the cache-read tokens are a subset of the reported input tokens, so the function subtracts them out and bills the cached portion once at the cache-read rate and the remainder at the input rate, never both.

The flag lives on the pricing entry itself, so the convention follows the model wherever its tokens are counted: get_cache_stats reads the same flag to normalize the hit-rate denominator across providers.

See prompt caching for how cache reads and writes are produced in the first place.

Logging a round

When a round ends, the engine reads its token usage from the adapter's uniform round result, prices it, and calls record_turn(session_id, turn_number, model, input_tokens, output_tokens, cost_usd, ...) to persist one row into the session_costs table in storage/sessions.db. The unit is the model round, not the user turn: a turn with five tool rounds writes five rows, and turn_number holds the round index within the turn.

Cost logging never breaks a chat. record_turn wraps its write in a try/except and only logs on failure, so a cost-logging error can never crash the turn that produced it. The same is true of the read-side aggregates, which return an empty result rather than raising.

Each row records the model, the four token counts, the estimated cost, the API duration, and a UTC timestamp:

ColumnMeaning
session_id, turn_numberWhich session and round this row belongs to.
modelThe model key that ran (drives which pricing row applied).
input_tokens, output_tokensNon-cached prompt tokens in, generated tokens out.
cache_read_tokens, cache_creation_tokensPrompt-cache reads and writes for the round.
cost_usdThe estimate_cost result for the round.
api_duration_msHow long the Bedrock call took.
created_atUTC timestamp, defaulted by SQLite; drives the daily rollups.

The table is created by server/migrations/001_add_session_costs.py with indexes on session_id and created_at. When a session is deleted, its cost rows are deleted with it. See Persistence for how the SQLite store is managed overall.

Background work bills against the session too, at turn numbers outside the live range so it never collides with a real round. The post-turn learning review (a fork of the turn's own request) numbers its rounds from REVIEW_TURN_BASE (900), precisely so the cost is visible in the panel instead of hiding behind the turn that triggered it.

Side tasks and auxiliary_models

A turn is not the only thing that calls a model. Memory recall, the goal evaluator, title generation, the auto-mode classifier, the permission explainer, query rewriting, CI diagnosis, compaction summaries, and the learning review each make their own call, and each used to hard-code Haiku at its own call site.

The auxiliary_models config map now names the model per task (server/infrastructure/auxiliary.py). Values are chat_models keys, plus one special value, "main", meaning "the session's own model", which the caller resolves because only it knows that model. A task absent from the map keeps its historical default, so an empty map (the shipped default) behaves exactly as before:

Task keyDefault when unset
memory_recall, goal_evaluator, title, auto_mode_classifier, permission_explainer, query_rewrite, ci_diagnoseHaiku
compaction, learning_reviewThe session's own model

Not every call site can honour every value. Recall, the classifier, and the explainer are direct Bedrock invokes, so an on-device key there falls back to the default; tasks routed through one_shot accept a local key. And naming a model other than the session's own for learning_review is read as a request for the cheap excerpt-based review on that model, because the cache-parity fork by definition runs on the turn's model.

Aggregations

The logged rows are read back through a handful of query helpers in server/costs/tracker.py:

get_session_summary(session_id)
Totals for one session: turn count, total input/output tokens, total cache reads, total cost, and total API duration.
get_session_costs(session_id)
The per-turn breakdown for a session, ordered by turn number.
get_model_breakdown(session_id="")
Per-model turns, tokens, and cost, ordered by spend. Pass a session id to scope it, or leave it empty for a global breakdown across all sessions.
get_daily_costs(days=30)
Daily totals for the last N days, grouped by DATE(created_at) - the data behind the bar chart.
get_today_total_cost()
The single number the daily budget check compares against: today's total cost in UTC.
get_session_usage(session_id)
The live composer readout's totals, grouped by model so each group's prompt tokens are normalized for its own cache convention before summing.

Cache telemetry

get_cache_stats(session_id="") aggregates prompt-cache usage - globally or for one session - into a small block: read_tokens, write_tokens, a hit_rate (cache reads over total prompt tokens), and est_savings_usd (what the cached reads would have cost at the full input rate minus their cache-read rate, summed per model). It is the live "is caching actually working" surface, and it rides on GET /api/costs/summary as a cache object.

Tracking remaining context

Remaining-capacity tracking answers a different question than the cost aggregates. It is not "how much have you spent" but "how much room is left in this conversation before it has to compact". This moved out of the costs package into the token-based context meter in server/chat/loop_hints.py: every round's message_start usage already reports the true prompt size, so note_prompt_tokens() records it directly against the model's window - no character-count estimate:

  • The true prompt size is input + cache_read + cache_creation tokens from message_start. note_prompt_tokens() stores the latest value per session and context_estimate() reads back (context_used, context_max).
  • The window is the usable input budget, not the raw context window: context_window_for() defers to the engine's own window accounting (server/chat/engine/windows.py), which subtracts the tokens reserved for the answer. A 1M-window Claude model therefore budgets against roughly 872K, GPT on mantle against its real 278,528-token prompt cap, and an on-device model against its live n_ctx. DEFAULT_CONTEXT_MAX (200,000 tokens) is only the fallback when that lookup fails.
  • When the real prompt crosses COMPACT_NUDGE_FRACTION (0.95) of the window, should_nudge_compaction() fires once so proactive compaction can trigger on token truth rather than a character guess.

The meter reads real prompt tokens. Every round's message_start usage reports the true prompt size and note_prompt_tokens() records it directly, so cached reads and cache creation need no correction. See Chat & tool orchestration for the compaction path this meter triggers.

Budgets: stopping before you overspend

Budgets are a hard gate, checked before each round in the chat loop. check_budget(session_id) in server/costs/budget.py reads two caps from config.json and returns either None (you are within budget) or a BudgetExceeded object describing which cap was hit:

max_session_cost_usd
Ceiling on one session's total cost. Compared against get_session_summary. 0 means unlimited.
max_daily_cost_usd
Ceiling on today's total cost across all sessions. Compared against get_today_total_cost. 0 means unlimited.

The session cap is checked first, then the daily cap. Because either limit set to 0 means "no limit", cost enforcement is off by default and you opt into it in Settings.

The soft limit: one round to answer

A hard stop at 100 percent of a cap throws away everything the turn had gathered, mid-sentence. So the same comparison runs twice, at two fractions. check_budget_soft(session_id, fraction) is check_budget with the cap multiplied by fraction; the engine calls it at SOFT_LIMIT_FRACTION (0.9, in server/chat/engine/runner.py) before every round, right after the hard check:

  1. First trip: finalize

    At 90 percent of a cap (or immediately, if the hard cap is already blown), a budget_warning frame goes out and a <system-reminder> is appended to the message list saying this is the final round: answer now, further tool calls will not execute. The round runs with tools forced off, so it genuinely terminates instead of asking for another tool.

  2. Second trip: stop

    Once _budget_finalized is set, the next check emits the warning again, streams a short [Budget exceeded] line into the transcript so the halt is visible in the conversation, sends [DONE], and returns. The turn stops rather than erroring, so nothing is left half-streamed.

The budget_warning frame carries the human-readable message plus the structured budget_kind (session or daily), budget_limit, and budget_current, so the SPA can render a precise notice. The message tells you exactly how to proceed: start a new session, raise the relevant cap, or wait until tomorrow for a daily reset. You can also clear today's records manually with POST /api/costs/reset-daily.

The reminder is appended to the message list, not injected into the request only. That is deliberate: a request-only injection would fork the token prefix and break the moving cache checkpoint, which would cost more than the cap was trying to save.

The same 0.9 fraction governs the time budget of an agent run, so the two behave alike: the reporting round starts with a tenth of the budget still in hand, and the report is written inside the budget instead of after it, where an outer limit could still kill it unsaved. See The agent flight recorder.

Agent budget bars

Because the engine is shared, an agent run is priced by the same code, and its progress events carry the numbers out to the UI. Every turn_start event a member emits is stamped with its round cap (live extensions included), seconds elapsed and allowed, the estimated spend so far as cost_usd, and whether the coming round is the final one.

src/hooks/chatStream/agentBudget.ts folds the latest of each into three bars (rounds, time, estimated cost) plus one state pill: working, finishing up, done, hit limit, salvaged, or failed. The reserved final slice is drawn from the same constant (FINALE_FRACTION, 0.1). Nothing is computed from client wall-clock time, so reopening the conversation later renders identical bars.

Settings and the Costs panel

The two caps are set in the Settings UI (and persisted to config.json); see Configuration and Settings & config keys. Live spend is surfaced in two places in the SPA:

Live in the chat

Each turn's usage SSE event carries the running token counts, the per-turn estimated_cost_usd, and context_used / context_max, so the current turn's cost and remaining context update as tokens stream.

The Costs panel

A dedicated panel reads the aggregate endpoints to show per-model totals, a daily bar chart, today's total, and the configured caps - the whole spend picture at a glance.
