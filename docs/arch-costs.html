Cost tracking & budgets

Every billed model call is logged once, with the token counts the provider itself reported. The log is priced when it is read, reported over UTC days, and gates the next round against your spend caps - all locally, in SQLite.

Cost tracking lives in server/costs/:

Remaining-capacity tracking lives outside this package, in the token-based context meter in server/chat/loop_hints.py (see below). Click a box below to trace the flow from a completed call to the Costs tab.

Token counts: the provider's payload first

Every row takes its counts from the provider's own response payload. Only when the payload carries no count is a count estimated, and then as exactly characters / 4 of what was actually posted (the request body, for input) or actually received (text, tool-call arguments, billed reasoning text, for output). An estimate is never presented as a reported count: the row names the estimated fields.

Claude on Bedrock
The stream reports twice. The Anthropic usage fields: message_start carries input, cache read and cache write, and message_delta carries output, which is cumulative per message, so the last value is the count, never the sum. And Bedrock's own amazon-bedrock-invocationMetrics trailer on message_stop (the non-streaming invoke_model carries the same numbers as x-amzn-bedrock-*-token-count headers). Bedrock bills from its own metering, so the trailer is authoritative; when the two disagree the row keeps both in count_detail and a warning is logged.
GPT on bedrock-mantle
The Responses usage on response.completed: input tokens, output tokens, and input_tokens_details.cached_tokens, a subset of input. The adapter releases the turn about a second after the answer ends instead of waiting out mantle's slow completed tail; such a round never sees the usage, so both counts are characters / 4 of the payloads and marked estimated.
On-device models
llama-server or MLX usage when the server sends it, characters / 4 otherwise. They cost $0, but the tokens still show.

An attempt that ends without a result (a mid-stream fault the engine retries, a terminal error, a Stop or a closed tab) was still billed for what the provider processed. The adapter reports what it knows (inflight_usage: the prompt counts message_start reported, the output as characters / 4 of what arrived) and the engine records it as its own row, once. A stream that failed before the provider started the message is not recorded: nothing shows it was billed.

Pricing: a per-model rate table

estimate_cost(model_key, input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens) returns a USD figure from token counts and a per-model price table. The rates are file-sourced: the committed pricing.example.json at the repo root holds the rates, and an optional gitignored pricing.json in the config dir (~/.whisper for the Mac app, the repo root for a source install) overrides them per key. Rates are USD per 1M tokens: input, output, cache read and cache write, plus a cached_in_input flag on the OpenAI entries.

pricing.json holds only the keys a user changes. Neither install path seeds it any more: a full copy of the template froze every rate at install time and shadowed each later correction. An existing copy is still read, but an entry equal to a rate some release shipped for that key (pricing_history.py) is ignored and logged, so only genuine overrides apply.

There is deliberately no fallback bucket. An unknown model key bills $0 and logs an error (once per key) rather than silently inheriting another model's rate, and the Costs tab says so on that row. On-device (local_*) models are expected to be free and log at debug.

Billed but not priced per token. Cohere Rerank 3.5 bills per search unit ($0.002 each), not per token, so its rows have no rate in the table. Its calls and tokens are in the log and on the Costs tab, priced at $0 with the unpriced-model note, so the app's total falls short of Cost Explorer by exactly that spend. Nova Sonic speech and text (<model id>:speech and <model id>:text) and Cohere Embed 4 are priced at the AWS Price List rates, which match the unit costs Cost Explorer shows.

Prices move and your bill depends on your account: treat pricing.example.json and your overrides as the source of truth and check the Amazon Bedrock pricing page.

The long-context tier

Every Bedrock OpenAI card bills a call whose prompt is over 272K input tokens at its long-context rates, on all of that call's tokens: 2x input, cache read and cache write, 1.5x output. Each GPT entry carries them as long_context ({"above": 272000, "input", "output", "cache_read", "cache_write"}). A model's context_window only sets when compaction starts, so single rounds do go over the break. The tier is a property of one call, so nothing prices a sum of calls with it: call_cost prices one call at the tier its own prompt falls in, the engine's running total is the sum of its rounds' call_cost, and every reader of the log groups rows by tier (long_context_sql) before summing, so each sum prices at one tier.

Two cache conventions, one function

Anthropic and OpenAI count cached tokens differently, and estimate_cost reads the convention from the model's pricing entry, never from the caller, so no call site can drop it:

  • Anthropic (no flag): input, cache read and cache write are three disjoint buckets, each billed once at its own rate.
  • OpenAI (cached_in_input): the cache-read tokens (input_tokens_details.cached_tokens) and the cache-write tokens (mantle's cache_write_tokens, which the OpenAI SDK does not declare) are subsets of the reported input, so each portion is billed once, at the cache-read and cache-write rates, and only the remainder at the input rate, never both.

Prompt tokens are normalized the same way (prompt_tokens_for: uncached input plus cache read plus cache write), so GPT and Claude figures add up.

Logging a call

record_turn writes one row per billed model call into session_costs in storage/sessions.db. For a turn the unit is the model round: a turn with five tool rounds writes five rows. An agent's rounds are recorded by the same engine under the parent session, exactly once; there is no second rollup row per agent.

ColumnMeaning
session_id, turn_numberThe session the call served (empty for work with no session, such as index passes) and the round.
modelThe model key that ran (drives which rates apply).
input_tokens, output_tokens, cache_read_tokens, cache_creation_tokensThe counts, in the provider's own convention.
sourceWho made the call (below). record_turn refuses an unknown one.
count_source, estimated_fieldsreported, or estimated with the fields that were characters / 4.
count_detailBoth reported sources, when Bedrock's metering and the Anthropic usage disagreed.

There is no dollar column. Every reader prices the stored counts with the current rate table, so a rate correction re-rates history the same way in the Costs tab, the export, the composer readout and the budget caps. Deleting a session keeps its rows: those calls were billed, and the Costs tab shows them as "Deleted session". Migrations 021 and 022 built this shape; see Persistence.

Side tasks and auxiliary_models

The auxiliary_models config map names the model per side task (server/infrastructure/auxiliary.py). Values are chat_models keys, plus "main", meaning "the session's own model". A task absent from the map keeps its historical default:

Task keyDefault when unset
memory_recall, goal_evaluator, title, auto_mode_classifier, permission_explainer, query_rewrite, ci_diagnoseHaiku

Recall, the classifier and the explainer are direct Bedrock invokes, so an on-device key there falls back to the default; tasks routed through one_shot accept a local key, and an on-device call costs nothing and is not logged. goal_evaluator applies to cloud-model sessions only: an on-device session's goal is judged by its own resident model.

Reading the log back

server/costs/usage.py answers the Costs tab. Days are UTC days, the same days AWS Cost Explorer reports, and both range ends are inclusive. Weeks start on Monday; a first or last week or month the range clips is flagged partial. Buckets are zero-filled over the whole range. Split by model, session or source, every figure adds up to the range totals, and each row carries a note when it includes GPT at list rates or a model with no rate.

The cache figures are for the selected range: cache-read tokens (counted on every model call, so a long agent loop re-reads its prefix every round), a hit rate over normalized prompt tokens, and what caching saved at list rates net of the cache-write premium.

get_session_usage(session_id) serves the session cap, and through session_readout the composer readout: that session's prompt tokens, output tokens, rounds and cost, priced now.

Tracking remaining context

Remaining-capacity tracking answers "how much room is left in this conversation before it has to compact", not "how much have you spent". The context meter in server/chat/loop_hints.py records each round's real prompt size with note_prompt_tokens(), against the model's usable input budget from context_window_for() (the engine's window accounting in server/chat/engine/windows.py, which subtracts the tokens reserved for the answer). When the real prompt crosses COMPACT_NUDGE_FRACTION (0.95) of the window, should_nudge_compaction() fires once so proactive compaction triggers on token truth rather than a character guess.

Budgets: stopping before you overspend

Budgets are a hard gate, checked before each round in the turn engine. check_budget(session_id) in server/costs/budget.py reads two caps from the config and returns either None or a BudgetExceeded naming the cap that was hit:

max_session_cost_usd
Ceiling on one session's cost (get_session_usage). 0 means unlimited.
max_daily_cost_usd
Ceiling on the current UTC day's cost across all sessions (usage.today_spend_usd); it resets at 00:00 UTC. 0 means unlimited.

Both price the log at read time, so they agree with the Costs tab. There is no manual reset: the rows are the history, and the daily window moves on its own.

The soft limit: one round to answer

A hard stop at 100 percent of a cap throws away everything the turn had gathered, mid-sentence. So the same comparison runs twice, at two fractions. check_budget_soft(session_id, fraction) is check_budget with the cap multiplied by fraction; the engine calls it at SOFT_LIMIT_FRACTION (0.9, in server/chat/engine/runner.py) before every round, right after the hard check:

  1. First trip: finalize

    At 90 percent of a cap (or immediately, if the hard cap is already blown), a budget_warning frame goes out and a <system-reminder> is appended to the message list saying this is the final round: answer now, further tool calls will not execute. The round runs with tools forced off, so it genuinely terminates instead of asking for another tool.

  2. Second trip: stop

    Once _budget_finalized is set, the next check emits the warning again, streams a short [Budget exceeded] line into the transcript so the halt is visible in the conversation, sends [DONE], and returns. The turn stops rather than erroring, so nothing is left half-streamed.

The budget_warning frame carries the message plus budget_kind (session or daily), budget_limit, and budget_current. The message says how to proceed: start a new session, raise the cap, or wait for the daily cap to start over on its own at 00:00 UTC.

The reminder is appended to the message list, not injected into the request only: a request-only injection would fork the token prefix and break the moving cache checkpoint, which would cost more than the cap was trying to save.

Agent budget bars

Every turn_start event an agent emits is stamped with its round cap (live extensions included), seconds elapsed and allowed, the estimated spend so far as cost_usd (the engine's running total: each round priced with call_cost at its own tier, never the summed counts priced again; a workflow's ledger adds the same figure per agent), and whether the coming round is the final one. src/hooks/chatStream/agentBudget.ts folds them into three bars and a state pill; see The agent flight recorder.

Settings and the Costs tab

The two caps are set in the Settings UI (and persisted to config.json); see Configuration and Settings & config keys. Live spend is surfaced in two places in the SPA:

Live in the chat

Each turn's usage SSE event carries the running token counts, the per-turn estimated_cost_usd, and context_used / context_max, so the current turn's cost and remaining context update as tokens stream.

The Costs tab

Settings > Usage and advanced > Costs reads one ranged report, GET /api/costs/usage. Three controls drive the whole tab: a range of UTC days (Today, Last 7 days, Last 30 days, This month, Last month, All time, which starts at the first public release on 2026-07-23 and says so, or Custom), a Day, Week or Month granularity (weeks start on Monday), and a split by Model, Session or Source. Below them sit summary tiles, a stacked chart with every bucket zero-filled (a week or month clipped by the range is drawn lighter), a breakdown table sorted by any column, the caps with today's UTC spend, and an export of the selected range. Every dollar figure is an estimate at list rates; figures that rest on estimated token counts are marked as such, and each row's pricing note (for GPT on Bedrock) is shown with it. The tab offers no manual reset: the cost rows are the spend history, and nothing there deletes them.

API endpoints

The router is mounted under /api/costs in server/costs/routes.py; every read runs off the event loop:
