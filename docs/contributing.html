Development & contributing

How to run the checks, find your way around the codebase, and land a change in the right layer. This page is for people working on Whisper Studio; if you just want to run it, start with Installation.

Whisper Studio is one FastAPI process serving one origin: a Python backend under server/ and a React 19 SPA under src/, built and served together by setup.sh. Get a working install first (see Installation), then use the checks and map below to make changes.

What you need

setup.sh requires Python 3.12 or newer and refuses to continue on anything older; in an interactive terminal it offers to install python@3.12 through Homebrew for you. The Mac app ships CPython 3.13, and the voice-mode SDK only installs on 3.12 or newer, which is where the floor comes from. Node is pinned by .nvmrc. Run bash setup.sh once to provision venv/ and the frontend bundle before anything below.

The local gate

Run these before you push. They are the same checks CI runs, so a green local run means a green pipeline. Run the pytest suite in the default environment, with no extra variables set.

venv/bin/python -m pytest tests/    # backend suite
venv/bin/ruff check .               # Python lint
venv/bin/ruff format --check .      # Python formatting

npx tsc --noEmit                    # TypeScript typecheck
npm test                            # vitest frontend unit tests
npm run lint                        # ESLint over src/
npm run build                       # production build

Gate on the exit code, not on the tail of the output: a piped pytest | tail reports the exit status of tail, not of the suite.

Run /doctor in the chat input for an automated AWS-credentials and Bedrock-connectivity check (it also verifies the workspace, sessions DB, and config load). It is the fastest way to confirm a fresh checkout is wired up correctly.

Conventions

Backend edits need a restart
Backend modules are imported once at startup, so edits to server/*.py do not take effect until the process restarts. Kill the old process first (lsof -ti :8000 | xargs kill) before re-running setup.sh: the script port-scans from 8000, so with the old server still alive it starts a second server on the next free port instead of restarting the code you just edited.
Frontend is strict TypeScript + Zod
The SPA uses TypeScript strict mode. SSE event payloads are validated at runtime with Zod schemas in src/types/, so a malformed event fails loudly rather than corrupting state.
Tools have three homes
Tool schemas live in server/agent_tools/ (and next to their executors for a few subsystems), dispatch in server/tool_router.py, which is pure name-to-handler routing and nothing else, and the implementation in server/executors/. Lifecycle (hooks, permissions, plan mode, the loop guard) belongs in server/tool_executor.py, never in the router.
Never reinvent the approval flow
Approval-gated server actions go through server/approval/registry.py, which holds the paused turn and re-validates the payload at execute time. Do not build a parallel approval path - see Approval & permissions for why.
Keep files under the size budget
tests/test_file_size_budget.py fails any server/ or src/ file over 1200 lines. Split a growing module along a topic rather than adding it to the allowlist.
No em dashes, no emoji
Not in code comments, prompts, docs, or commit messages. Use a comma, colon, period, or parentheses.

Invariants to review every change against

These are the load-bearing rules of the codebase. A change that breaks one usually still passes its own test and then fails somewhere expensive, so check your diff against the list.

  1. Register always, refuse at execution

    The tool catalog is byte-stable across plan mode, strict-RAG, and connecting or disconnecting a workspace. Per-turn restrictions are enforced in server/tool_executor.py and the executors, never by rewriting the tools array: rewriting it invalidates the prompt cache.

  2. Static before dynamic

    System-prompt sections at or below PromptLayer.WORKSPACE are cached. Anything that varies per request belongs on DYNAMIC or later (server/prompts/__init__.py). Session-stable text parked on a dynamic layer is re-billed on every round.

  3. Reminders are persisted, not injected per request

    Anything the model must see mid-turn is appended to the last user message (inject_reminder in server/chat/loop_hints.py), so the token prefix never forks between rounds.

  4. Every tool result flows through the safety gate

    Providers yield neutral events. execute_tool_batch and process_tool_results own hooks, permissions, approvals, budgeting, and the loop guard. An adapter never reads tool output.

  5. SSE frames are pinned

    tests/golden_fixtures/ pins the frame vocabulary; re-record on purpose with GOLDEN_RECORD=1. The frontend Zod schema (src/types/schemas/chat.schema.ts) strips unknown fields, so a new frame or field must be added there and in src/types/chat.ts or the UI silently drops it.

  6. Import boundaries

    server/infrastructure/config.py never imports through server.chat.

  7. One deliverable, one file

    File-producing tools overwrite the same path atomically. Never create a _v2 or _final stray.

  8. User files live in ~/.whisper

    App storage sits under the data root. Tests pin WHISPER_USER_DIR and redirect every import-time DB path (_DB_MODULES in tests/conftest.py). A new sqlite table needs three things: a numbered migration in server/migrations/, the same schema in the module's own _ensure_* bootstrap, and the module listed in _DB_MODULES.

Testing conventions

  • Behaviour contracts over snapshots. Assert how two pieces of data relate; never freeze a catalog count or a model list.
  • Patch where production reads. Many modules import lazily inside functions, so monkeypatch the attribute the call site actually resolves.
  • Mock load_config with the normalized shape (rich chat_models entries, chat_model_meta present), not the raw example JSON.
  • A new SSE field needs a golden refresh and a Zod schema entry, or the UI silently drops it.

Continuous integration

Three workflows live in .github/workflows/.

WorkflowWhen it runsWhat it does
ci.ymlPushes to main, v* tags, every pull request, and manual dispatch.Three jobs. Backend on Linux with Python 3.13: ruff check, ruff format check, then pytest. Backend on macOS for the tests that can only pass on a Mac (the open and reveal routes shell out to open, and the sandbox runs under sandbox-exec); it skips on pull requests, since macOS runners bill at ten times the rate, so dispatch it by hand when a change touches those paths. Frontend on Linux: tsc --noEmit, vitest, ESLint, production build.
build-macapp.ymlPushes to main and v* tags that touch the shipped app, and manual dispatch.Runs macapp/build_app.sh then macapp/make_dmg.sh on an arm64 macOS runner, the same two scripts you would run locally. The DMG is a workflow artifact on every run; on a v* tag it also creates the GitHub release and attaches the DMG.
pages.ymlPushes to main that touch docs/, and manual dispatch.Uploads docs/ as-is and deploys it to GitHub Pages. There is no build step.

The backend jobs install a trimmed requirements.txt: the Apple-silicon and heavy ML pins are stripped, with torch constrained back to the version the app pins, so the runner installs fast and still exercises the same torch. If a new test imports the transcription stack, it belongs on the macOS job.

GitHub CI is a safety net, not the merge gate. Verify locally with the commands above and merge when they are green. Branch, keep commits granular, open a PR, merge, fast-forward local main, delete the branch. Commit messages stay short and precise, and never end with a dash.

Cutting a release

An annotated vX.Y.Z tag is the whole release trigger. Pushing it runs build-macapp.yml, which builds the app and the DMG on a clean arm64 runner and creates the GitHub release with the DMG attached. Signing and notarization are optional and driven by repository secrets; with none configured the build falls back to ad-hoc signing, which works on the building machine but trips Gatekeeper elsewhere.

After a merge that touches the app, rebuild the DMG from the same main commit so a source install and the Mac app stay in parity. The DMG filename comes from git describe but its contents come from dist-app/, so verify the bundle, not the filename.

Working on these docs

The site in docs/ is hand-built static HTML and CSS with a little vanilla JavaScript: no build step, no dependencies, and no external network calls (the fonts are self-hosted), so it renders correctly on an isolated network. Serve it with python3 -m http.server from inside docs/ to preview.

  • Adding a page: create docs/<name>.html, copy the <head> and the script tags from an existing page, write your content inside <main class="doc" data-page="...">, and add an entry to assets/nav.js. The header, sidebar, breadcrumb, on-this-page table of contents, and prev/next links are all injected by assets/site.js from that one navigation model.
  • Adding a diagram: create assets/diagrams/<name>.js calling WSDiagram.mount("<name>-diagram", { ... }) with grid col and row coordinates, drop a <div id="<name>-diagram" class="diagram"> into the page, and include the config script after site.js.
  • Theming: every color is a CSS variable in assets/theme.css, defined for both light and dark. Use the existing variables; never hard-code a color.

The same folder is served by the backend at /docs-site and opened from the ? dock panel, so a docs change ships with the app as well as to Pages.

Contributing

Small fixes: open a pull request. For anything larger, read the architecture overview and the relevant subsystem page first, so the change lands in the right layer and reuses the existing approval, tool, and persistence plumbing instead of working around it. Match the surrounding code - the backend and frontend both have a consistent house style, and CI enforces the linting and file-size rules above.
