Model backends & modes

Whisper Studio can send a chat turn to three very different runtimes: an on-device model server, OpenAI GPT over Bedrock, or the default Anthropic Claude path. The choice is made from one thing (the model key you picked in the toolbar) and it happens before any tokens stream.

Every chat turn enters the same endpoint in server/chat/routes.py, but not every turn talks to the same provider. Only the on-device branch returns its own response object and exits the endpoint early; even that response runs the same unified engine internally, so the only real fork is which provider adapter the engine drives. Click a box in the diagram to trace where a given model key ends up.

One key, one engine, three adapters

The toolbar model key is latched on the first turn of a session, so switching models in Settings never disrupts an in-flight conversation. Once the system prompt and messages are assembled, the endpoint asks two yes/no questions in order, and the first "yes" wins:

  1. Is it a local model?

    server/chat/routes.py calls local_chat_response(...) (server/local/route.py). If is_local_model() matches the key (that is, the key is in the on-device registry; keys are prefixed local_ by convention), it returns a StreamingResponse and the turn runs entirely on-device.

  2. Cloud models: one engine, two adapters

    Claude and GPT turns run on the SAME unified turn engine (server/chat/engine/runner.py). The endpoint picks the provider adapter from chat_model_meta (provider == "openai_bedrock" selects the Responses adapter in server/chat/engine/openai.py; everything else uses the Bedrock adapter in server/chat/engine/anthropic.py) and hands the assembled turn to run_turn(...).

One loop, thin adapters. Rounds, budgets, wind-down reminders, proactive/reactive compaction, the salvage round, tool execution through the shared safety gate, approval pauses, and cost accounting all live in the engine and behave identically for every provider. Adapters own only the wire protocol. Compaction summarizes through one_shot with the session's own model, so no provider depends on another. The same engine also runs cron fires, subagents, and headless turns (run_headless_turn in server/exec/headless.py, a Python-callable entry with output_schema and ephemeral options), which is what gave those paths local-model support.

Context windows and compaction budgets

Before the engine can decide when to compact, it needs to know how large a prompt this model accepts. server/chat/engine/windows.py answers that for every provider, in this order: the context_window on the model's chat_models entry, then a per-family default, and for on-device models the live context size the model server is actually running at.

ModelInput cap
Fable 5.1, Fable 5.0, Opus 5, Opus 4.8, Opus 4.7, Opus 4.6, Sonnet 5, Sonnet 4.61,000,000 tokens
Haiku 4.5200,000 tokens
GPT-6 Astra922,000 tokens
GPT-5.6 Sol, Terra, Luna, GPT-5.5, GPT-5.4278,528 tokens (the cap the mantle deployments enforce)
Any other Claude id200,000 tokens (the Anthropic family default)
On-device modelsThe running context size, then the size you last asked for, then the registry ctx

The 1M figure is applied by model id rather than trusted from config: a Claude entry left at 200000 by an older config is lifted to 1,000,000 on read when its id belongs to a 1M-context family, because any other explicit value is treated as a deliberate override.

From the window the engine derives the usable prompt budget. The Claude window is total (prompt plus answer), so the answer allowance is reserved out of it: 64K tokens for Haiku, 128K for every other Claude tier, matching the adapter's own max_tokens clamp. The GPT deployments enforce a separate prompt-only cap, so nothing is reserved there. Local models reserve their max_output, defaulting to 4096. The result is floored at a quarter of the window so a misconfigured output reserve can never starve the prompt. Proactive compaction fires at 95 percent of that budget and the last-resort truncation at 98 percent, estimated at four characters per token. When a deployment rejects a prompt anyway, the engine reads the real cap straight out of the rejection text and budgets against that number from then on.

The Anthropic adapter (default)

This is the adapter most turns use, running the Claude models in your config: Fable 5.1 and 5.0, Opus 5, Opus 4.8, Opus 4.7, Opus 4.6, Sonnet 5, Sonnet 4.6, and Haiku 4.5. The engine loop from Chat & tool orchestration drives it, so the backend-specific parts are the Bedrock client, the request body (prompt-cache checkpoints, effort/thinking), and the resilience wrappers around each round.

The shared Bedrock client

All Bedrock traffic goes through a process-wide singleton boto3 bedrock-runtime client, one per region, cached in server/chat/infra.py. A fresh client per call multiplies boto3's connection pool by the number of concurrent agents and can exhaust the macOS default file-descriptor limit (256), so the cache exists to keep sockets bounded (the pool is capped at 32 connections). Changing the region in Settings clears the cache so the next call rebuilds it.

The streaming call is invoke_model_with_response_stream. Chunks arrive as content_block and message events, which the loop parses into text, thinking, and tool_use blocks as they stream.

Retry and reactive compaction

Each streaming invocation is wrapped by invoke_with_retry in server/infrastructure/bedrock_retry.py. The wrapper classifies every Bedrock error and reacts accordingly:

Error kindBehavior
Throttling (429)Retried with exponential backoff, up to 5 attempts (THROTTLE_MAX_RETRIES).
Other transient (for example, service unavailable)Retried up to 3 attempts (MAX_RETRIES).
Non-retryableRaised immediately, no retries.
Prompt too longRaised immediately as PromptTooLongError so the caller can compact.

Backoff is capped exponential: 500ms, 1s, 2s, 4s, up to a 10s ceiling. When the wrapper raises PromptTooLongError, the engine runs reactive compaction (server/chat/engine/runner.py, for every provider): it drops the oldest message pairs, calls compact_messages_with_claude(...), and retries the round. If the conversation is still too long after that, it surfaces an error asking you to start a new session. (Reactive compaction is the mid-stream safety net; the endpoint also compacts pre-emptively when history grows large. See Chat & tool orchestration.)

That wrapper only covers the request. A stream that has already returned HTTP 200 and then dies (Bedrock raises ModelStreamErrorException or InternalServerException as a non-chunk event; the OpenAI path sees a server_error or a bare transport timeout) never reaches it, so the engine handles those itself: the adapter reports the fault as a retryable round error and server/chat/engine/runner.py re-runs that round, up to twice, with a linear two-second backoff. It retries only while no answer text has streamed yet, since a retry would duplicate it, and only while a round is left in the turn budget, because each retry spends one. A round that completes resets the allowance, so one early blip cannot consume a long turn. Completed tool rounds are kept across the retry rather than thrown away.

Cost tracking

Cost tracking runs in the engine for every provider. Each round logs input, output, and prompt-cache token counts and an estimated USD cost (via estimate_cost; OpenAI's cached tokens are a subset of its input tokens and are billed once, local rounds record at $0), which feeds the session and daily spend caps. If a cap is exceeded, the turn stops with an error. See Cost tracking & budgets.

On-device models

The local backend (server/local/) runs a model entirely offline, in a subprocess the app starts, speaks to over an OpenAI-compatible /v1/chat/completions endpoint, and stops on shutdown. There are two such engines and the model's registry entry picks which one it belongs to:

  • llama-server for GGUF weights. This is upstream llama.cpp's own HTTP server and the only thing in the app that runs a GGUF. It is a real binary, found on PATH and then in the Homebrew locations, so if it is missing or too old a local turn fails loudly with the command that fixes it.
  • MLX for MLX-format weights, served by mlx_lm server running inside the app's own Python interpreter. Availability is therefore an import check, not a PATH lookup, and the error names the fix (venv/bin/pip install mlx-lm, or bash setup.sh --local).

The subprocess is the point. Each server owns the chat template plus the tool-call and reasoning parsers for the model families it supports, so a model added to config gets parsed tool_calls and a separate reasoning channel with no per-family marker code in this repo. Nothing under server/local/ contains model-specific tokens. Both engines speak the same SSE shape, so the adapter, the stream parser, and the turn engine above them are engine-agnostic.

server/local/route.py
The bridge the endpoint calls. Detects a local key, then returns the unified engine with the LocalAdapter (server/chat/engine/local.py) under the offline LOCAL policy. It also builds the lean system prompt and threads the composer's context-size request.
server/local/serving.py
The engine facade every other module calls. It is the one place that knows which engine a model key belongs to, and it owns the cross-engine residency rule. It also holds the non-streaming complete(...) used by the workspace index and the on-device session summariser, which deliberately sends no tools.
server/local/llama_server.py
The GGUF subprocess lifecycle: locating the binary (PATH, then Homebrew) and checking its build, starting / reusing / restarting it, the /health wait, stop(), and orphan reaping. It knows nothing about chat, tools, or SSE.
server/local/mlx_server.py
The same lifecycle for mlx_lm server. Its weights are a whole-repo snapshot directory rather than one file, it loads them lazily on the first request (so the facade fires a one-token warmup, otherwise "loaded" would lie until the first real turn), and it has no context-size flag at all.
server/local/server_stream.py
llama-server protocol helpers the LocalAdapter builds on: the /v1/chat/completions SSE parser, the streamed tool_calls accumulator, loose-argument coercion, tool-result message rendering, and the local post-turn memory hooks. The agentic loop itself lives in the unified engine.
server/local/registry.py
The effective model registry: the curated Discover catalog (RECOMMENDED_LOCAL_MODELS) gated on downloaded weights, merged with every is_local entry in config's chat_models, config winning per key.
server/local/runtime.py
Everything around the weights: the live registry view (LOCAL_MODELS), GGUF download and paths, capability flags, the sticky context-size request, and build_local_system_prompt(...).

Loading and unloading a model

ensure_serving(key, n_ctx) in server/local/serving.py is the whole entry contract: guarantee this model is being served at this context size, and return its base URL. It reuses the running process when it already matches, and otherwise stops what is running and starts a new one, because only one local model is resident at a time, across both engines. Chat weights and the speech stack already share unified memory on the machines the on-device build targets (for example an M3 with 18GB), so loading an MLX model evicts a running GGUF one and the other way round.

The order inside a transition matters and is fixed: validate that the engine is usable, then fetch the weights, and only then evict whatever is resident. A doomed request (mlx-lm not installed, an unknown key) or a first download that takes minutes must never leave the machine with nothing loaded. The whole transition runs under one lock so two concurrent loads for different engines cannot both end up resident, or SIGTERM each other's freshly started server.

A load that would displace the resident server waits for live chat turns to drain instead of stopping a model mid-answer, which is what used to kill an in-flight reply when you switched models in the composer. The wait gives up with a readable error after ten minutes (WHISPER_LOCAL_BUSY_WAIT_S), and the model-load endpoint can cancel out of it. A turn on the already-resident model skips all of this on a lock-free fast path, so it never queues behind another model's download. The call is blocking either way, so both the chat path and the load endpoint run it in a thread executor rather than on the event loop.

A GGUF process is started on an ephemeral port with four flags that carry the design:

FlagWhy
--jinjaActivates the model's own chat template and upstream's per-family tool-call parser. Without it, tools are not parsed at all.
--parallel 1One slot. The default is 4, and each slot gets its own KV cache, so the default quadruples KV memory for a single-user desktop app and can OOM Metal at a large context.
--cache-reuse 256Reuses cached prompt prefixes across turns, so a follow-up does not re-prefill the whole system plus tools prompt.
--reasoning-format autoPuts reasoning on its own channel (reasoning_content) instead of leaking raw thought markers into the answer.

WHISPER_LLAMA_SERVER_ARGS appends extra arguments for anything else you want to pass (WHISPER_MLX_SERVER_ARGS does the same for the MLX engine). The subprocess logs to models/.logs/, and a failed start raises with that log's tail, so a load error names its own cause. Each engine has its own startup timeout, WHISPER_LLAMA_SERVER_TIMEOUT and WHISPER_MLX_SERVER_TIMEOUT, both ten minutes by default, because a cold start reads gigabytes off disk.

Three things work differently on the MLX engine, and the facade hides all three. There is no context-size flag, so the window is whatever the model's own config carries and the size you pick is recorded only to give the context meter a number. The request's model field must be the literal default_model sentinel, because any other name makes mlx_lm try to download that name from the Hub. And tool_choice is ignored, so the final round's "no more tools" rule is enforced by sending no tools list at all rather than by asking for one.

The child runs in its own session, so a signal aimed at the app cannot take the model down mid-turn. The flip side is that SIGKILL on the app (force quit, OOM killer) skips the shutdown hook and orphans a process holding its port and gigabytes of RAM, so startup calls reap_orphans(), which sweeps leftovers from both engines. Matching is deliberately narrow: only processes whose model path is inside our models/ directory, never a llama-server or mlx_lm the user runs for their own purposes.

What a local turn does differently

  • A Discover-driven registry. The app ships no local chat models: a fresh install has an empty on-device catalog until you download one from Settings > Models > Discover. RECOMMENDED_LOCAL_MODELS in server/local/registry.py is a curated Discover catalog of four models (local_gemma, local_gemma_coder, local_qwen35_9b, local_ministral3_14b); a recommended model only enters the effective catalog once its weights are on disk, so a model downloaded by a prior release is never orphaned. Each recommended entry carries size_bytes so Discover can warn about memory fit before the download starts. User installs land in chat_models and are always present, even mid-download; the effective list merges config entries over the recommended catalog, config winning per key. Adding a model is a one-place change: an entry carrying repo_id, filename, and dir alongside the picker fields becomes downloadable, loadable, and selectable with no code change. An MLX entry adds engine: "mlx" and needs only repo_id and dir, because its weights are a whole-repo snapshot rather than a single file. An entry still missing a weight field after the merge is dropped with a warning rather than failing later at load time.
  • A lean system prompt. The cloud system prompt is tool-heavy and workspace-heavy (roughly 2 to 2.5K tokens the local model cannot act on), so build_local_system_prompt(...) drops it and keeps a short identity plus project and memory context. This speeds prefill and frees context space. With tools on it swaps in a tools-positive identity (the no-tools one makes the model refuse instead of calling what is declared) and, when a workspace is connected, a short marker telling it to reach the code through the ws_* tools.
  • A configurable context window. llama.cpp fixes the window when the server starts, so changing it restarts the process. ensure_serving resolves the size in order: an explicit request, then the last size the user asked for, then the model's registry ctx, then 32K (config entries with no ctx also default to 32K). That second tier is sticky on purpose: a chat turn only asks that the model be resident, and without it a lazy start later in the session would restart the server back down at the model default while the badge still reads a larger size. The chat-input slider is the explicit request, from the 32K floor (also the default) up to 256K, and anything above 32K confirms first because the KV cache grows with the window. The slider value rides on every local chat turn (local_context_window in the request body, clamped server-side to 2048 through 262144 in server/local/route.py), so a lazy server start can never run at a stale size, and it is recorded via set_requested_n_ctx so non-chat callers reuse it. On the MLX engine the slider only labels the context meter: mlx_lm has no context-size flag, so the window is the one baked into the model's own config.
  • The full tool pool, always. There are no user-facing gates: like the cloud paths, a tool-capable local model always gets the full pool, and a thinking-capable one always thinks. The old per-turn toggles (local_tools / local_tool_scope / local_thinking) are gone; the capability flags in the model registry are the only switch. The full pool renders a roughly 17.2K-token prompt, which is why the 32K default context exists (a 16K window would reject the very first tool turn); because it is a stable prompt prefix, llama-server's prefix cache absorbs the prefill cost after turn one.
  • Native tool messages, and looser arguments. Executed results go back as real OpenAI tool messages, which is a much stronger signal than folding them into a user turn. Because llama-server passes through whatever the model produced (Bedrock validates against the schema first), arguments are coerced toward their declared JSON-schema types before reaching an executor, so a "path": ["a.py"] slip does not waste the call on an AttributeError. Parallel tool calls work here, matching how the cloud paths batch reads.

The loop itself matches the cloud paths: up to 50 tool rounds, with calls forbidden on the last round so the model must synthesize an answer from what it has. Tool execution goes through the engine's shared execute_tool_batch and process_tool_results pipeline, so an on-device turn is gated by the same permission modes and approval flow, and a pause lands in the unified pause store (paused_sessions in server/chat/engine/pause.py) that the approved_tool_result continuation turn restores from, for local and cloud alike. When progressive tool disclosure is on (the progressive_tools flag, server/chat/tool_partition.py), the advertised pool everywhere is the core set plus session-activated tools, with the rest reachable through a deferred index via tool_search. On-device turns are billed at $0 but still emit a usage frame in the cloud shape. It just never touches AWS.

Summarising a huge transcript reuses the resident model. Condensing an oversized transcript runs a fast per-chunk extraction (the map step), and because only one on-device model is resident at a time, that step runs on the model you are chatting with (its key is threaded into the condense call), falling back to whatever model is currently resident (loaded_key()) and then the first downloaded model - rather than loading a fixed model and evicting the one you are chatting with. So the map step never restarts the model server on a different model. See Transcript summarization.

OpenAI on Bedrock

GPT models are invoked through Bedrock but in OpenAI request/response format (the Responses API shape on the bedrock-mantle endpoint). Their turns run on the same engine as everything else through the adapter in server/chat/engine/openai.py, which owns the mantle stream quirks (early release, heartbeats) and prompt-too-long detection against the model's real input window.

server/openai_bedrock/runtime.py
The runtime plumbing the adapter builds on: backend detection (is_openai_model), bearer-token auth and client construction (streaming + a sync twin for one-shot calls like compaction summaries), region resolution, request-mapping helpers, and the effort and verbosity mappings below.

Two GPT-specific controls are mapped from the app's own settings:

  • Reasoning effort. reasoning_effort_for(...) maps the app's effort label to OpenAI's reasoning effort. On GPT-5.4/5.5 the ladder tops out at xhigh, so the app's extra, max, and ultracode all collapse to it. GPT-5.6 and up add a max tier above xhigh: when _supports_max_effort(...) is true the top-tier labels (max / ultracode) ride it, while only extra always collapses to xhigh. GPT-6 (Astra) also has no none rung: its ladder runs low through max, and a none label degrades to low instead of being rejected by the endpoint.
  • Verbosity. verbosity_for(...) resolves the response verbosity (low / medium / high): a per-request override wins, then the model's configured default, otherwise medium.

GPT follows instructions literally, so a prompt like "think for N seconds" can turn into an actual wait. To avoid that, the OpenAI path drops the sleep tool from the pool and appends a short note to the (Claude-tuned) system prompt telling the model to interpret timing phrases as "reason briefly." Requests route to the app-wide bedrock_region, with an optional per-model openai_region override in chat_model_meta. GPT-6 Astra ships with us-west-2 pinned: at launch bedrock-mantle served it there only, even though the model is listed in every US region.

The decision chain above describes the top-level chat turn. The agent and subagent runtime is provider-agnostic too (WS-C): server/agents/providers/ holds base, anthropic, and openai adapters, and get_adapter(model_key, model_id) returns a ProviderTurn in canonical Anthropic shape, so a subagent can run on GPT-on-Bedrock as well as on Claude (with effort propagation and shared AGENT_CALL_CONCURRENCY). See The ultracode workflow runtime.

Where the model list comes from

The cloud model catalogue is config-driven, resolved in server/infrastructure/config.py and read through the thin accessors in server/chat/infra.py:

Config keyWhat it holds
chat_modelsMap of model key to its entry. A plain string is read as the model id; the usual form is an object carrying the id plus its metadata.
chat_model_metaThe metadata half of that map after normalization: label, context_window, thinking mode, supports_tools, is_local, engine, provider, effort_tier, and verbosity.
chat_models_disabledKeys hidden from the composer picker. A disabled on-device model stays manageable in Models, so its weights can still be deleted.
default_chat_modelThe key used when no model is selected.
bedrock_regionThe AWS region for the shared Bedrock client.
model_fallback_enabledOff by default. Turns on the automatic downgrade described below.

On-device models sit in the same chat_models map, marked is_local and carrying their weight fields (repo_id, filename, dir, and optionally ctx, defaulting to 32K). server/local/registry.py merges those over the recommended Discover catalog, where a recommended model only counts once its weights are on disk, and their id is a local: sentinel that never reaches Bedrock. For every field the Settings UI writes, see Settings & config keys.

Data-retention consent

One piece of model metadata needs its own path: requires_data_retention. Mythos-class models such as Fable 5.0 and 5.1 only run when the AWS account's Bedrock data-retention mode is provider_data_share, so selecting one routes through a consent screen (src/components/chat/dataRetentionConsent.tsx) before the model is used. The setting is account-wide and managed just-in-time around model selection rather than left on permanently: acknowledging the screen enables it, and switching back to a non-retention model offers to return the account to zero retention (mode none).

Falling back to a cheaper model

Settings > Costs has a checkbox, Enable model fallback (downgrade model when approaching budget). It is off by default. With it on, the chat endpoint resolves the session's model through server/infrastructure/model_fallback.py before the turn starts: once the session or daily spend reaches 80 percent of its cap, the turn runs on the next cheaper model instead.

"Next cheaper" is computed rather than hardcoded. The chain is derived from the authoritative price table in server/costs/tracker.py, so it tracks the live catalog instead of drifting, and the pick is the most expensive model whose list price is strictly below the current one, which is the smallest capability drop that still relieves the pressure. If that model is not configured in this install, the resolver keeps walking down rather than silently skipping the downgrade. A model with no price entry is never downgraded, since it bills at zero already. With the checkbox off, the model you selected is the model that runs, and a cap is enforced by stopping the turn instead. See Cost tracking & budgets.

Family aliases for agent overrides

Catalog keys are versioned (opus4.8, sonnet5), but a spawned agent or a workflow script often asks for a family name instead (opus, sonnet, haiku). server/agents/model_resolve.py resolves that to the newest configured key in the family and reports the substitution in the run's warning, rather than failing silently back to the default model. An override that still does not resolve, or that names an on-device model without tool support, falls back to the default and says why.

Model backend is not model mode

This is the distinction that trips people up. The chat model (which backend runs your turn) is one setting, chosen in the toolbar. The model mode (cloud / hybrid / local) is a different setting entirely, and it controls the indexing and retrieval stack, not the chat model.

Chat model (toolbar)

Selects the backend for the conversation itself: Claude, GPT, or an on-device model. This is the decision chain on this page.

Model mode (cloud / hybrid / local)

Selects where the RAG stack runs: embeddings, the reranker, and entity extraction for the workspace index. It does not change your chat model. A fresh install starts in local mode.

So you can, for example, chat with cloud Claude while your index embeddings run locally, or run an on-device model while nothing about your indexing changes. The two settings are independent. For a hands-on tour of the mode dial, see the Model modes tutorial; for what each capability actually runs in each mode, see Index / GraphRAG & search.
