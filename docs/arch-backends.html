Model backends & modes

Whisper Studio can send a chat turn to three very different runtimes: on-device Gemma, OpenAI GPT-5.x over Bedrock, or the default Anthropic Claude path. The choice is made from one thing (the model key you picked in the toolbar) and it happens before any tokens stream.

Every chat turn enters the same endpoint in server/chat/routes.py, but not every turn talks to the same provider. Two of the three backends are self-contained side paths that return their own SSE stream and exit early. Click a box in the diagram to trace where a given model key ends up.

One key, one engine, three adapters

The toolbar model key is latched on the first turn of a session, so switching models in Settings never disrupts an in-flight conversation. Once the system prompt and messages are assembled, the endpoint asks two yes/no questions in order, and the first "yes" wins:

  1. Is it a local model?

    server/chat/routes.py calls local_chat_response(...) (server/local/route.py). If is_local_model() matches the key (that is, the key is in the on-device registry; keys are prefixed local_ by convention), it returns a StreamingResponse and the turn runs entirely on-device.

  2. Cloud models: one engine, two adapters

    Claude and GPT turns run on the SAME unified turn engine (server/chat/engine/runner.py). The endpoint picks the provider adapter from chat_model_meta (provider == "openai_bedrock" selects the Responses adapter in server/chat/engine/openai.py; everything else uses the Bedrock adapter in server/chat/engine/anthropic.py) and hands the assembled turn to run_turn(...).

One loop, thin adapters. Rounds, budgets, wind-down reminders, proactive/reactive compaction, the salvage round, tool execution through the shared safety gate, approval pauses, and cost accounting all live in the engine and behave identically for every provider. Adapters own only the wire protocol. Compaction summarizes through one_shot with the session's own model, so no provider depends on another.

The Anthropic adapter (default)

This is the adapter most turns use, running Claude Haiku, Sonnet, or Opus. The engine loop from Chat & tool orchestration drives it, so the backend-specific parts are the Bedrock client, the request body (prompt-cache checkpoints, effort/thinking), and the resilience wrappers around each round.

The shared Bedrock client

All Bedrock traffic goes through a process-wide singleton boto3 bedrock-runtime client, one per region, cached in server/chat/infra.py. A fresh client per call multiplies boto3's connection pool by the number of concurrent agents and can exhaust the macOS default file-descriptor limit (256), so the cache exists to keep sockets bounded (the pool is capped at 32 connections). Changing the region in Settings clears the cache so the next call rebuilds it.

The streaming call is invoke_model_with_response_stream. Chunks arrive as content_block and message events, which the loop parses into text, thinking, and tool_use blocks as they stream.

Retry and reactive compaction

Each streaming invocation is wrapped by invoke_stream_with_retry in server/infrastructure/bedrock_retry.py. The wrapper classifies every Bedrock error and reacts accordingly:

Error kindBehavior
Throttling (429)Retried with exponential backoff, up to 5 attempts (THROTTLE_MAX_RETRIES).
Other transient (for example, service unavailable)Retried up to 3 attempts (MAX_RETRIES).
Non-retryableRaised immediately, no retries.
Prompt too longRaised immediately as PromptTooLongError so the caller can compact.

Backoff is capped exponential: 500ms, 1s, 2s, 4s, up to a 10s ceiling. When the wrapper raises PromptTooLongError, the endpoint runs reactive compaction: it drops the oldest message pairs, calls compact_messages_with_claude(...), and retries the round. If the conversation is still too long after that, it surfaces an error asking you to start a new session. (Reactive compaction is the mid-stream safety net; the endpoint also compacts pre-emptively when history grows large. See Chat & tool orchestration.)

Cost tracking

Cost tracking runs in the engine for every provider. Each round logs input, output, and prompt-cache token counts and an estimated USD cost (via estimate_cost; OpenAI's cached tokens are a subset of its input tokens and are billed once, local rounds record at $0), which feeds the session and daily spend caps. If a cap is exceeded, the turn stops with an error. See Cost tracking & budgets.

On-device models

The local backend (server/local/) runs a quantized GGUF model entirely offline, through llama-server: upstream llama.cpp's own HTTP server, run as a subprocess. The app starts it, speaks its OpenAI-compatible /v1/chat/completions endpoint, and stops it on shutdown. There is no in-process engine and no fallback, so if the binary is missing or too old a local turn fails loudly with the command that fixes it.

The subprocess is the point. llama.cpp's server owns the chat template plus the tool-call and reasoning parsers for every model family it supports, so a GGUF added to config gets parsed tool_calls and a separate reasoning channel with no per-family marker code in this repo. Nothing under server/local/ contains model-specific tokens.

server/local/route.py
The bridge the endpoint calls. Detects a local key, then returns the unified engine with the LocalAdapter (server/chat/engine/local.py) under the offline LOCAL policy. It also builds the lean system prompt and threads the composer's context-size request.
server/local/llama_server.py
The subprocess lifecycle: locating the binary (PATH, then Homebrew) and checking its build, ensure_serving(key, n_ctx) to start / reuse / restart it, the /health wait, stop(), orphan reaping, and a non-streaming complete(...) for non-chat callers. It knows nothing about chat, tools, or SSE.
server/local/server_stream.py
llama-server protocol helpers the LocalAdapter builds on: the /v1/chat/completions SSE parser, the streamed tool_calls accumulator, loose-argument coercion, tool-result message rendering, and the local post-turn memory hooks. The agentic loop itself lives in the unified engine.
server/local/registry.py
The effective model registry: built-in defaults merged with every is_local entry in config's chat_models, config winning per key.
server/local/runtime.py
Everything around the weights: the live registry view (LOCAL_MODELS), GGUF download and paths, capability flags, the sticky context-size request, and build_local_system_prompt(...).

The model server

ensure_serving(key, n_ctx) is the whole entry contract: guarantee this model is being served at this context size, and return its base URL. It reuses the running process when it already matches, and otherwise stops it and starts a new one, because only one model is resident at a time (the on-device build targets a memory-constrained machine, for example an M3 with 18GB). Weights are fetched before the process is spawned, so a missing GGUF is not an opaque subprocess exit, and the call is blocking, so both the chat path and the load endpoint run it in a thread executor rather than on the event loop.

The process is started on an ephemeral port with four flags that carry the design:

FlagWhy
--jinjaActivates the model's own chat template and upstream's per-family tool-call parser. Without it, tools are not parsed at all.
--parallel 1One slot. The default is 4, and each slot gets its own KV cache, so the default quadruples KV memory for a single-user desktop app and can OOM Metal at a large context.
--cache-reuse 256Reuses cached prompt prefixes across turns, so a follow-up does not re-prefill the whole system plus tools prompt.
--reasoning-format autoPuts reasoning on its own channel (reasoning_content) instead of leaking raw thought markers into the answer.

WHISPER_LLAMA_SERVER_ARGS appends extra arguments for anything else you want to pass. The subprocess logs to models/.logs/llama-server-<key>.log, and a failed start raises with that log's tail, so a load error names its own cause.

The child runs in its own session, so a signal aimed at the app cannot take the model down mid-turn. The flip side is that SIGKILL on the app (force quit, OOM killer) skips the shutdown hook and orphans a process holding its port and gigabytes of RAM, so startup calls reap_orphans(). Matching is deliberately narrow: only processes whose --model path is inside our models/ directory, never a llama-server the user runs for their own purposes.

What a local turn does differently

  • A config-driven registry. The built-ins (local_gemma, local_gemma_coder) stay in code so a fresh checkout with no config.json still has working on-device models, but the effective list is those merged with any is_local entry in chat_models, config winning per key. Adding a model is a one-place change: an entry carrying repo_id, filename, and dir alongside the picker fields becomes downloadable, loadable, and selectable with no code change. An entry still missing a weight field after the merge is dropped with a warning rather than failing later at load time.
  • A lean system prompt. The cloud system prompt is tool-heavy and workspace-heavy (roughly 2 to 2.5K tokens the local model cannot act on), so build_local_system_prompt(...) drops it and keeps a short identity plus project and memory context. This speeds prefill and frees context space. With tools on it swaps in a tools-positive identity (the no-tools one makes the model refuse instead of calling what is declared) and, when a workspace is connected, a short marker telling it to reach the code through the ws_* tools.
  • A configurable context window. llama.cpp fixes the window when the server starts, so changing it restarts the process. ensure_serving resolves the size in order: an explicit request, then the last size the user asked for, then the model's registry ctx (32K for the built-ins), then 16K. That middle tier is sticky on purpose: a chat turn only asks that the model be resident, and without it a lazy start later in the session would restart the server back down at the model default while the badge still reads 32K or 64K. The chat-input slider is the explicit request, from 16K up to Gemma's 256K maximum, and anything above 16K confirms first because the KV cache grows with the window.
  • A shrinkable tool set. The Tools dropdown sets a scope of off, core, core_web, or all, and the default is core_web rather than the full pool: the full pool prefills for around 50s on a 12B model (a few seconds for the core set) and renders a prompt large enough that a 16K window rejects the very first turn, which is why the built-ins default to 32K. Advertising fewer tools makes the prompt smaller and prefill faster.
  • Native tool messages, and looser arguments. Executed results go back as real OpenAI tool messages, which is a much stronger signal than folding them into a user turn. Because llama-server passes through whatever the model produced (Bedrock validates against the schema first), arguments are coerced toward their declared JSON-schema types before reaching an executor, so a "path": ["a.py"] slip does not waste the call on an AttributeError. Parallel tool calls work here, matching how the cloud paths batch reads.

The loop itself matches the cloud paths: up to 50 tool rounds, with calls forbidden on the last round so the model must synthesize an answer from what it has. It reuses the same executor and approval pipeline (run_tool_round), so an on-device turn is gated by the same permission modes and approval flow, and a pause stores its state in memory for resume_chat(...) to pick up. On-device turns are billed at $0 but still emit a usage frame in the cloud shape. It just never touches AWS.

Summarising a huge transcript reuses the resident model. Condensing an oversized transcript runs a fast per-chunk extraction (the map step), and because only one on-device model is resident at a time, that step runs on the model you are chatting with (its key is threaded into the condense call), falling back to whatever model is currently resident (loaded_key()) and then the first downloaded model - rather than loading a fixed model and evicting the one you are chatting with. So the map step never restarts the model server on a different model. See Transcript summarization.

OpenAI on Bedrock

GPT-5.x models are invoked through Bedrock but in OpenAI request/response format (the Responses API shape on the bedrock-mantle endpoint). Their turns run on the same engine as everything else through the adapter in server/chat/engine/openai.py, which owns the mantle stream quirks (early release, heartbeats) and prompt-too-long detection against the model's real input window.

server/openai_bedrock/runtime.py
The runtime plumbing the adapter builds on: backend detection (is_openai_model), bearer-token auth and client construction (streaming + a sync twin for one-shot calls like compaction summaries), region resolution, request-mapping helpers, and the effort and verbosity mappings below.

Two GPT-5.x-specific controls are mapped from the app's own settings:

  • Reasoning effort. reasoning_effort_for(...) maps the app's effort label to OpenAI's reasoning effort. On GPT-5.4/5.5 the ladder tops out at xhigh, so the app's extra, max, and ultracode all collapse to it. GPT-5.6 and up add a max tier above xhigh: when _supports_max_effort(...) is true the top-tier labels (max / ultracode) ride it, while only extra always collapses to xhigh.
  • Verbosity. verbosity_for(...) resolves the response verbosity (low / medium / high): a per-request override wins, then the model's configured default, otherwise medium.

GPT-5.x follows instructions literally, so a prompt like "think for N seconds" can turn into an actual wait. To avoid that, the OpenAI path drops the sleep tool from the pool and appends a short note to the (Claude-tuned) system prompt telling the model to interpret timing phrases as "reason briefly." The default region for this provider is us-east-2, overridable per model.

The "self-contained side path" framing above describes the top-level chat turn. The agent and subagent runtime is provider-agnostic too (WS-C): server/agents/providers/ holds base, anthropic, and openai adapters, and get_adapter(model_key, model_id) returns a ProviderTurn in canonical Anthropic shape, so a subagent can run on GPT-on-Bedrock as well as on Claude (with effort propagation and shared AGENT_CALL_CONCURRENCY). See The ultracode workflow runtime.

Where the model list comes from

The cloud model catalogue is config-driven, resolved in server/infrastructure/config.py and read through the thin accessors in server/chat/infra.py:

Config keyWhat it holds
chat_modelsMap of model key to the Bedrock model id.
chat_model_metaPer-model metadata: label, thinking mode, supports_tools, is_local, provider, and effort levels.
default_chat_modelThe key used when no model is selected.
bedrock_regionThe AWS region for the shared Bedrock client.

On-device models sit in the same chat_models map, marked is_local and carrying their weight fields (repo_id, filename, dir, and optionally ctx). server/local/registry.py merges those over the built-ins it keeps in code, and their id is a local: sentinel that never reaches Bedrock. For every field the Settings UI writes, see Settings & config keys.

Data-retention consent

One piece of model metadata needs its own path: requires_data_retention. Mythos-class models such as Fable 5.0 only run when the AWS account's Bedrock data-retention mode is provider_data_share, so selecting one routes through a consent screen (src/components/chat/dataRetentionConsent.tsx) before the model is used. The setting is account-wide and managed just-in-time around model selection rather than left on permanently: acknowledging the screen enables it, and switching back to a non-retention model offers to return the account to zero retention (mode none).

Model backend is not model mode

This is the distinction that trips people up. The chat model (which backend runs your turn) is one setting, chosen in the toolbar. The model mode (cloud / hybrid / local) is a different setting entirely, and it controls the indexing and retrieval stack, not the chat model.

Chat model (toolbar)

Selects the backend for the conversation itself: Claude, GPT-5.x, or on-device Gemma. This is the decision chain on this page.

Model mode (cloud / hybrid / local)

Selects where the RAG stack runs: embeddings, the reranker, and entity extraction for the workspace index. It does not change your chat model.

So you can, for example, chat with cloud Claude while your index embeddings run locally, or run on-device Gemma while nothing about your indexing changes. The two settings are independent. For a hands-on tour of the mode dial, see the Model modes tutorial; for what each capability actually runs in each mode, see Index / GraphRAG & search.
