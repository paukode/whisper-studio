Settings & config keys

Every field in the in-app Settings panel, and the exact config key it writes. Use this page as a lookup when you want to hand-edit config or understand what a toggle actually changes.

Whisper Studio has no separate config UI to learn: the gear icon opens a Settings panel whose fields map one-to-one onto keys in your user config file (config.user.json, or legacy config.json; see Config layers for where it lives). Everything below is resolved by server/infrastructure/config.py, which merges several layers in priority order. If you prefer to edit JSON directly, the key names in the second column are what you write.

Most of these fields are also latched per session: the model, region, effort level, brief mode, and permission mode are snapshotted when a chat turn first starts, so changing them mid-conversation never disrupts an in-flight turn or invalidates the prompt cache. The new value applies to the next new session. See Persistence for the latch details.

Settings-UI fields

Open the panel with the gear icon in the top bar. Each row is one control:

SettingWhat it does
Bedrock Region The AWS region every Claude and GPT call is routed to. It must match a region where the model you selected is actually enabled, or Bedrock returns an access error. Defaults to us-east-1. See Region pitfalls.
Default Model The model new sessions start with: Haiku 4.5, Sonnet 4.6, Sonnet 5, Opus 4.6 / 4.7 / 4.8, Opus 5, Fable 5.0, GPT-5.4 / 5.5, GPT-5.6 Sol / Terra / Luna, or an on-device model when local mode is on. The picker only shows models valid for the current Model Mode (cloud hides on-device models and vice versa). The shipped default is opus5.0 (set in config.example.json, the SYSTEM layer every install actually reads); opus4.8 is only the code-level fallback used if that file is unreadable. Fable 5.0 requires the data-retention consent flow before it can be selected. Full catalog on Model backends.
Model Mode Where indexing and retrieval run: cloud (all on Amazon Bedrock), local (all on-device), or hybrid (pick a backend per capability). This also drives which chat models the picker shows. Changing it prompts a reload so the app re-initializes in the new mode. A dev checkout inherits cloud from config.example.json; a fresh packaged install is seeded to hybrid with on-device embed/rerank (Qwen3) and GLiNER entity extraction, but cloud Haiku as the indexing writer until you install a local chat model. See Model modes.
Feature Flags Per-feature on/off toggles for gated behavior (hybrid search, reranker, query rewrite, prompt caching, and others) without editing config.json by hand. Changes persist immediately. See Feature flags.
Effort Level The reasoning budget the model is given, from lowest to highest: low, medium, high, extra (also accepted under its alias xhigh), max, and ultracode. Higher effort trades latency and cost for deeper thinking. Default is high. The levels a model exposes depend on its tier: Opus 4.8, Opus 5, and Fable expose the full ladder up through ultracode; Sonnet and older Opus cap at max; GPT-5.5 and 5.6 run none through ultracode; Haiku and the local models have no effort control. The value is clamped to the nearest level the selected model supports when you switch models. ultracode is a session mode rather than a plain level - it sends the top reasoning effort plus dynamic-workflow orchestration. The old auto value is retired and is coerced back to a real level.
Permission Mode How the assistant is gated when it wants to act: default, auto, plan, acceptEdits, bypassPermissions, or dontAsk. Default is default (reads run freely, writes ask). See Permission modes and Permissions & approvals.
Tavily API Key Enables the web_search tool; web_fetch works without it. Left empty by default, which disables web search entirely. The API never returns the raw key back to the UI; you only see a masked hint. Prefer the environment variable path (see Tavily key).
Cost Limits Two spend caps in USD: a per-session cap and a per-day cap. When a running turn would exceed either, it stops with an error. 0 means unlimited (the default for both). See Cost tracking & budgets.
Models > Discover The model browser for on-device models. The app ships with no local model installed by default; Discover lists recommended models you can install, each graded by whether it actually fits your device's memory. Removing a local model deletes its weights; removing a cloud (Bedrock) model just tombstones it in the picker.
Import project One-shot migration from a Claude Code or Codex CLI project: its instructions file (CLAUDE.md or AGENTS.md) copies to WHISPER.md, its skills copy into the skills folder, and its .mcp.json translates into MCP server config. Never overwrites a file that already exists, and nothing it imports is executed as part of the import.
Permissions The full permission surface beyond the single mode dropdown: per-tool rules, per-category approval defaults, and the network egress policy. See Permission modes below.

These live inside a grouped settings rail rather than one flat list: Chat and models (Model mode; Models, with Chat / Discover / Transcription / Indexing sub-tabs), Tools and automation (MCP servers; Import project; Skills and plugins; Workflows and tasks, including Scheduled tasks and Hooks), and Access and usage (Keys and permissions - API keys, Permissions; Usage and advanced - Stats, Costs, Feature flags, Live preview).

Model mode and backends

model_mode picks where the index and retrieval pipeline runs; the backends object is consulted only in "hybrid" mode, where each capability can point at a different engine. Unset capabilities fall back to the cloud backend.

backends.embed
cohere or qwen3 - the embedding model for the index.
backends.rerank
cohere or qwen3 - the reranker applied to retrieved passages.
backends.ner
haiku, gliner, or an on-device model key (LLM-based NER) - entity extraction for the GraphRAG entity graph.
backends.index_llm
haiku, an on-device model key, local (follow whichever local model is currently active), or none - the model that summarizes and enriches indexed content. Installing a local chat model from Discover flips this to it automatically.

These map onto the same per-capability picks that setup.sh --hybrid pulls the on-device weights for. See Model backends & modes and Index / GraphRAG for how each capability is used.

Feature flags

The feature_flags key is a small namespace of booleans that gate optional behavior without a code change. The panel lives under Settings > Access and usage > Usage and advanced > Feature flags. Toggling one persists it immediately. Under the hood the toggle is surgical: it patches only that one boolean inside the feature_flags object and leaves every other byte of the config file untouched, so it never reflows your formatting or flattens the model catalog. The live state of each flag is exposed to the UI through the config endpoint so the panel can show what is currently on.

The full registry, from server/infrastructure/feature_flags.py:

FlagDefaultWhat it gates
companionfalseShow the cosmetic buddy companion in the chat corner. Purely visual; makes no model calls.
git_contexttrueInclude git status and instructions in the system prompt.
prompt_cachingtrueCloud (Bedrock) prompt caching of tool definitions and the static system prompt, to cut input-token cost on multi-turn conversations.
progressive_toolstrueProgressive tool disclosure: advertise a core tool set plus session-activated tools, with everything else discoverable via tool_search from a compact index. Cuts roughly 60-75% of tool-schema tokens per turn.
strict_ragtrueWhen index grounding is injected, withhold the workspace file/search tools so the model answers from the retrieved passages instead of re-crawling files.
rag_hybrid_searchtrueFuse keyword/BM25 (SQLite FTS5) results with dense vector search via reciprocal-rank fusion.
rag_rerankertrueCross-encoder reranking of fused retrieval candidates before grounding's top-k (Cohere Rerank 3.5 in cloud mode, Qwen3-Reranker-0.6B in local mode).
rag_query_rewritefalseUse a fast LLM (Haiku) to rewrite a follow-up question into a standalone search query before grounding. Adds one model call per grounded turn.
auto_memorytrueTwo-tier auto memory with extraction and recall: global (cross-workspace) plus project (workspace-scoped). Also gates whether the memory_* tools appear in the catalog.
session_memorytruePer-session structured summaries injected into the prompt.
goal_looptrueGoal loop + completion gate: a session goal (set with /goal) auto-continues the turn until a cheap evaluator judges it achieved, capped at 8 blocks. See The ultracode workflow runtime.

preview_toolstrueAssistant-controllable browser preview tools (start/stop/click/fill/eval/screenshot); they only surface once Playwright and Chromium are installed.

Unlike the latched fields, feature flags take effect right away rather than waiting for a new session, because they change server behavior rather than the cached prompt.

Transcript condensation keys

The map_reduce_summary object tunes how an oversized transcript is condensed before it reaches summarize_transcript or the main model. It has no Settings-UI field, so edit your user config file (or the config.example.json template) directly. Every size below is in characters (roughly 4 characters per token), and any malformed numeric value falls back to its default rather than failing the chat turn.

Sub-keyDefaultMeaning
enabledtrueMaster switch. When false, transcripts are never condensed and pass through unchanged.
threshold_chars600000Condense only above this size (about 150k tokens). Below it the transcript passes through with no extra LLM calls.
chunk_chars150000Per-chunk size for the cloud map step (about 37k tokens).
local_chunk_chars40000Per-chunk size in local mode (about 10k tokens; comfortably under the 32K on-device window).
overlap_chars800Overlap between adjacent chunks so nothing is lost at a boundary.
map_max_tokens1200Output cap for each per-chunk extract.
max_chunks40Cap on the number of chunks; the splitter re-chunks coarser before hitting it.
max_output_chars480000Cap on the aggregate condensed output in cloud mode (about 120k tokens), so the reduce turn does not overflow.
local_max_output_chars24000Tighter aggregate cap for the smaller local window.
engine"auto"Which model runs the map step. "auto" follows the model mode (cloud uses Haiku, local uses the on-device model); force "haiku" or "local" to override.

See Transcript summarization for how the map-reduce pipeline uses these values.

Permission modes

The permission_mode key controls how the assistant is gated when it wants to run a tool. You can also switch it inline with the Mode dropdown in the chat input. Per-tool rules under Settings > Permissions override the mode for specific commands, and per-category defaults below pin a mode for one kind of action.

ValueBehavior
defaultReads run freely; writes ask for approval.
autoA classifier decides per-tool, per-call; it runs whenever this mode is selected (rules edited via config_set).
planRead-only. The assistant plans but never executes.
acceptEditsFile edits auto-approve; deletes and shell commands still ask.
bypassPermissionsEverything runs without prompts.
dontAskReads auto-allow; writes are silently denied.

The auto mode reads three companion keys - auto_mode_allow, auto_mode_soft_deny, and auto_mode_environment - edited with config_set in chat or in your user config file. Selecting the mode is the opt-in: the classifier runs on every call that would otherwise ask. See Approval & permissions for the classifier and the pause-and-resume flow.

Per-category approval defaults

Beyond the single global mode above, permissions.json can carry a category_modes object: a per-category override keyed by the approval categories the app declares (write, delete, cli, save, worktree, preview, github, github-destructive, mcp, mcp-elicit), plus the policy-only workflow entry described below. A category with no entry falls back to the global mode, so you can, for example, leave the global mode at default while setting category_modes.cli to acceptEdits so shell commands stop asking but file deletes still do. One category is absolute: github-destructive (repo or ref deletion, PR merge, archive or rename, a raw API DELETE) always asks no matter what the global mode, a category override, a bypass mode, or a blanket session approval says.

workflow is the one entry that is not an approval-card category. It is read by server/workflows/launch_policy.py when the model launches a new ultracode workflow script: bypassPermissions launches with no card, auto launches a run whose budget is within the 600,000 output-token default and cards anything larger, dontAsk declines the launch, and any other mode shows the phase-preview card. Trusted saved workflows and resumes skip the gate, and no mode relaxes the runtime's server-side caps.

Rule justification and dry-run testing

Each permission rule can carry an optional justification string, an audit-trail note with no effect on evaluation, useful for remembering why a rule exists. Before saving a new rule, the rule editor's Test this rule button dry-runs a draft rule list against POST /api/permissions/rules/test without persisting anything, so you can check its effect first. Every rule change (add, edit, or the dry-run) also returns shadowed-rule warnings when an earlier rule in the list already matches everything a later one would, so a rule that can never fire gets flagged instead of silently doing nothing.

The auto-mode circuit breaker

Because the auto classifier judges one tool call at a time, it can drift over a long turn. A per-turn circuit breaker in server/security/permissions.py trips auto mode back to asking - for the rest of the turn - after either 3 consecutive classifier denials or 5 denials in the last 10 classifier calls. A tripped breaker surfaces as an AutoModeBreakerBanner in the UI with a one-click resume; the breaker itself resets automatically at the start of the next new turn.

Network egress policy

Sandboxed commands (ws_run_command, terminal_run, and friends) are network-open by default, matching the app's single-trusted-user assumption. An opt-in network_policy object in permissions.json tightens that: a tier of permissive (default, unrestricted), curated, or restrictive, plus a custom_allowed_domains list and a methods_only_safe flag. In a non-permissive tier, sandboxed commands are forced through a local SNI-filtering proxy (it never decrypts traffic, only reads the TLS ClientHello hostname) that enforces the domain allowlist; see the egress policy for the enforcement details and documented limitations.

Per-server MCP fields

Each connected MCP server (Settings > Tools and automation > MCP servers) carries its own config entry beyond the basic command / args / env (local, stdio) or url (remote, streamable HTTP) transport fields:

url
Reaches a remote server over streamable HTTP instead of spawning a local stdio child process. Mutually exclusive with command.
bearer_token_env_var
The name of an environment variable holding the bearer token for a remote server. Only the variable name is persisted; the actual token is read from the environment at connect time and never written to config.
approval_mode
The server's default approval tier: auto (no approval, the default for an unconfigured server), prompt (every call goes through the normal approval pipeline, category mcp), writes (calls that look read-only by name auto-execute, everything else prompts), or approve (every call always asks - a hard floor that no bypass mode or blanket session approval can skip).
tool_overrides
A map of tool name to approval tier, overriding approval_mode for specific tools on that server.
enabled_tools / disabled_tools
Allow/deny lists of tool names for the server. An empty allowlist permits everything; disabled_tools wins on overlap with enabled_tools.

When a connected server asks the human a question mid-call (an elicitation), it is surfaced through the approval pipeline under its own category, mcp-elicit, rather than answered silently. See the MCP tools for how these fields interact with what the model can call.

The Tavily key

Web search is off until a Tavily key is present. You can set it two ways, and the environment variable always wins:

  1. Environment variable (preferred)

    Export TAVILY_API_KEY in your shell. It overrides the tavily_api_key config value and is re-read on every config load, so a rotated key applies without a restart and never touches disk.

    echo 'export TAVILY_API_KEY=tvly-...' >> ~/.zshrc

  2. Settings field

    Paste the key into the Tavily API Key field. It is stored in your user config file. The config endpoint never returns the raw value - only a masked hint like tvly...abcd - so the UI can show that a key is set without exposing it.

See Web research to put the key to work and Environment variables for the full env list.

Config layers

A resolved config is the merge of five layers, lowest priority first. Higher layers override lower ones, and nested objects generally merge key-by-key.

#LayerSourceScope
1Defaultsbuilt into server/infrastructure/config.pyFallbacks for everything, used only when the SYSTEM file below can't be read.
2Systemconfig.example.json at the repo rootThe app-owned shipped defaults and model catalog. Read live on every config load, not just copied once.
3Userconfig.user.json (or legacy config.json) at the app homeYour own deltas on top of the shipped defaults: added local models, region/keys/flags, per-field overrides, a hide-list.
4Project.whisper/settings.json in the workspace rootPer-project overrides for a safe subset of keys.
5Environmentshell env vars (e.g. TAVILY_API_KEY)Secrets and deployment overrides; wins over everything.

The User layer lives at the app home: the repo root in a dev checkout (where setup.sh still seeds config.user.json - or the legacy monolithic config.json - from the example config on first run), or WHISPER_HOME in a packaged install. A packaged install never seeds config.json at all; it writes config.user.json directly, holding only your deltas. Either file is gitignored where it lives inside the repo. A project's .whisper/settings.json overrides your user config, but only for a project-safe subset of keys (region, model, effort, brief mode, permission mode, the auto-mode lists, cost caps, feature flags, the model catalog and its hide-list, and the permission-explainer and model-fallback toggles) - global-only secrets like the Tavily key are not accepted there. Environment variables override all four config layers.

The model catalog (chat_models) does not simply replace wholesale at every layer. Across the System and User layers it deep-merges additively: the shipped catalog always appears, and a User-layer entry either adds a new model key or overrides specific fields of a shipped one, so a hand-added local model survives the next app update untouched. chat_models_disabled (a list of keys, honored in the User and Project layers) then drops any of those merged models you don't want to see, without deleting their definition. Only the Project layer keeps the older wholesale-replace behavior: a project config that lists chat_models replaces the merged System+User catalog outright rather than adding to it.

Separately from that config subset, .whisper/settings.json may also carry an optional hooks key: arbitrary project hook code from the cloned repo. It is treated as untrusted and stays inert until the exact hook set is explicitly trusted (a SHA-256 of the canonical hooks, mirroring trusted skills), so a checked-out repo cannot run hook code on its own. See the Security model for the project-trust flow.

Secrets hygiene. Your user config file is gitignored where it lives inside the repo, but it sits on disk in plain JSON either way. Treat it like any credential store: do not sync it to untrusted backups, rotate keys after sharing your screen, and prefer the env-var path for the Tavily key.

Region and edit pitfalls

  • Region must be non-empty. A blank bedrock_region would build a malformed endpoint and fail every Bedrock call, so the loader coerces blank or missing values back to us-east-1 and strips stray whitespace. The Settings UI and the config API both refuse to persist a blank region or default model.
  • Region has to match the model. Enabling a model in one region and pointing bedrock_region at another produces an access error. If chat fails with an access or model-ID error, this mismatch is the usual cause.
  • Unknown default model falls back. If default_chat_model names a key that is not in the catalog, the loader falls back to opus4.8 (or the first available model), so resolution never dead-ends.
  • Prefer the UI or a surgical edit for the model catalog. The rich chat_models shape carries per-model metadata; a naive re-save can flatten it. To add or change a model, edit config.example.json (the canonical template) rather than hand-flattening the live file.
