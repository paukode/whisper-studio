Blocking hooks

Hooks let you gate what the assistant does. A hook can deny a tool call, rewrite its input, add context to a result or a prompt, or refuse to end a turn, deterministically, in your own code, before the model ever sees the outcome. The tool hooks run across every path: chat, sub-agents, cron, and headless turns. The Stop gate runs only on interactive cloud chat, through the completion gate.

The engine lives in server/hooks/: schema.py (the hook definition, outcome, and matcher semantics), engine.py (evaluation), config_loader.py (loading + project trust), and routes.py (the /api/hooks API). Click a box in the diagram to trace one tool call through the gates.

The events

A hook is registered for one event. Six exist, and the tool ones are gates the model cannot route around:

EventWhenWhat a hook can do
SessionStartTurn setup, before the model is calledReturn context to append to the last user message. A deny here is ignored: only the context is read.
UserPromptSubmitImmediately after, carrying the prompt (first 500 characters)Same: context only.
PreToolUseJust before a tool executesDeny the call (the model gets the reason instead of a result) or rewrite its input.
PostToolUseJust after a tool returns successfullyFold context into the result the model sees, for example a lint summary after a write. No rewrite.
PostToolUseFailureWhen a tool raised instead of returningThe same shape, with the error as the output. Context here must be returned as JSON; bare stdout is not read on this event.
StopWhen the turn is about to endRefuse to end: return a reason and the turn continues. Bounded by goal_max_consecutive_blocks (default 8) so it can't loop forever.

TurnEnd is accepted in config as an alias for Stop; there is one wire point, not two.

A hook is a HookDef (server/hooks/schema.py): an event, a shell command, a matcher (default *; exact name, a pipe|list, or a /regex/ against the tool name), a timeout (default 10 seconds, clamped to 1 to 60), an enabled flag, and an on_error policy (ignore or block). Its source is user, project, or plugin. Events with no tool name (Stop, SessionStart, UserPromptSubmit) match every hook regardless of matcher.

Where hooks live

Not in config.json. Your own hooks live in hooks.json under the app data directory (~/.whisper/data/hooks.json in an installed app), with project trust recorded beside it in hooks_trust.json. Project hooks live under a "hooks" key inside <workspace>/.whisper/settings.json. Both use schema v2, nested by event:

{"version": 2, "hooks": {
  "PreToolUse": [{"id": "h_ab12cd34",
                  "matcher": "ws_write_file|ws_edit_file",
                  "command": "./scripts/guard.sh",
                  "timeout": 10,
                  "enabled": true,
                  "on_error": "ignore"}],
  "Stop": []}}

The retired v1 format (a flat {event, tool, command} list) is still read once from your own hooks.json and rewritten as v2 on that first load, so an old file keeps working but never loads twice. Project settings are v2 only.

Two phases, one contract

run_hooks(event, payload) evaluates an event in two phases. Phase 1 runs in-process hooks, which today means Python plugins; a control dict here can short-circuit the whole event. Phase 2 runs shell hooks: user hooks first, then trusted project hooks, each filtered by its matcher against the tool name. The first deny wins and returns immediately. Rewrites chain: each subsequent hook sees the latest tool_input.

A shell hook receives the event payload as JSON on stdin and communicates back through both its exit code and its stdout:

  1. Exit code

    0 passes. 2 blocks: stderr becomes the reason the model sees. Any other code, or a timeout, is handled by the hook's on_error (ignore lets the call through and records the failure internally; block denies with stderr as the reason).

  2. Structured stdout

    A JSON object is parsed if present. {"decision": "deny", "reason": "..."} blocks. {"decision": "rewrite", "updatedInput": {...}} replaces the tool input, and only on PreToolUse: updatedInput without the rewrite decision is ignored, and rewriting is disabled outright on the other events. additionalContext is honoured on every event and appended to what the model reads.

  3. Plain stdout

    Non-JSON output becomes context, but only on PostToolUse, SessionStart and UserPromptSubmit. On the other events it is discarded, so a PostToolUseFailure hook must emit JSON to be heard.

Fields from other hook ecosystems are not implemented here and are silently ignored: permissionDecision, hookSpecificOutput, systemMessage, suppressOutput, and continue. additionalContext is a top-level key, not nested. Context reaches the model prefixed [Hook] on a tool result and [Hook context] when appended to a user message.

What a hook command runs with

  • stdin: the payload as JSON. The Stop event (and the Test button) send the full envelope, with a schema version, the session id, the workspace, the model id, and stop_hook_active; the tool and prompt events send a smaller hand-built dict without the schema and workspace keys.
  • Environment: your whole environment (minus the sandbox's denylist) plus five convenience variables, WHISPER_EVENT, WHISPER_TOOL, WHISPER_INPUT, WHISPER_OUTPUT and WHISPER_SESSION, the last three truncated to 500 characters.
  • Working directory: the connected workspace, or the app data directory when none is connected.
  • Execution: through the same sandbox every shell command uses, off the event loop, killed by process group on timeout.

Those variables are passed via the subprocess environment (env=), not prepended to the command. A command prefix would turn any hook that begins with a shell construct (if, for, case) into a syntax error whose exit code 2 reads as DENY, silently blocking every matched call.

A hook that fails under on_error: "ignore" is recorded on the outcome but not surfaced anywhere: neither the model nor the panel sees it. When you are debugging a hook, the Test button is the only place raw stdout and stderr are shown.

Wired across every path

PreToolUse, PostToolUse and PostToolUseFailure fold into the shared tool executor (execute_tool_batch) that chat, sub-agents, cron, and headless turns all call, so a deny or a rewrite applies uniformly no matter which consumer is running the turn. A denied call is reported to the model as [Hook denied] <reason> in place of the tool result. SessionStart and UserPromptSubmit fire once per cloud chat turn, in the route that assembles it.

The Stop gate is different. check_stop_hooks() is invoked only from run_completion_gate (server/goals/gate.py), and the engine only calls that gate when the turn's TurnPolicy has completion_gate on, which today is the interactive cloud-chat policy alone. Sub-agents force the gate off so a child can never trip the parent turn's evaluator, and cron, headless turns, and the local chat path all run with it off too. Cron instead verifies its own runs with a separate cron_verify step; see The goal loop.

The completion gate calls the Stop hooks; it does not register one. That matters when you read the transcript: the gate's own deliverable and verification checks emit the same stop_hook_block frame, which renders as Continuing (Stop hook), so a turn can continue itself with no Stop hook configured at all. Which check spoke is carried on the decision's source field.

server/hooks/engine.py
run_hooks(event, payload), the two-phase evaluator, check_stop_hooks(), and dry_run() for the Test button.
server/hooks/schema.py
HookDef / HookOutcome, the event list and its TurnEnd alias, matcher semantics, the stdin envelope, and config normalization.
server/hooks/config_loader.py
User hooks.json plus project hooks in <workspace>/.whisper/settings.json, the latter inert until trusted.

Project trust

Hooks are code that runs on your machine, so a hook that arrives inside a cloned repository is a supply-chain vector. Project hooks are therefore inert until you approve them: the panel shows each project hook's command before you trust it, and a SHA-256 of the trusted content is recorded so an edit re-arms the prompt. The document that is hashed is the same one that is then normalized and run, so there is no window in which a trusted hash could cover different code (the same trust model as skills and saved workflows). User hooks, the ones you wrote in your own config, are trusted by definition.

The API and the panel

The Settings Hooks panel is backed by the /api/hooks routes; the assistant does not create hooks itself (there is no hook tool and no /hooks command, since hooks are a user-owned guardrail).

RouteMethodPurpose
/api/hooksGET / POSTList hooks (grouped by event); create one.
/api/hooks/{hook_id}PUT / DELETEEdit or remove a hook.
/api/hooks/testPOSTDry-run a hook against a sample payload (the Test button) without wiring it live.
/api/hooks/project/approve · /revokePOSTTrust or untrust the current workspace's project hooks.

Live blocks surface in the chat: a denied call renders a hook_blocked card and a refused turn renders a stop_hook_block frame.
