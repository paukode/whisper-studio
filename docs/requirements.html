Requirements

Everything you need in place before installing: the operating system, the command-line tools a source install expects, an Amazon Bedrock account, model access for chat and for voice, an optional web-search key, and the disk and memory each model mode asks for.

Whisper Studio targets macOS. Which of the boxes below you have to tick depends on how you install. The Mac app needs almost nothing: an Apple Silicon Mac on macOS 14 or later, and an AWS account if you want cloud models. From source, most of the heavy lifting (the venv, Node, ffmpeg, ripgrep, the serving runtime) is done for you by setup.sh. Budget 15 to 25 minutes for a first install either way, most of it spent downloading.

Platform. Whisper Studio is a macOS app on Apple Silicon. Transcription uses the MLX runtime, on-device chat uses llama.cpp with Metal or MLX, the sandbox is sandbox-exec(5), and setup.sh leans on Homebrew for system packages. There is no supported Windows or Linux path today, though the Python backend itself is largely portable. Intel Macs are not supported.

Required command-line tools (source install)

You need exactly four tools present before you run the setup script. Everything else the app depends on is installed for you (see What setup.sh installs below). Open Terminal and run each check command; if it prints a version, you are set.

ToolWhy you need itCheck command
GitClone the repository (and used at runtime for the workspace Git integration and skill/plugin cloning).git --version
Python 3.12 or newerThe FastAPI backend. The Bedrock bidirectional streaming SDK that voice mode needs installs only on 3.12 or newer, so 3.12 is a hard floor.python3 --version
HomebrewInstalls the rest (ffmpeg, ripgrep, llama.cpp, and Git, Python or the AWS CLI if they are missing).brew --version
AWS CLIAuthenticates to Amazon Bedrock for cloud chat and voice mode. You run aws configure once.aws --version

If Homebrew is installed but Git, Python, or the AWS CLI is not, setup.sh can install them for you. Python is the one gate the script enforces up front, before it touches anything: if your python3 is older than 3.12 or missing, it offers to install python@3.12 via Homebrew (only in an interactive terminal) and persists it on your PATH. Decline, or run it non-interactively, and it exits rather than building a venv that cannot do voice. The fastest way to get all four in one line:

# Install Homebrew first if `brew --version` fails:
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
# then install Git, Python, and the AWS CLI:
brew install git python@3.12 awscli

You do not need to install Node.js. The Installation guide has copy-paste blocks for Homebrew, Python, and AWS if any check above fails. Come back here for the hardware and AWS specifics.

What setup.sh installs for you

The point of the required-tools list being so short is that setup.sh provisions everything else into an isolated venv/, so your system Python and global toolchain stay untouched. On a fresh run it:

  • Creates the venv/ and installs the Python dependencies from requirements.txt, preferring an extension-capable Homebrew Python so vector search can use sqlite-vec (a numpy fallback covers the rest).
  • Installs ffmpeg, ripgrep, git, and the AWS CLI via Homebrew when they are missing (ffmpeg decodes audio for Whisper; ripgrep backs the workspace search tools).
  • Installs Node 22.16.0 into the venv via nodeenv (the version is pinned in .nvmrc), then runs npm install and builds the frontend. You never install Node yourself.
  • Fetches the Playwright Chromium build used by the live-preview browser tools.
  • Installs the llama.cpp serving runtime (llama-server) via Homebrew, in every mode, so a model you install later from Discover serves without re-running setup. It upgrades the install when the build is older than 10090, which is what current model architectures need.
  • Fetches the three always-on speech models (about 190 MB): language ID plus the ReDimNet2 and ECAPA speaker encoders. These are the same three the Mac app ships inside its bundle, and every transcription path needs them.
  • Seeds a config.user.json with the first-run defaults if you have no config yet, then starts the backend on the first free port from 8000 and opens your browser.

Homebrew is therefore doing double duty: it is one of the four things you install by hand, and it is what the script reaches for to fill in ffmpeg, ripgrep, llama.cpp, and (if needed) Python, Git, or the AWS CLI. On a machine without Homebrew, the script warns and some of these steps are skipped; on-device chat in particular will not work, because llama-server has no fallback. See Installation for the full run-through and the setup flags.

Amazon Bedrock access

Cloud chat (Claude or GPT) runs on Amazon Bedrock, so for that path you need an AWS account with Bedrock access and the models you want enabled in your region. Fully on-device (--local) mode skips this section entirely - see Hardware, by model mode below. Two things trip people up here, both region-related:

  1. Enable model access. In the Bedrock console, request access to the Claude and/or GPT models you plan to use - each needs its own access grant, per model, per region.
  2. Match the region. Whatever region you set with aws configure must be the same Bedrock Region you enter in Whisper Studio's Settings, and the model must be enabled there. A mismatch shows up in chat as You don't have access to the model with the specified model ID.

Configure credentials once:

aws configure

The full walk-through, including how to create access keys, is in the AWS CLI configuration docs. Running aws configure installs nothing on the AWS side; it only stores your keys and default region locally.

No enabled cloud model, no cloud chat. Transcription and every local workspace tool run without AWS, and an on-device chat model needs no AWS at all. But for cloud chat, until the Claude or GPT model you selected is enabled in your region and your credentials can reach it, the chat panel returns AccessDeniedException. If that happens after install, run /doctor in the chat input for an automated AWS-credentials and Bedrock-connectivity check.

Voice conversations: Amazon Nova 2 Sonic access

Talking to the assistant out loud is a separate grant from chat. The voice stream runs on Amazon Nova 2 Sonic (amazon.nova-2-sonic-v1:0), so you need that model enabled in the Bedrock region voice uses, on the same credentials as chat. Three things decide whether the Talk button is available:

  • Model access. Request access to Nova 2 Sonic in the Bedrock console, in the region below.
  • The region. Voice follows your Bedrock Region setting unless you override it with the voice.region config key. The default is us-east-1. Nova 2 Sonic is offered in us-east-1, us-west-2, eu-north-1, and ap-northeast-1 only, so if your chat region is elsewhere, set voice.region to one of these.
  • Python 3.12 or newer, because the Bedrock bidirectional streaming SDK installs only there. The Mac app bundles 3.13, so this only ever bites a source install.

When any of these is missing the Talk button is disabled and its tooltip names the actual reason, including the model id and region to check. Dictation (the microphone button) is unaffected: it transcribes on-device and needs no Bedrock access at all. See Voice conversations.

Optional: a Tavily key for web search

The assistant's web-search tool is powered by Tavily. It is entirely optional, and only web_search needs a provider: either a Tavily key, or an enabled Amazon Bedrock AgentCore browser MCP server it falls back to. The web_fetch tool fetches URLs directly and works without any key, and everything else (chat, transcription, documents, the workspace IDE) works normally. The free tier covers personal use.

If you want it, sign up at app.tavily.com, copy the key, and either export it in your shell or paste it into the Settings UI. The environment variable takes priority when both are set, which makes rotation a one-line change:

echo 'export TAVILY_API_KEY=tvly-...' >> ~/.zshrc
source ~/.zshrc

See Configuration for how the environment, project, and user config layers stack.

Hardware, by model mode

The disk and memory you need depend on which model mode you run in. The mode decides where indexing and retrieval run and, with that, which model weights end up on your machine as you use the app. It is separate from the chat-model choice in the composer. A fresh install starts in local mode; you can pick a different one with a flag at install time (--cloud, --hybrid, --local) or change it any time under Settings, so this is not a permanent commitment.

ModeWhat runs on-deviceOn-device weights (downloaded on demand)Footprint
Cloud Only transcription. Embeddings, reranking, entity extraction, and chat all run on Bedrock. None beyond the transcription models. Lean. The smallest install.
Hybrid Whatever you choose per capability. You pick a backend (cloud or on-device) for each of embeddings, reranking, and entity extraction. The on-device index stack (Qwen3 embed and rerank, GLiNER), downloaded on your first index build, plus the llama.cpp serving runtime. About 5 GB of index weights once you index a folder; you decide at runtime what actually runs.
Local first-run default Everything on-device: chat (a model you install from Discover), embeddings and reranking (Qwen3), entity extraction (GLiNER), and transcription. Fully offline. The same index stack and runtime as Hybrid (~5 GB). Chat models are installed per model from Settings → Models → Discover. ~5 GB of index weights, plus several GB per chat model you install, plus the RAM to load the ones you run.

The rule of thumb: install time pulls only the three always-on speech models (about 190 MB: language ID and the two speaker encoders). Everything else downloads on demand, exactly like the Mac app's first launch: the transcription engines on your first recording, and in Hybrid and Local the same ~5 GB index stack (Qwen3 embed and rerank, GLiNER) on your first index build. No mode pulls a chat model: a fresh install ships none, and on-device chat models are chosen and downloaded per model (several GB each) from Settings → Models → Discover, so the total depends on which you install. The difference between Hybrid and Local is what you let run: Hybrid mixes per capability; Local commits to running everything locally.

Transcription is always on-device. In every mode, the Whisper, Parakeet, and Canary speech models run locally and audio never leaves the laptop. Whichever mode you chose, the engine you record with downloads on your first recording (with a progress banner), or you can pre-pull it from Settings → Models → Transcription. See Transcription & diarization.

A few practical notes on the on-device weights:

models/
Where every weight lands when it is downloaded on demand (at the repo root for a source install, under ~/.whisper for the Mac app). Downloads are idempotent and resume on first use if interrupted.
Memory
The ~5 GB figure is disk for the index stack. On-device chat with whichever model you install additionally needs enough free RAM to hold it while it runs. You do not have to guess: Discover grades every model against your machine's memory before you download, so you see whether it fits (and how much free RAM it needs) before committing. Only one on-device chat model is resident at a time, across both serving engines, because chat weights and the speech stack share the same unified memory. The smaller index models (Qwen3, GLiNER) are lighter.
Apple Silicon
The on-device runtimes (MLX for transcription, llama.cpp with Metal or MLX for chat models) are built for Apple Silicon. On-device chat is a macOS-arm64 feature.

Not sure which mode?

A fresh install starts in Local, so nothing leaves the machine until you decide otherwise. That is a fine place to stay if you want everything offline and have the disk and memory for an on-device chat model. Switch to Hybrid when you want cloud chat with some of the index stack on-device, and to Cloud for the leanest footprint with everything on Bedrock. Nothing is locked in: you change the mode in Settings at any time, and you can chat on Bedrock from a Local-mode install without switching, because the picker never hides every model. The full trade-offs, including which backend handles what, are on the Model modes page.
