Agent tools

The assistant is agentic: it calls tools to read and change your workspace, search the web, run git, remember things, schedule jobs, and coordinate sub-agents. This page lists every tool, grouped by area, with what each one does and whether it needs your approval.

With progressive tool disclosure (feature flag progressive_tools, default on) the model is advertised only a core set plus the tools this session has activated; every other tool lives as a one-line entry in a deferred index and loads on demand via tool_search. The same partition applies uniformly to interactive chat, sub-agents, cron runs, and headless turns; there is no separate full-catalogue path left when the flag is on. Tools that change files, run commands, or alter git or config state pause for your approval before they take effect; read-only tools run without prompting.

How tools reach the model

Tool definitions are part of the input the model reads before your message. Advertising the full catalogue (roughly 70-99 tool schemas) would cost about 15-25K tokens of JSON per turn, so with progressive tool disclosure (progressive_tools, default on) only the core and session-activated schemas are sent, while every deferred tool costs a single index line in the cached system block (build_deferred_index) rather than a full schema. That cuts roughly 60-75% of tool-schema tokens per turn. Sub-agents, cron runs, and headless turns go through the same partition as interactive chat (sub-agents additionally filter the pool by agent type). For cloud models the schemas bill as input tokens (a cost concern, not a speed one); local models run through the same unified engine and get the same partition, where fewer schema tokens also speed the on-device prefill. There is no per-model Tools dropdown any more: a tool-capable local model always gets the full treatment, with always-on thinking, a 32K context floor, and a per-turn CTX slider in the composer.

Dispatch itself is a pure name-to-function mapping. Each executor is registered with safety metadata (read_only, concurrent_safe, destructive) that the tool loop uses to decide what can run in parallel and what must pause for consent. Defaults are fail-closed: a tool is treated as unsafe unless it declares otherwise. See Tool dispatch & executors for the mechanics.

Throughout the tables, a ★ Core badge marks a tool in the progressive-disclosure core set (CORE_TOOLS, ~34 names in server/chat/tool_partition.py): always advertised, never deferred. Unbadged tools appear only as one-line entries in the deferred index until tool_search activates them for the session.

Approval at a glance

Two badges appear in the tables. Read the Approval & permissions page for the full pause-and-resume flow and per-tool rules.

read Runs freely

Read-only tools (reading files, searching, viewing git history, fetching pages) run without a prompt. Consecutive read-safe tools can also run concurrently in one batch.

approval Pauses for consent

Tools that write files, run commands, or change git or config state pause the turn on the server and wait for you to confirm. The same gate applies to both Claude and Gemma.

The direct-save flow

save_file, ws_create_file (without a workspace), and the document tools never ask where to save. The destination is resolved from your own words: "put it in Downloads" becomes ~/Downloads/<filename> (a ~ path is allowed), and if you named no location the file goes to ~/Documents/<filename>. The content is built and staged inside the app sandbox (server/workspace/paths.py, stage_file_bytes) before the approval card appears, so the card shows the exact final path; approving moves the staged file there (the save_to_path action, its own save approval category). Saved and created files render in the reply as clickable links that open with your OS default app.

Session worktrees

Separate from the ws_*_worktree task worktrees above, a chat session can be pinned into its own worktree via the enter_worktree / exit_worktree approval actions (approval category worktree; these are approval-card actions, not tools). Entering creates or reuses <repo>/.whisper/worktrees/<slug> on branch worktree-<slug> and persists across restarts (server/git/worktree_session.py); collisions are prevented by git itself, which allows a branch in only one worktree at a time - a session must cd in for its shell commands to follow, and file tools never do. Worktree-isolated sub-agents get a third variant that does redirect file tools automatically: see Sub-agents.

Shell commands run through the OS sandbox and the server-side approval router, not a client-asserted flag. Even in a permissive mode, denied commands and blocked paths are refused. See Sandbox & security.

Sub-agents

The assistant can delegate work to independent agents, each running its own full tool loop, and coordinate them as a team. The built-in agent types are general (full tool access), explore (read-only, fast model), plan (read-only, structured plans), verify (runs tests, returns a PASS/FAIL/PARTIAL verdict), and coordinator (orchestrates other agents, no direct file access). Any custom type saved under .whisper/agents/<name>.md also works as agent_type. See Sub-agents & the event bus and the sub-agents tutorial.

ToolWhat it doesApproval
spawn_agent ★ CoreSpawn one independent agent to handle a subtask. Options: agent_type (built-in or custom), agent_definition (define an ephemeral type inline), detach, and isolation.approval
promote_agent_typeSave an ephemeral agent type used earlier this session as a persistent custom type at .whisper/agents/<name>.md (project scope) or user-wide.approval
list_agentsList active agents in the session with their IDs, types, and status.read
send_messageSend a message to another agent by ID, or broadcast to all agents.read
list_sessionsList your other chat sessions (separate conversations, not agents) with IDs and titles.read
send_session_messageSend a short text message to another chat session found via list_sessions; never history or files, just the text.read
team_create ★ CoreCreate a named team of parallel agents for a complex, multi-part task.approval
team_deleteDisband a team and clean up its resources.read

Each brief you write for spawn_agent or a team_create member must be self-contained: the agent sees none of the parent conversation, so restate the objective, scope, constraints, and expected output. A spawned agent inherits the session-selected model rather than an agent-type default.

Three spawn_agent options deserve detail. agent_definition defines a new type inline (name, description, system prompt, optional tool whitelist) when no registered type fits; it goes through the same write-tool safety filtering as any other type, and when neither tools nor read_only is given it defaults to a read-only tool pool, since nobody reviews the definition before it runs. A good ephemeral type can then be kept with promote_agent_type. detach: true returns a task_id immediately instead of blocking the turn (poll with task_status/task_output); detached agents run read-only unless isolated. isolation: 'worktree' gives the agent its own git worktree so parallel agents can write without colliding; when it completes, clean changes are applied uncommitted back to the originating branch's working tree and the worktree is removed (server/git/worktree_harvest.py), while a conflicted or failed run keeps the worktree and says where it is.

MCP servers themselves come in two transports (server/mcp.py): local servers spawned as stdio child processes, and remote HTTP servers reached over streamable HTTP (a url plus an optional bearer token read from an environment variable named by bearer_token_env_var, never stored raw in config). Each server also carries its own trust settings: a per-server approval_mode, where "approve" is a hard approval floor that no bypass mode, trusted skill, or session approval can skip, and per-server enabled_tools / disabled_tools allow/deny lists (disabled_tools wins on overlap). When an MCP server asks the human for input mid-call (an elicitation), the question is surfaced through the approval pipeline (category mcp-elicit) rather than answered silently. See the per-server MCP fields.

Built-in core tools

These ship as native tools, schemas in code next to their executors (server/executors/tools.py and server/prompt_tools/), always in the pool, and never listed or editable in the Skills panel:

  • Command, code, and cloud execution - terminal_run, run_python, aws_cli, and aws_boto3. These run commands, Python, or AWS calls; the mutating ones pause for approval like the other command tools.
  • Web - web_search and web_fetch, listed in the Web section above. Read-only.
  • Content - analyze_document (attached files) and summarize_transcript (the live session transcript).
  • Prompt tools - verify_change, create_program, and github_actions. Their result is an instruction script the model then carries out with the other tools (e.g. verify_change ends in a deterministic VERIFY PASS/VERIFY FAIL line).

Skill-backed tools

Beyond skill_invoke, every skill installed under skills/ is also advertised to the model as its own top-level tool, named after the skill (dashes become underscores), described by its own frontmatter. The model picks a skill the same way it picks any tool, from that description and the skill's triggers; nothing in the app hardcodes when a skill should be used. See Skills for the bundled examples and how to add your own.

Because this set is driven by the installed skills rather than hardcoded, the exact list depends on what is in skills/. Adding or removing a skill adds or removes its tool, so the pool grows with your skill folder.
