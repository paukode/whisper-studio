Frontend architecture

The whole UI is one React 19 single-page app served from the same local origin as the API. It is built around one idea: each chat session is a self-contained runtime that keeps streaming, recording, and saving whether or not you are looking at it.

Where the chat pipeline is the backend state machine, this page is its client. Three pieces carry most of the weight: AppShell.tsx (layout plus startup), the session runtime registry in src/stores/sessionRuntimes.ts, and the useChatStream hook that consumes Server-Sent Events. Click a box in the map to trace where data flows.

The shell and the startup sequence

src/components/layout/AppShell.tsx is the top-level component. It renders the five-region layout (sidebar, chat, an optional transcript pane, the workspace IDE, and a right-side dock) and it owns the one-time boot sequence. There is no separate layout engine: every visible split is a ratio-flex Splitter, so no pane is ever pinned to a pixel width and surviving panes redistribute through flexbox when you open or close one.

The layout is always fully mounted, even when a pane is hidden. Rendering Splitter conditionally around the workspace panel would put the chat pane's subtree at two different structural positions, so React unmounts and remounts it, and every component inside it, on each workspace connect or disconnect - silently wiping local component state such as an in-progress composer draft. So both children are always rendered and the hidden one is collapsed visually and interactively through a hideFirstPane or hideSecondPane flag instead of being removed from the tree (Splitter.test.tsx pins the regression).

The shell also mounts a persistent bottom status strip, src/components/layout/AppStatusBar.tsx (WS-H), that reads only from existing stores to show the active model, effort, permission mode, git branch with dirty and ahead/behind counts, a live context-window meter, per-turn tokens and cost, and a running background-task pill. The Header carries its own running-count pill that opens the BackgroundTasksPanel.

On mount, the shell fires the startup fetches in parallel:

  • Load config and models. loadConfig() reads the merged runtime config; loadModels() fetches the model list only. On-device weights are deliberately not eager-loaded at startup, so launch stays fast and memory stays free until you actually pick a local model. See Model backends & modes.
  • Load data retention and skills, and open the event channel. loadDataRetention() and loadSkills() populate the settings store, which is also where the skill catalogue behind the composer's autocomplete lives. openEventChannel() opens the app-wide /api/sessions/events stream; each time it opens it loads the MCP server list into mcpStore, its mcp_changed frames keep that list live, and its workspace_changed frames (the backend's watcher on the connected folder, server/workspace/watcher.py) become the whisper-workspace-refresh event that re-lists the loaded folders they name and re-reads the open tabs they name.
  • Restore sessions. loadSessions() lists saved sessions, then the persisted currentSessionId is restored and rehydrated through switchSession(). A stale persisted id is dropped so the next session prompt starts fresh. This is what survives the reload-mid-chat case (a Vite HMR cascade that forces a full reload).
  • Check workspace status. A GET /api/workspace/status recovers a previously connected repo after a refresh, flipping the UI back to the connected state and reopening the workspace panel.

The dock and the terminal

The right-side dock is a stack of panels rather than a fixed inspector. AppShell owns only its outer width; the panel list lives in src/stores/dockStore.ts and the chrome in src/components/preview/RightDock.tsx. Five kinds of panel can be open: a live preview of a running dev server (titled Live · <name>, or Live preview when a localhost link in the chat routed into it), a plan, a workspace file opened from a citation link, Tasks, and Documentation. Panels stack vertically with their own drag handles, each header carries a colored dot for its kind and a close button, and closing the live panel leaves a Live preview chip in the corner to bring it back.

Below the chat, when a workspace is connected, sits the terminal panel (src/components/terminal/TerminalPanel.tsx). Collapsed it is a bar reading Terminal, with a branch chip and, when the session is pinned into a worktree, a worktree chip. Its buttons are Refit terminal to panel, New Terminal, Branches and worktrees, and Close Panel. It keeps its height however long the conversation gets, because the chat and transcript split above it flexes from a zero basis rather than from its content.

The shell also wires the global keyboard shortcuts (Cmd/Ctrl+, for Settings, Cmd/Ctrl+B to toggle the sidebar, Cmd/Ctrl+K for the command palette) and the ESC kill switch, which is armed only while a stream is running or subagents are alive so Esc keeps its normal meaning everywhere else.

Per-session runtimes

The registry in src/stores/sessionRuntimes.ts is the heart of parallel sessions. Every live session owns a RuntimeEntry: its own chat store, its own transcription store, its own long-lived cron/notification EventSource, an in-flight chat AbortController, and self-saving subscriptions.

The design rule is simple: nothing is cleared on a switch. The UI binds to the active session's stores and re-points on switch; background sessions keep streaming, keep receiving cron events, and keep saving themselves. This is why you can start a long answer in one session, switch to another, and come back to find the first one finished.

Two different caps, both set to 3, do two different jobs. MAX_LIVE_RUNTIMES (in sessionRuntimes.ts) is how many runtimes stay resident in memory. MAX_ACTIVE_SESSIONS (in useChatStream.ts) is the user-facing ceiling on how many sessions may be busy (streaming, mid-approval, or recording) at once.

Eviction is LRU over idle, hydrated sessions. maybeEvictIdle() flushes a save first, then drops the least-recently-used runtime and closes its channels. isEvictable() guarantees it never evicts the current session, the recording owner, a streaming session, one that is mid-approval, or one still hydrating. Because busy sessions are never evicted, the cap is soft: the registry may briefly exceed three until one goes idle.

Access is through a small set of getters and hooks:

getChatStore(sessionId)
The imperative getter stream code uses. Bind it once at send time so the stream keeps writing to its owning session regardless of switches.
useActiveChatStore(selector)
The reactive hook UI components use. Built on useSyncExternalStore, so a session switch swaps subscription and snapshot in a single commit.
countActiveSessions(excluding?)
Counts busy sessions for the parallelism ceiling; viewing idle sessions is never counted.
dropRuntime(sessionId)
Teardown: aborts the in-flight stream, closes the EventSource, and unsubscribes.

Each runtime also carries its own cron EventSource to /api/sessions/{id}/events, so a background session still receives its cron events and raises an unread badge on its sidebar row. Stale streams (after a laptop wake or a network restore) are recycled on online and tab refocus so leaked connection slots do not starve new /api/chat requests.

Chat streaming

The useChatStream hook in src/hooks/useChatStream.ts owns the send path. Its central contract is bind once, never let go:

  1. Resolve the owning session

    send() reads currentSessionId once (creating a session if there is none), then does every store access through getChatStore(activeSessionId). A mid-stream session switch changes nothing about where this stream writes.

  2. Check the parallelism ceiling

    Activating a session beyond MAX_ACTIVE_SESSIONS gets a toast, not a queue. Re-sends and approval continuations in an already-active session always pass. Any in-flight stream for this session is aborted first.

  3. Build the request body

    The user message is appended, history is capped to 40 entries, and UI-only rows (role='cron_event') are filtered out before the wire. The body carries the question, transcript, model, effort level, verbosity, session id, attachment ids, and the selected search indexes.

  4. POST and consume

    A fetch('/api/chat') streams the response into readSSEStream. A 409 means the server refused the turn; the hook surfaces the server's guidance as a toast instead of stacking two streams.

  5. Commit atomically

    On stream end, streaming state is cleared and the final assistant message (text, tool traces, team reports, usage, any artifact or plan) is added in a single store update, so there is never a frame with neither the streaming bubble nor the final message.

Sending into a running turn

While the session is streaming, the composer's Send does not open a second stream. It calls sendMidTurn, which POSTs a minimal {question, session_id, midturn: true} to the same /api/chat and waits for a JSON answer. The composer only clears on a confirmed success, so the text is never lost: a success says the message was added to the running turn and will be taken into account as it continues, and a failure (the turn ended in the gap) says plainly that nothing was sent and offers to send it again as a new message. The queueing and fold-in happen server side; see Sending while it works.

Routing SSE events

src/hooks/chatStream/sseStream.ts holds readSSEStream, the parser. It reads the response body, splits on newlines, strips the data: prefix, and validates each payload against a Zod schema (SSEEventDataSchema, src/types/schemas/chat.schema.ts) before dispatching it to the owning session's store. Validation failure logs loudly but still passes the raw payload through, because some event types are intentionally loose. Lines that do not start with data: are skipped, which is how the server's keepalive comment frames are ignored. The last 200 events are kept on window.__lastSSE for DevTools.

A whole new frame survives; a new field inside a known frame does not. SSEEventDataSchema ends in .passthrough(), so a frame the client has never heard of reaches the reducer untouched. Every nested object in that schema is a plain z.object, which silently drops keys it does not declare. That asymmetry has already cost real behaviour once: workflow_preview.model_id was stripped, so every approved workflow ran, and was billed, on the config default instead of the session's model. Two tests in src/types/schemas/schemas.test.ts pin it now. The rule to work by: adding a field to an existing frame means adding it to chat.schema.ts and to src/types/chat.ts, or the UI never sees it. The server half of the same contract is tests/golden_fixtures/, which pins the exact frames six representative turns emit.

WorkspacePromptCard is workspace-connect only. It exists for exactly one situation: a workspace-write tool paused because no workspace is connected, or the target path falls outside the connected one. Picking a suggested or recent folder, or browsing for one, POSTs /api/workspace/connect and then resumes the model with an explicit instruction to re-issue the original write. A one-off "save this file somewhere" request never reaches this card at all: the file-saving tools resolve their own destination from the user's words (or a Documents default) and go straight to a normal approval card - see Results back to the loop for that staged-then-move flow. No card ever asks you where to save a file.

Frames that never touch the chat stream

Anything that can happen while a session is not streaming cannot ride the chat POST response. Those frames arrive instead on the per-session EventSource opened in src/stores/sessionRuntimes.ts (/api/sessions/{id}/events), so they reach a session you are not looking at: cron_event, task_event (the header's task list, global across sessions), agent_progress (the dock's agent pane), memory_event, session_message, team_progress, ci_progress, ci_result, and the two agent-report frames below. A frame that does not parse as JSON is dropped, which is how the channel's own heartbeats are ignored.

EventEffect
agent_reportAgent work finished with no live turn to carry it (you pressed Stop, the app restarted, a detached or resumed agent ended). The reports are appended as an AgentReportCard row so the work is not lost twice.
agent_answerThe answer a one-round wake turn wrote from those reports, appended as an assistant bubble labelled "Answered from the agents' reports".

Both are stored as real session rows (role: 'agent_report' and role: 'agent_answer'), so they survive a reload and are translated for the model's context on the next turn. See the agent flight recorder.

An approval is not a dead end, and there are two entry points onto the same resume channel. A full approval card's accept/deny buttons call sendApprovalContinuation, which POSTs a single approved_tool_result object (tool_use_id, content, accepted) back to /api/chat and feeds the continuation response straight back into readSSEStream; the two functions are mutually recursive, which is why they share one module. UserQuestionCard and WorkspacePromptCard instead dispatch a whisper-submit-answer DOM event carrying an answers array of tool_use_id / content pairs, which useComposerChatEvents routes into chatStream.send('', { approvedToolResult: answers }) - the same request-body field, just array-shaped, so either path reaches server/chat/routes.py's approved_tool_result branch and restores the same stashed paused-turn state. A bare answer string sent any other way is treated as a brand-new chat message and never resumes anything. The ESC kill switch stops the viewed session's stream and every running subagent synchronously, and a wasKillFinalized guard stops the read loop from resurrecting an answer after a kill.

A readable transcript

A long agentic turn can produce dozens of tool calls. Rendered one bubble per step, the answer disappears into the machinery, so three rules shape what you actually see.

Tool steps collapse into one activity row
groupForActivity puts a sequence of tool calls into one ActivityRow (src/components/chat/ActivityRow.tsx). Each model round gets its own row. A new row starts when the round of the next call is different from the round of the row. The server counts the rounds of each request from 0. A request that continues a turn after an approval or an answer also starts at 0. Thus the browser adds a base to each round of a request. The base is 1 more than the highest round of the turn, or 0 if no call in the turn has a round (nextRoundBase in src/hooks/chatStream/sseStream.ts). A call without a round does not start a new row. Examples are a refusal card, which stays with the call that it blocked, and a row from an older transcript. A card comes after the call that it blocked. Thus, when a row holds only cards, the next call with a round starts a new row. The collapsed row is one line with a label that shows what the group did, for example Read 3 files or ruff check failed. A monospace tail shows the file names or the command, and chips show the diff, line, match, and exit counts. An expanded row shows one line for each call with a file link, a diff pill, and an output toggle. The diff pill opens the diff dialog of the Git panel (src/components/git/DiffDialog.tsx) through src/components/chat/EditDiffViewer.tsx. The dialog shows the file before and after that call, from GET /api/workspace/edits/{tool_use_id}. The header of the dialog shows the full path of the file. Expand all shows each output, and a row with an error is open at the start. Because the streaming view and the saved transcript use the same constant, ACTIVITY_MIN_RUN, the row does not move when the turn ends. When the auxiliary model returns a caption for the group (the activity_label frame), the caption replaces the label and the sentence becomes the tail. If the group failed, the failure stays the label, for example ruff check failed, and the caption becomes the tail. In Local mode, in a chat that uses an on-device model, or when the caption call fails, the row keeps the sentence.
One bubble for each assistant turn
Text that the model writes before a tool call is a complete thought, so the stream commits it as a row of its own. The store keeps these rows separate, because their indices control edit, delete, regenerate, the task checkpoints, and the deliveries. src/components/chat/turnEntries.ts puts each run of consecutive assistant rows into one turn, and TurnBubble (src/components/chat/TurnBubble.tsx) shows the turn in one bubble. Each row shows as a TurnSegment. When a row has no text after its tool calls, the rows of only tool calls that come directly after it show in the same segment (traceRuns), and the tool calls of these rows show as one list. Thus a call and the refusal card that comes after it show as one group. Then the "Verified" chips, the timestamp, and the actions show one time. A workflow or CI card stays in the turn when the row before it has the model call that made the card (workflow_run, ci_watch, or ci_autofix). A card that a slash command or the Autofix button adds starts a new turn. While the turn streams, the live reply shows at the end of the same bubble.
Agent work gets a row, not a transcript
Consecutive agent-orchestration calls become an AgentCard, or one agent row each (AgentRows.tsx) when matching team results arrived: name, state, and Open. Open puts the agent in the dock's agent pane (AgentPanel.tsx), which reads the run's record once (GET /api/agents/{id}/record) and follows it live through agent_progress frames merged by the journal's seq. The pane's status line reads state, model, rounds against the cap, time and estimated cost, and while an agent is running Extend +20 grants it more rounds (POST /api/agents/{id}/extend) without losing its loaded context. The first row of the feed is the task. For a workflow agent, the row shows the part of the task that is different from the other agents of the run. The text that is the same for these agents is in a closed "shared brief" section above it. The section title gives the length of the text and the number of the other agents. If the part of the agent is longer than 4,000 characters, the row shows maximum 4,000 characters. The text that follows is in a second closed section. See the agent flight recorder.

src/components/chat/ChatMessage.tsx shows the user bubble and four card roles that do not use the normal bubble: cron_event, session_message, agent_report, and agent_answer (an assistant bubble labelled "Answered from the agents' reports", with the team name appended when there is one).

Rendering safety

All Markdown passes through src/utils/sanitizeHtml.ts before it reaches the DOM. renderMarkdownSafe is the single path that produces HTML for React's raw-HTML escape hatch: markdown -> marked.parse -> DOMPurify.sanitize. DOMPurify runs with USE_PROFILES: { html: true }, which permits standard elements but strips <script>, on* handlers, and javascript: URLs.

This matters because a web_fetch can pull a prompt-injected page into the model's context. Without sanitization, a payload like <img onerror> would run inside the SPA's same-origin context. A separate sanitizeHtml helper covers already-HTML content that never went through marked, such as a .docx converted for the document viewer. See the security model.

Chat links: citations, created files, path mentions, and localhost

A rendered message can contain four kinds of link the app intercepts instead of letting the browser handle them, all wired through one delegated click handler, attachWsFileHandlers in src/utils/wsFileLinks.ts (delegated so it survives the streaming innerHTML swaps that would otherwise detach a per-anchor listener):

  • Citation links from index/semantic search use a #wsfile=<url-encoded path>&L=<start>-<end> fragment (chosen because a fragment survives HTML sanitization). A plain click opens the file in the dock at those lines, deduping by path; a modifier-click (Cmd/Ctrl/Alt) reveals it in Finder/Explorer via POST /api/workspace/reveal instead.
  • Created-file links mark a file the assistant just wrote rather than an existing one it is citing: created_file_link() in server/index/citations.py (emitted from the save/approval paths in server/approval/bootstrap.py) produces the same scheme with &open=os instead of an &L= range. A plain click opens it with the OS default app - there is no in-app dock view to fall back to for a brand-new file - while a modifier-click still reveals it, for consistency with every other #wsfile= link.
  • Path mentions are workspace paths that the assistant writes as plain text, for example server/goals/gate.py:40-44. Before marked parses the text, linkifyPaths in src/utils/pathLinks.ts changes each mention to a citation link with the same #wsfile= fragment. A :line or :start-end suffix gives the &L= range. The function does not change code (fences, code spans, and the pre, code, kbd and samp elements), links, or web addresses. When no workspace is connected, the function does not change the text. The file preview and the notebook viewer set linkPaths={false} on MarkdownRenderer, because a relative path in a file can start at the folder of that file, not at the workspace root.
  • Localhost links (http://localhost:* / 127.0.0.1 / [::1], any port) route into the Live preview pane instead of opening a browser tab, since the assistant only ever names one when it started or is talking about a dev server it spun up itself. A modifier-click is the escape hatch back to a real tab.

The rest of the glue

  • Providers. The app is wrapped with TanStack Query (for cached, non-streaming server reads) and a theme provider that mirrors the light/dark toggle you see in these docs.
  • Validated API client. The client in src/api/client.ts validates responses with Zod schemas, so a shape drift shows up as a clear error rather than a silent undefined deep in a component.
  • Reference-counted recording. The chat-input mic and the meeting recorder share a single MediaStream through the recording controller, so two features can hold the microphone without fighting over the device. See Transcription & diarization.
  • Bulk session selection. The sidebar's select-all checkbox (src/components/layout/Sidebar.tsx) drives a multi-select mode with an indeterminate state for a partial selection, feeding the bulk export/import/delete flows.
  • Collapsible descriptions. src/components/settings/ExpandableText.tsx clamps a long settings-row description to a couple of lines with a See more / See less toggle, measuring actual overflow so short text never shows a toggle it does not need.
  • The feature-flags panel. src/components/settings/FeatureFlagsPanel.tsx lists every backend feature flag from GET /api/feature-flags with its default and source (config or default), and flips one with PUT /api/feature-flags/{name}; the one exception is auto_memory, which is also mirrored in the toolbar, so it routes through the settings store setter instead of a direct PUT to keep both in sync.
