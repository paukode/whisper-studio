The goal loop & completion gate

Give the assistant a goal and it keeps working until the goal is met. An end-of-turn completion gate checks whether the work is actually done, with hooks, deterministic checks and a cheap evaluator, and, if not, feeds back what's missing and lets the turn continue, capped so it can never loop forever.

The loop lives in server/goals/: store.py (the goal and its quality gates on the session), deliverables.py (did the files it claimed actually get written), verification.py (did anything green run after the last code edit), gates.py (the must-pass shell commands), tail.py (the transcript the evaluator reads), evaluator.py (the verdict), gate.py (the gate that ties it together), cron_verify.py (the same idea for cron), and routes.py (the goal REST endpoints, under /api/sessions). Why a gate

Left alone, a model tends to stop as soon as it has produced something, often before the task actually holds up. The completion gate turns "the model emitted end_turn" from an unconditional stop into a decision: did any Stop hook object, do the deliverables the reply claims actually exist, did anything green run after the last code edit, do the goal's own gate commands pass, and is the stated goal met? If the answer is no, the turn is not over: the gate re-injects what's missing and the model keeps going. Only the goal half is opt-in (you set a goal); the deliverable and verification checks run on every turn. Every check fails open on an error, and one shared cap means a stubborn evaluator or an always-blocking hook cannot trap you.

run_completion_gate: the order of checks

The engine calls run_completion_gate(ctx) at end of turn and acts on the returned GateDecision, but only on the interactive cloud-chat policy: that is the one policy whose TurnPolicy.completion_gate is on. Every unattended consumer runs with the gate off entirely: sub-agents (so a child can never trip the parent turn's evaluator), cron, headless turns, and local chat. Cron instead verifies its own runs with a separate step (see Verified cron below). Where the gate does run, the checks are deliberately ordered cheapest and most deterministic first, so a model call only happens when nothing definite has already settled the question. The first block wins and returns immediately.

  1. Stop hooks (always)

    check_stop_hooks() from the hooks engine runs regardless of the goal flag. A block re-injects the hook's reason and the turn continues. The goal_loop flag gates only the evaluator phase, so turning goals off never disables your Stop hooks.

  2. Claimed deliverables (always)

    Behind the deliverable_check flag, and with or without a goal. If the turn's last reply tells you a file was saved, or points at an artifact card, the gate checks that the file exists and is non-empty, and that a create_artifact or edit_artifact call actually happened in this turn. A miss names the missing items and tells the model to produce them or correct the reply, never to report a deliverable it has not verified.

  3. Verification evidence (always)

    Behind the verify_on_stop flag. Purely deterministic, no model call: if the turn edited code but no test, lint, typecheck or build ran green after the last edit, the gate asks for the run, or for an honest statement of what blocks it. A green suite followed by another edit is stale evidence and does not count. Bounded to two nudges per turn on top of the shared cap.

  4. The goal's quality gates (when a goal is active)

    Any commands added with /goal gate add run at this point, on a worker thread, in the workspace. A red gate is deterministic proof the goal is not met, so its exit code and output tail become the continuation feedback and the evaluator is not consulted at all. See Quality gates below.

  5. The goal evaluator (last)

    When goal_loop is on, a goal is set and active, and every gate above is green, a cheap non-streaming call judges the turn: {achieved | not_achieved | blocked, feedback, confidence}. achieved ends the turn and deactivates the goal; not_achieved re-injects the feedback and loops; a confident blocked (confidence at or above 0.7) ends the turn rather than looping on something the model genuinely cannot do.

Every phase fails open: a checker that raises is logged and skipped, and the evaluator is wrapped so a transport error or a malformed reply lets the turn end normally rather than trapping it. The whole thing is bounded by one shared consecutive-block cap (goal_max_consecutive_blocks, default 8). At the cap every phase gives up and emits a goal_cap_reached frame naming which check was asking, and the turn is allowed to end. The counter resets at the start of each new user turn, so the cap counts blocks within one continuous stretch of work, not across a conversation.

Three of these checks run whether or not a goal is set, and all of them surface in the UI through the same stop_hook_block frame, which the transcript labels Continuing (Stop hook). So a turn that keeps going with no Stop hook configured at all is normal: the decision's source field (stop_hook, deliverable, verify, gate or evaluator) is what says which check spoke.

Quality gates

A gate is a shell command that must exit 0 before the goal can be judged done. The evaluator reads prose; a gate is stronger, and it is the one part of the loop you control directly. Gates are stored on the session's goal state, managed with /goal gate add <command>, /goal gate list, /goal gate remove <N> and /goal gate clear, and served by GET / POST / DELETE /api/sessions/{session_id}/goal/gates.

  • Each gate runs in the workspace with a 300 second timeout; a timeout counts as a failure with no exit code.
  • On failure the feedback embeds the exit code and the last 3,000 characters of output for the first two failing gates, then names how many more also failed, and ends by saying the gate re-runs at the next turn boundary. So a gate whose input the model just repaired passes next time.
  • Failure counters are per gate: a pass resets one to zero. A gate that fails three times in a row stops looping and pauses the goal instead, with a verdict saying to fix it manually, remove the gate, or set the goal again.

The evaluator and the transcript

The evaluator (server/goals/evaluator.py) is a single non-streaming call, cheap enough to run at the end of every turn. Which model makes it is the goal_evaluator entry in the auxiliary_models config map, Haiku by default, so the judge is deliberately cheaper than the session's own model and can judge a GPT session just as well as a Claude one. It reads the goal plus a rendered tail of the turn from server/goals/tail.py, a provider-neutral renderer that flattens the last 15 messages (Anthropic content blocks, OpenAI Responses items, and top-level function_call / function_call_output items) into text, tool results sliced head and tail, capped at 12,000 characters so a huge turn can't blow the prompt. The verdict JSON is extracted with a balanced-brace scan and one retry; near-miss verdicts are coerced and the confidence clamped. With no model configured, or an output that will not parse, it returns achieved at confidence 0 so the turn ends rather than hanging on a broken judge.

Its instructions are strict by design: it is told to weigh a verify_change result's VERIFY PASS or VERIFY FAIL above any prose, and to be skeptical of "done!" with no supporting tool output.

The evaluator weighs a deterministic signal above prose: the built-in verify_change tool (server/prompt_tools/verify_change.py) runs the repo's real verification gate and ends with exactly VERIFY PASS or VERIFY FAIL: <reason>. That is the same line a generated CI autofix workflow finishes on, proof beats a confident-sounding summary.

Full-stack goals: verifying the UI

For a change that touches rendered UI, that verification is not just tsc-and-tests: the built-in verify_change tool's ui_facing branch drives the live preview: it spins up your dev server, loads the changed view, checks the browser console for errors, drives the changed interaction, and captures a screenshot before emitting its verdict. Because the gate weights that verdict above prose, a goal on full-stack work will not be judged done until the page actually renders and behaves, so Whisper keeps re-driving the preview and screenshotting on its own until the UI holds up, without you asking it to "check the browser". See Verifying the UI in the loop for the full mechanism (and its limits: it needs the preview tools available, and parallel UI checks each spin their own dev server).

Where the goal lives

The goal is stored on the session itself. server/goals/store.py adds two additive columns to the sessions row, goal (the text) and goal_state (JSON: whether the goal is active, the consecutive-block counter, the total evaluation count, the last verdict and feedback, when it was set, and the quality gates with their failure counts). See Persistence.

The store keys on whatever id it is handed, and the engine hands it turn_scope_id when a caller set one. That is what keeps a sub-agent's inner turn (scoped agent:<id>) or a cron run (cron:<job>) from resetting the parent session's in-flight goal tracking while it runs. A goal set on a brand-new session that has not been written yet inserts a placeholder row rather than being silently dropped.

Verified cron

The same idea guards scheduled work. server/goals/cron_verify.py lets a cron run verify it actually achieved its prompt before reporting ok: it folds any notify_user bodies in as a synthetic assistant message, runs the evaluator, and continues the run (up to two continuations) if the goal is unmet. A run that never meets its goal is marked failed and its report is prefixed [UNVERIFIED]. Gated by the cron_verify flag. This is also the only way goals reach an unattended run: the completion gate itself is off for cron (and for sub-agents and headless turns), so cron_verify is not a variant of the gate, it is the substitute for it.

Setting a goal

/goal <text> does two things at once: it arms the gate with that text as the goal, and it sends the same text as the first message. Arming the gate alone left the composer empty with nothing running, which read as a swallowed message. If a turn is already streaming, the text is folded into it as a mid-turn message instead of starting a second one. /goal clear ends the goal. The active goal shows in a GoalBanner above the composer (hydrated from the session on load) with a verdict chip reading achieved, working… or blocked, an attempts counter, and a clear button. The gate's decisions surface as goal_eval, goal_cap_reached and stop_hook_block frames, which the transcript renders as Goal check, Goal check paused (cap reached) and Continuing (Stop hook) rows.

The REST surface is small, all under /api/sessions/{session_id}: GET / POST / DELETE /goal for the goal itself, and GET / POST /goal/gates plus DELETE /goal/gates/{index} (1-based) and DELETE /goal/gates for the quality gates.
