The goal loop & completion gate

Give the assistant a goal and it keeps working until the goal is met. An end-of-turn completion gate checks whether the work is actually done, with hooks, deterministic checks and a cheap evaluator, and, if not, feeds back what's missing and lets the turn continue, capped so it can never loop forever.

The loop lives in server/goals/: store.py (the goal and its quality gates on the session), deliverables.py (did the files it claimed actually get written), verification.py (did anything green run after the last code edit), gates.py (the must-pass shell commands), tail.py (the transcript the evaluator reads), evaluator.py (the verdict), local_judge.py (the verdict for an on-device session, on its own model), gate.py (the gate that ties it together), cron_verify.py (the same idea for cron), and routes.py (the goal REST endpoints, under /api/sessions). Why a gate

Left alone, a model tends to stop as soon as it has produced something, often before the task actually holds up. The completion gate turns "the model emitted end_turn" from an unconditional stop into a decision: did any Stop hook object, do the deliverables the reply claims actually exist, did anything green run after the last code edit, do the goal's own gate commands pass, and is the stated goal met? If the answer is no, the turn is not over: the gate re-injects what's missing and the model keeps going. Only the goal half is opt-in (you set a goal); on cloud chat the deliverable and verification checks run on every turn. A deterministic check that errors is skipped, a judge that cannot run says so instead of passing the goal, and one shared cap means a stubborn evaluator or an always-blocking hook cannot trap you.

run_completion_gate: the order of checks

The engine calls run_completion_gate(ctx) at end of turn and acts on the returned GateDecision, on the two interactive chat policies, whose TurnPolicy.completion_gate is on. Cloud chat runs it at the end of every turn. On-device chat runs it only while the session has an active goal (the local preset sets gate_requires_goal, and the goal_loop flag must be on): every block costs a full local round, so plain on-device chat with no goal still ends the moment the model stops. With a goal set, an on-device turn runs every phase below in the same order, except that the two checks that ask for a file (claimed deliverables and requested file) stay quiet for a model with no tools, which could not act on them. Every unattended consumer runs with the gate off entirely: sub-agents (so a child can never trip the parent turn's evaluator), cron and headless turns. Cron instead verifies its own runs with a separate step (see Verified cron below). Where the gate does run, the checks are deliberately ordered cheapest and most deterministic first, so a model call only happens when nothing definite has already settled the question. The first block wins and returns immediately.

  1. Stop hooks (always)

    check_stop_hooks() from the hooks engine runs regardless of the goal flag. A block re-injects the hook's reason and the turn continues. The goal_loop flag gates only the evaluator phase, so turning goals off never disables your Stop hooks.

  2. Claimed deliverables (always)

    Behind the deliverable_check flag, and with or without a goal. The gate reads every reply of the turn for what it says was made: a path after "saved to" or a word like it, the app's own file link, the rows of a table whose header names a file, path, location, output or saved column, and an artifact card. A file name may hold spaces where the reply marks its ends (backticks, double quotes, a link target, a cell of such a table); a question, an offer, a plan or a negation is not a claim, and neither is a web address. Each file must exist and be non-empty, and a card must have been made, by a create_artifact or edit_artifact call this turn or by an earlier turn of the session (the app keeps a session's cards with its saved history, so a restart does not forget them). In plan mode a path counts only once a tool that writes outside the workspace ran (save_file, run_python, a terminal command or a document tool); until then it is a file the plan will write. A miss names the missing items and tells the model to produce them or correct the reply, never to report a deliverable it has not verified. One nudge per turn.

  3. Requested file (always)

    Behind the requested_file_check flag, and quiet in plan mode. When the user asked for a file and the turn produced none (no file or document tool ran, and no reply names a file it made that exists), the gate asks for it once, or for a plain statement that it will not be made. Each request is checked on its own: one in the prompt against the whole turn, and one in a message sent while the turn ran ("also make a PNG chart") against only what came after that message, so restating the file made for the prompt does not answer it. A file the user called off ("no need to save a file") is not a request.

  4. Verification evidence (always)

    Behind the verify_on_stop flag. Purely deterministic, no model call: if the turn edited code but no test, lint, typecheck or build ran green after the last edit, the gate asks for the run, or for an honest statement of what blocks it. A green suite followed by another edit is stale evidence and does not count. Bounded to two nudges per turn on top of the shared cap.

  5. The goal's quality gates (when a goal is active)

    Any commands added with /goal gate add run at this point, on a worker thread, in the workspace. A red gate is deterministic proof the goal is not met, so its exit code and output tail become the continuation feedback and the evaluator is not consulted at all. See Quality gates below.

  6. The goal evaluator (last)

    When goal_loop is on, a goal is set and active, and every gate above is green, a non-streaming call judges the turn, reading the reply it is judging: {achieved | not_achieved | blocked, feedback, confidence}. achieved ends the turn and deactivates the goal; not_achieved re-injects the feedback and loops; a confident blocked (confidence at or above 0.7) ends the turn rather than looping on something the model genuinely cannot do. While it runs, the transcript shows Checking the goal on <model>....

A deterministic checker that raises is logged and skipped. The judge never fails open: when it cannot run or its answer cannot be understood (a refused cloud call in Local mode, a transport error, a timeout, an empty or cut-off answer, JSON that is still unreadable after one retry, an on-device model that is no longer loaded or a context window too small for the check), the verdict is not_checked with the reason. It ends the turn, keeps the goal active, is not counted as a block, and is never recorded as achieved; the goal is checked again when the next turn ends. A turn that ends on its last round (the round cap, the cost or time budget, or the salvage round after a context overflow) skips the gate, because a block would need a round the turn does not have, and an active goal is reported as not_checked with that reason too. The whole thing is bounded by one shared consecutive-block cap (goal_max_consecutive_blocks, default 8). When the cap is hit the engine calls the gate once more, every phase gives up and emits a goal_cap_reached frame naming which check was asking, and the turn is allowed to end. The counter resets at the start of each new user turn, so the cap counts blocks within one continuous stretch of work, not across a conversation.

Four of these checks run whether or not a goal is set, and all of them surface in the UI through the same stop_hook_block frame, which the transcript labels Continuing (Stop hook). So a turn that keeps going with no Stop hook configured at all is normal: the decision's source field (stop_hook, deliverable, requested_file, verify, gate or evaluator) is what says which check spoke.

Quality gates

A gate is a shell command that must exit 0 before the goal can be judged done. The evaluator reads prose; a gate is stronger, and it is the one part of the loop you control directly. Gates are stored on the session's goal state, managed with /goal gate add <command>, /goal gate list, /goal gate remove <N> and /goal gate clear, and served by GET / POST / DELETE /api/sessions/{session_id}/goal/gates.

  • Each gate runs in the workspace with a 300 second timeout; a timeout counts as a failure with no exit code.
  • On failure the feedback embeds the exit code and the last 3,000 characters of output for the first two failing gates, then names how many more also failed, and ends by saying the gate re-runs at the next turn boundary. So a gate whose input the model just repaired passes next time.
  • Failure counters are per gate: a pass resets one to zero. A gate that fails three times in a row stops looping and pauses the goal instead, with a verdict saying to fix it manually, remove the gate, or set the goal again.

The evaluator and the transcript

The evaluator (server/goals/evaluator.py) is a single non-streaming call, cheap enough to run at the end of every turn. Which model makes it depends on the session:

  • A cloud-model session is judged by the goal_evaluator entry in the auxiliary_models config map, Haiku by default, so the judge is deliberately cheaper than the session's own model and can judge a GPT session just as well as a Claude one. "main" means the session's own model.
  • An on-device session is judged by its own resident model (server/goals/local_judge.py), in Local and Hybrid mode alike, so nothing about its goal is sent to Bedrock. goal_evaluator does not apply to it (the server logs once when it is set). The call goes through a resident-only request that never loads, displaces or waits on a model, and takes its own busy mark so the server cannot be stopped under it. Its 300 second timeout bounds the answer: the server answers one request at a time, so while another chat or agent uses the same model the check may queue behind that round first, and that wait is allowed for on top (the status line says so, and so does a timeout's reason). On llama-server the answer is constrained to the verdict's JSON schema; on both engines it runs at temperature 0 with thinking off, and the same strict parser applies. The verdict the user sees is prefixed Judged by <model> on this Mac:, because the model is judging its own work.

The judge reads the goal plus a rendered tail of the turn, the final reply included, from server/goals/tail.py, a provider-neutral renderer that flattens the last 15 messages (Anthropic content blocks, OpenAI Responses items, and top-level function_call / function_call_output items) into text, tool results sliced head and tail, capped at 12,000 characters so a huge turn can't blow the prompt. On-device, the cap shrinks to fit the resident context window, and a window too small for the check is refused before anything is sent. The verdict JSON is extracted with a balanced-brace scan and must name a known verdict and a numeric confidence (clamped to 0..1); an unreadable answer gets one retry, then the verdict is not_checked.

On an on-device model, add a quality gate with /goal gate add <test command>. A small model judging its own work is a weaker signal than a test that has to pass, and a red gate settles the question before the judge is asked.

Its instructions are strict by design: it is told to weigh a verify_change result's VERIFY PASS or VERIFY FAIL above any prose, and to be skeptical of "done!" with no supporting tool output.

The evaluator weighs a deterministic signal above prose: the built-in verify_change tool (server/prompt_tools/verify_change.py) runs the repo's real verification gate and ends with exactly VERIFY PASS or VERIFY FAIL: <reason>. That is the same line a generated CI autofix workflow finishes on, proof beats a confident-sounding summary.

Full-stack goals: verifying the UI

For a change that touches rendered UI, that verification is not just tsc-and-tests: the built-in verify_change tool's ui_facing branch drives the live preview: it spins up your dev server, loads the changed view, checks the browser console for errors, drives the changed interaction, and captures a screenshot before emitting its verdict. Because the gate weights that verdict above prose, a goal on full-stack work will not be judged done until the page actually renders and behaves, so Whisper keeps re-driving the preview and screenshotting on its own until the UI holds up, without you asking it to "check the browser". See Verifying the UI in the loop for the full mechanism (and its limits: it needs the preview tools available, and parallel UI checks each spin their own dev server).

Where the goal lives

The goal is stored on the session itself. server/goals/store.py adds two additive columns to the sessions row, goal (the text) and goal_state (JSON: whether the goal is active, the consecutive-block counter, the total evaluation count, the last verdict and feedback, when it was set, and the quality gates with their failure counts). See Persistence.

The store keys on whatever id it is handed, and the engine hands it turn_scope_id when a caller set one. That is what keeps a sub-agent's inner turn (scoped agent:<id>) or a cron run (cron:<job>) from resetting the parent session's in-flight goal tracking while it runs. A goal set on a brand-new session that has not been written yet inserts a placeholder row rather than being silently dropped.

Verified cron

The same idea guards scheduled work. server/goals/cron_verify.py lets a cron run verify it actually achieved its prompt before reporting ok: it reads the run's history with the reply the run finished on (the engine's own history stops before that reply), folds any notify_user bodies in as a synthetic assistant message, runs the evaluator, and continues the run (up to two continuations, each with its last reply in view) if the goal is unmet. A run that never meets its goal is marked failed and its report is prefixed [UNVERIFIED]. A verifier that cannot judge the run spends no continuation: the run is marked the same way, with [UNVERIFIED] Not checked: and the reason, and never passes silently. Gated by the cron_verify flag. This is also the only way goals reach an unattended run: the completion gate itself is off for cron (and for sub-agents and headless turns), so cron_verify is not a variant of the gate, it is the substitute for it.

Setting a goal

/goal <text> does two things at once: it arms the gate with that text as the goal, and it sends the same text as the first message. Arming the gate alone left the composer empty with nothing running, which read as a swallowed message. If a turn is already streaming, the text is folded into it as a mid-turn message instead of starting a second one. /goal clear ends the goal. The active goal shows in a GoalBanner above the composer (hydrated from the session on load) with a verdict chip reading achieved, working…, blocked or, in a neutral colour with the reason on hover, not checked, an attempts counter, and a clear button. The gate's decisions surface as goal_eval, goal_cap_reached and stop_hook_block frames, which the transcript renders as Goal check, Goal check paused (cap reached) and Continuing (Stop hook) rows. A Goal check row reading not checked is neutral, not an error, and opens on its reason; the full feedback is behind the row's expand button.

The REST surface is small, all under /api/sessions/{session_id}: GET / POST / DELETE /goal for the goal itself, and GET / POST /goal/gates plus DELETE /goal/gates/{index} (1-based) and DELETE /goal/gates for the quality gates.
