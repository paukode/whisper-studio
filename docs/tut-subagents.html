Sub-agents & teams

Divide a large task among focused agents that run at the same time. You continue to chat. Each agent shows as a row in the chat, and its full feed opens in the agent pane.

Usually, one conversation is sufficient. But some tasks have parts that can run at the same time, for example "search these five folders", "write it, and then let a second agent examine it", or "audit each service". For these tasks, Whisper Studio can run sub-agents. A sub-agent is an independent agent with its own tool loop. It uses your session and its selected model: Claude, OpenAI GPT on Bedrock, or an on-device model that can call tools.

This tutorial shows how to start agents and how to read their progress. It also shows how to get the work of an agent after its turn ended.

Two ways to start agents

/subagent: one focused helper

Type /subagent <task> in the chat box. One agent starts in the background, in its own message. The chat box stays available, and you can continue to chat. The agent writes its result into that message. To stop it, use the tasks pill in the header.

Agents that the assistant starts

Describe the work in usual words. The assistant can call spawn_agent (one agent) or team_create (a team). You do not call these tools. The start of an agent has no approval card. The tool calls of each agent go through your permission mode.

Limits and cost. Maximum 16 agents run at the same time in one session. At this limit, the assistant gets an error and must wait or use fewer agents. The app examines your session cost cap before each agent starts. When the cost is more than the cap, no new agent starts. Agents can start agents, to maximum 5 levels.

Detached agents. Without detach, spawn_agent and team_create report in the same turn. With detach: true, spawn_agent returns a task ID immediately, and the agent runs in the background. A detached agent is read-only by default. With isolation: 'worktree', it can write in its own Git worktree. Maximum 8 detached agents run at the same time in one session.

A detached agent shows in the task list of the header. The next turn after it completes receives its result.

The assistant does not poll a detached agent. It ends the turn or does other work, and the agent's completion wakes the chat. To wait in the same turn, it calls task_wait. Use task_status and task_output to examine it, and task_cancel to stop it. When a worktree agent completes, the app applies its changes to the branch as uncommitted changes, and removes the worktree. Use git status to see the changes. If the agent stopped early, or its files conflict with your changes, the app keeps the worktree and tells you its location. Refer to Branches & worktrees.

The model of an agent. By default, each agent uses the model and the effort of your session. The assistant can select a different model for one agent, for example a cheaper model for a simple task. If the app cannot use that model, the agent uses the session model, and the tool result tells the assistant. On-device models can run agents if the model can call tools. The app refuses a model that cannot call tools, and gives the reason.

Refer to Model modes.

Agents use your current session and workspace. With no open workspace folder, the agents cannot use the file tools (ws_read_file, ws_grep, ws_glob, and the other ws_ tools). The agents then tell you this. Open a folder before a task that uses files. Refer to the workspace IDE.

Agent types

Each agent has a type. The type sets its tools and its instructions. The assistant selects the type when it starts an agent. You can also name a type in a team request. The read-only types can search and read, but they cannot write or run commands. Thus, they are fast and safe to run at the same time.

TypeToolsUse
generalAll toolsAll work: read, edit, run, and commit, under the permission mode of the session.
exploreRead-onlyA fast search to answer a question. Short findings, with no changes.
planRead-onlyExamines the codebase and returns a plan with steps and the files to change.
verifyAll toolsExamines work, reads code, and runs tests. Ends with VERDICT: PASS, FAIL, or PARTIAL.
coordinatorControl of agents onlyControls other agents. It has no file access. It can only start agents, send messages, list agents, and complete the coordination.

All types use the same two limits from "Settings", "Costs", "Budget":

  • A round limit. The default is 120 rounds.
  • A time limit. The default is 15 minutes. The time limit counts only the work of the agent. When the agent waits for agents that it started, the clock stops.

The first limit that the agent gets to stops the run. Your session cost cap can also stop it. In each case, the agent gets one last round to write a report. To give a running agent 20 more rounds, click "Extend +20" in the agent pane.

The app enforces the read-only types. It removes each write tool from the tools of an explore or plan agent. Examples are file writes, ws_run_command, git commits, config_set, and memory writes. If the model calls a removed tool, the app refuses the call. A coordinator has only four tools: spawn_agent, send_message, list_agents, and complete_coordination. Thus, it cannot change your files.

A frequent pattern is explore, then verify. One agent gets the facts. A second agent examines a change and returns PASS or FAIL. Each agent has its own loop. Thus, the verify agent gives an independent result.

Custom agent types

You can define your own types, and the assistant can define a type during a turn:

  • Permanent custom types are Markdown files. The file has YAML frontmatter, and the body is the system prompt of the agent. The app reads the keys name, tools, and read_only. The app also reads model, but the agent does not use it. The limits come from "Settings", "Costs", "Budget".
  • The files are in your user folder or in the project. The user folder is ~/.whisper/agents/<name>.md for the Mac app, and .whisper/agents/ in the checkout for a source install. The project folder is <workspace>/.whisper/agents/<name>.md. If two files have the same name, the project file has priority. A file can replace a built-in type of the same name.
  • Temporary types are in memory only. The assistant gives an agent_definition to spawn_agent in place of a type name. The definition stays only for the session.
  • Promotion makes a temporary type permanent. The promote_agent_type tool validates the definition and writes it as an agent file. By default, the file goes into the project. On request, it goes into your user folder.

Custom and temporary types get the same write-tool filter as the built-in types. A read-only custom type cannot write. If a type is read-only and also lists a write tool, the app removes the write tool.

Agents do not read your project instructions. An agent uses the system prompt of its type. The project WHISPER.md, the rules, and AGENTS.md are in the prompt of the main chat turn only. Put the facts for an agent in its task text or in the custom type file. Refer to the workspace IDE.

Run a team

With team_create, the assistant names the team and lists the members. Each member has a name, a task, and an agent type. All the members run at the same time and use the session model.

  1. Describe the work

    For example: "Look at the auth, billing, and notifications modules in parallel and tell me which ones lack tests." The assistant makes a team with one agent for each module.

  2. Let the team start

    The start of a team has no approval card. The writes and commands of each agent go through your permission mode. A read-only agent cannot get to the write tools.

  3. Read the agent rows

    The chat shows one line for the team, for example "Team · audit · 2/3 done". Below it, there is one row for each agent. The rows change during the run.

  4. Open an agent

    Click "Open" on a row. The agent pane in the dock shows the full feed of that agent.

  5. Read the results

    When all members complete, the assistant tells you what the reports say. The assistant receives the full report of each member. It must tell you the findings, because you did not see the reports.

The agent rows and the agent pane

The chat shows each agent as one line: "Agent", the name of the agent, its state, and an "Open" button. One spawn_agent call is one row. A team has one row for each member, below a line with the team name and the number of members that are done.

The state of a row is one of these texts:

  • starting, running, or done · 5 rounds.
  • failed.
  • stopped at the turn limit, stopped at the time limit, or stopped at the cost cap.
  • stopped after repeated refused calls.
  • stopped, when a person stopped the agent.

"Open" shows the agent in the agent pane of the dock. The tasks pill in the header also has a row for each running agent, and it opens the same pane. The pane has these parts:

  • The status line. It shows the state, the model, the round number and the round limit, the time, and the estimated cost. During the run, it also shows "Extend +20". The state is "running", "finishing up" (the next round is the last round, and the agent writes its report), "done", "failed", or the limit that stopped the run.
  • The feed. The task of the agent, each text that the agent wrote, and each tool call with its result below it. While the agent waits, the feed shows what it waits for.
  • The report. When the run is complete, the pane shows the report of the agent.

"Extend +20" gives a running agent 20 more rounds, while its context is still loaded. This costs less than a new start of the agent. A toast tells you if the extension failed. A completed agent has no "Extend +20" button. Send it a follow-up in place of an extension.

The feed also shows the self-check of each agent. The instructions of each agent type tell the agent to state the task again and work step by step. The agent then examines its result before the final answer. The feed shows this text. Thus, you can see if the agent examined its own work.

How the progress gets to you

Each agent sends typed events to an event bus for each session. Examples are started, turn_start, tool_call, tool_result, completed, and the failure and limit events. The chat endpoint reads the bus and sends the events to the browser as team_progress SSE frames. The app adds them to the message and updates the rows. Thus, the rows are correct during the full run.

Agents run on the same turn engine as the chat. They use the same round limits, last report round, tool safety gate, and deferred tool index with tool_search. Refer to Sub-agents & the event bus.

Agents that send messages to each other

Agents in a session can work together with two tools:

send_message
Sends a message to an agent by its ID. With broadcast: true, it sends the message to all active agents. The agent reads the message between its turns.
list_agents
Lists the active agents of the session with their type, state, and task.

A coordinator agent uses this pattern. It starts workers, sends them messages, and calls complete_coordination at the end. It does not change a file. A message to an agent that is complete starts that agent again. Refer to A follow-up for a completed agent.

Stop a run

During the run, a "Stop" button is in the row of the agent in the tasks pill, and in the header of the agent pane. "Stop" cancels the run. It sends POST /api/background-tasks/{id}/stop. The agent row and the pane then show the stopped state.

Esc and the main "Stop" button of the chat also stop the agents of the current turn. They do not stop an agent from /subagent. Refer to Permissions & approvals.

A stopped agent still gives a report. The app writes the record of each agent to disk during the run. When an agent stops early, the app makes a report from the last text and the tool calls of the agent. The report says that the app made it.

Results after the turn

Sometimes the reports return when no turn runs. For example, you clicked "Stop", you quit and opened the app again, or the agent ran in the background. These results go into the chat automatically:

  • A report card. The card is one closed line, as a line of tool activity. It shows "Report from" and the agent name, the task, and a chip with the stop reason and the number of rounds. Examples of chips are finished · 15 rounds, time limit, cancelled, and failed. A team report starts as one line, for example "Reports from 3 agents", which opens to one line for each agent.
  • A "New" chip. Until you open a report, its icon has the accent color and its line shows a "New" chip. An open line shows the report and an "Open in the agent pane" control. The reason for the card shows at the top of the open card.
  • A notification. The app records a notification at the same time. Thus, the bell in the header tells you of the results, also when you are in a different session.
  • An answer. If a turn runs, the app adds the reports to that turn, as a message that you type during a turn. If no turn runs, the assistant uses one round to read the reports and answer your first question. The answer has the label "Answered from the agents' reports" and the team name.

If the cost of the session is at the cost cap, the app does not write the answer. A notification gives the reason. The reports stay in the chat, and your next message can use them. To stop the automatic answer, set wake_parent_on_reports to false in the settings. The reports then show as cards with no answer.

A follow-up for a completed agent

A completed or stopped agent stays available. Ask the assistant to send the agent a follow-up by its ID, for example "ask the auth agent whether it checked the refresh path". The app starts the run again with its full context: the same agent ID, the same history, and your question as the next message. The follow-up runs in the background, and its answer returns as a report card. A running agent gets the message in its mailbox, and reads it in its next round.

To read the record of an agent, ask for task_output with its ID. For a running agent, it shows the last progress. For a completed agent, it returns the report, also after a restart of the app.

CAUTION: Use small teams. Each agent is a full model run with its own token cost. A team of five agents costs approximately as much as five conversations. Use read-only explore agents when possible, and examine the usage counter. Refer to Cost tracking & budgets.

When to use agents

Good tasks

Independent parts (one for each file, module, or source), a write-then-verify loop, or a large search that you divide among folders.

Do not use agents when

The work is one line of steps, or each step uses the result of the step before. A usual chat turn is simpler, costs less, and is easier to follow.
