Sub-agents & teams

Split a big task across several focused agents that run at the same time. You keep chatting; a live report card shows each agent spawn, its tool calls, and its final answer as they happen.

Most work is fine as a single conversation. But some tasks are naturally parallel: "search these five directories," "draft it, then have another agent verify it," "audit each service." For those, Whisper Studio can run sub-agents - independent worker agents, each with its own tool loop, sharing your session and its selected model (Claude, OpenAI GPT-on-Bedrock, or an on-device model that can call tools). This tutorial covers the two ways to start them, the agent types you can pick, how to read the progress card that streams back, and how to get an agent's work back after the turn that launched it is gone.

Two ways to start agents

There are two entry points, depending on whether you want one helper or several.

/subagent - one focused helper

Type /subagent <task> in the chat input to launch a single one-shot agent. It runs its own tool loop in the background and reports back into the same conversation. Good for a self-contained side task you do not want cluttering the main thread.

Let the assistant spawn them - multi-agent work

Just describe the parallel work in plain language. The assistant decides when to call spawn_agent (one independent agent) or team_create (a whole team at once) rather than doing everything sequentially. You do not call these tools yourself, and starting an agent is not itself approval-gated: each agent's own tool calls are what pass through your permission mode.

How many, and how expensive. At most 16 agents run at once in one session; past that the assistant is told to wait or shrink the team. Your session cost cap is also checked before each agent starts, so once the combined spend has cleared the cap no further agent is launched, rather than each one discovering the problem after paying for its own startup. Agents can spawn agents, bounded at five levels deep.

Detached (background) agents. Both entry points above run inline and report within the same turn. The assistant can instead call spawn_agent with detach: true: it returns a task id right away, runs read-only by default (or writes safely with isolation: 'worktree'), and shows up in the background-tasks panel while it works. Its result is folded into a later turn, and you or the assistant can check on it with task_status / task_output or stop it with task_cancel. When a worktree-isolated agent finishes its work, its changes are automatically applied back to the spawning branch as uncommitted edits (they show up in git status for you to review) and the worktree is removed; an agent stopped early, or one whose files clash with edits you made meanwhile, keeps its worktree and says where it is. See Branches & worktrees.

Which model an agent runs on. By default every agent inherits your session's selected model and effort, so a team is one model working in parallel rather than a mix. The assistant can override it per agent with a model key (for example a cheaper model for a mechanical subtask); a key it gets wrong falls back to your session model and the tool result says so instead of failing quietly. On-device models can run agents as long as the model supports tool calling. A chat-only local model is refused with a plain reason, so pick a tool-capable one before delegating in local mode. See Model modes.

Agents share your current session and workspace. If no workspace folder is open, file tools (ws_read_file, ws_grep, ws_glob, and friends) are not available to the agents, and they will say so. Open a folder first when the task needs to touch files. See the workspace IDE.

Agent types

Every agent has a type that shapes its tools, its turn budget, and its instructions. The assistant picks a type when it spawns an agent (or you can name one in a team brief). The read-only types can search and read but never write or run commands, which makes them fast and safe to parallelize.

TypeToolsTurn limitTime limitBest for
generalFull tool set12015 minDo-anything worker: read, edit, run, commit (subject to the session's permission mode).
exploreRead-only3010 minFast search-and-read to answer a question. Concise findings, no side effects.
planRead-only4010 minStudy the codebase and return a step-by-step implementation plan with files to change.
verifyFull tool set3010 minCheck work by reading and running tests. Ends with VERDICT: PASS, FAIL, or PARTIAL.
coordinatorOrchestration only10030 minManages other agents. No file access at all - it can only spawn, message, list, and finish.

The turn limit is a runaway backstop and the time limit a wall-clock budget; whichever trips first ends the run, and your session cost cap can end it too. Whichever it is, the agent gets a last round to write a report rather than being cut off mid-sentence. Both limits are overridable through an agent_limits block in config.json, per type or under a "default" key (a null deadline disables the time limit for that type).

The read-only guarantee is enforced, not just requested: the runtime strips every write tool (file writes, ws_run_command, git commits, config_set, memory writes, and so on) from an explore or plan agent's tool pool. A coordinator gets an even tighter whitelist of just spawn_agent, send_message, list_agents, and complete_coordination, so it cannot touch your files even by accident.

A classic pattern is explore, then verify: one agent gathers the facts, another checks a change and returns a clear PASS or FAIL. Because each runs its own loop, the verify agent is a genuine second opinion, not the same context re-reading itself.

Custom agent types

The built-in types are not the whole menu. You can define your own presets, and the assistant can invent one on the fly:

  • Persistent custom types are Markdown files: YAML frontmatter followed by the agent's system prompt as the body. The frontmatter keys that are read are name, tools, read_only, model and max_turns. They live in your user directory (~/.whisper/agents/<name>.md) or in the project (<workspace>/.whisper/agents/<name>.md); on a name collision the project file wins, and either can shadow a built-in name. Once the file exists, the type is spawnable by name like any built-in.
  • Ephemeral types are built in memory when the assistant passes an inline agent_definition to spawn_agent instead of a registered type name. Nothing touches disk; the definition lives only for the session.
  • Promotion turns an ephemeral type into a persistent one: the promote_agent_type tool writes the definition out as an agent file, re-validating it on the way, into the project by default or into your user directory when asked.

Custom and ephemeral types pass through the same write-tool filtering as the built-ins, so a read-only custom type is enforced read-only, not merely asked to behave. A type that both declares itself read-only and whitelists a write tool has the write tool stripped.

Agents do not read your project instructions. An agent runs on its type's own system prompt; the repo's WHISPER.md (and the AGENTS.md that is honoured live alongside it) is part of the main chat turn's prompt, not an agent's. Anything an agent must know belongs in its task brief or in the custom type file you spawn it with. See the workspace IDE.

Running a team

When the assistant uses team_create, it names the team and lists the members, each with a name, a task, and an agent type. All members then run in parallel, sharing your session-selected model. Here is what a run looks like end to end.

  1. Describe the parallel work

    For example: "Look at the auth, billing, and notifications modules in parallel and tell me which ones lack tests." The assistant proposes a team with one agent per module.

  2. The team starts

    Starting a team is not itself an approval card. What each agent then does is: its writes and commands go through your permission mode like any other tool call, and a read-only agent type physically cannot reach the write tools at all.

  3. Watch the card fill in

    A team report card appears in the chat immediately (the "scaffold"), then each agent's row updates live as it spawns, calls tools, and finishes. The card header shows a running tally like 2/3 done · 1 running · 14s.

  4. Read the results

    When every member finishes, the card flips to done and the assistant relays what the reports say. It is handed each member's full report, not a fragment, and reminded that you have not seen any of it, so a good answer names the findings and how confident each agent was. Expand any row to see that agent's full event log and final output.

Reading the team report card

The report card (rendered by src/components/chat/TeamReportCard.tsx) is the window into a run. It is one collapsible card per team, with a collapsible row per agent. A plain single spawn_agent renders in the same card as a one-member team, Stop button included, so one helper and a whole team read the same way.

  • Header - team name, agent count, and a live status such as 3/3 done or 1/3 done · 2 running, plus elapsed time. A green check means all completed; a red mark means at least one failed.
  • Agent rows - each shows the agent name, its role badge (team or orchestrator), its type badge (explore, verify, and so on), the model it is running on, a state pill, and a live status like running · turn 3 or done · 5 turns · 2 tools. A running or failed row opens automatically so you see it without clicking. When a run ended at a limit the status says which: stopped at the turn limit · report written, stopped at the time limit · report written, stopped at the cost cap · report written, or cancelled · report salvaged.
  • The state pill - one word for where the run stands: working, finishing up (the next round is its last, so it is writing its report), done, hit limit, salvaged (it was cut off and the runtime assembled the report from its record), or failed.
  • Budget bars - inside an expanded row, one thin bar each for rounds (7/30), time (2m10s/10m) and cost ($0.42). The last tenth of each bar is drawn as a hatched reserved slice: that is the part of the budget held back for the agent to write its report, which is why a run "finishes up" a little before the bar is full. A row with no time limit simply has no time bar.
  • Extend - while an agent is still running, its budget panel has an Extend +20 rounds button. It grants the running agent 20 more rounds while its context is still loaded, which is cheaper and better than letting it stop and picking it up cold. A toast confirms the grant, or explains why it failed. A finished agent has no Extend button; you resume it instead.
  • Expanded row - the agent's task, a real-time event log (each tool call and its result, click a line to expand the full input or output), and the agent's final output once it is done.
  • Child agents - if an agent spawns its own sub-agent, that child appears as its own row badged ↵ child, so a nested tree stays visible in one card.

Nothing in the bars or the pill is guessed by the browser. Each figure is stamped on the agent's own progress events as they arrive, so reopening an old session shows the same numbers it showed live.

The card also surfaces each agent's own self-check. Every user-facing agent type is told to restate the task, work step by step, and run a brief self-assessment before its final answer, which shows up as a text event in the log. So you can see the agent reason about whether it actually finished, not just its conclusion.

How progress reaches you

Under the hood, each agent publishes typed events (started, turn_start, tool_call, tool_result, completed, and failure or turn-limit phases) to a per-session event bus. The chat endpoint drains that bus and relays the events to the browser as team_progress SSE frames, which the SPA folds onto the message to build the card you see. Because it is a live stream, the card is accurate the whole way through, not just at the end. Agents run on the same unified turn engine as chat, with the same round budgets, salvage round, and tool safety gate, and the same progressive tool disclosure: a compact index of deferred tools that an agent loads on demand via tool_search. For the runtime and bus internals, see Sub-agents & the event bus.

Agents that talk to each other

Agents in a session are not isolated. They can coordinate through two tools:

send_message
Message another agent by its ID, or set broadcast: true to reach every active agent at once. Messages are delivered between an agent's turns.
list_agents
List the active agents in the session with their type, status, and current task, so an agent (or you, by asking) can see who is working on what.

This is the pattern a coordinator agent uses: it spawns workers, messages them, and calls complete_coordination when the work is done, without ever touching a file itself. Agents can spawn agents up to five levels deep, so a coordinator can build a small tree without runaway recursion. A message to an agent that has already finished does something different: it resumes that agent (see follow-ups above).

Stopping a run

While any agent is still working, a Stop button sits in the team card header. Click it to cancel the whole team mid-flight: the server cancels the parallel run (POST /api/teams/{team_id}/stop), each running agent flips to a stopped state through the same event stream, and the card reflects it. Pressing Esc and using the main chat Stop control also tears down in-flight agents along with the streaming turn. See Permissions & approvals for the broader kill-switch behavior.

Stopping does not throw the work away. Every agent's record is written to disk as it runs, so a cancelled agent still leaves a report: the runtime assembles one from what it last wrote and what it ran, marked plainly as assembled rather than written by the agent.

When results arrive after the turn

Sometimes the reports come back with nothing listening: you pressed Stop, you closed the app and reopened it, or the agent was running in the background all along. Those results land in the chat on their own.

  • A report card appears in the conversation, titled Agent reports: with the team or agent name, a line saying why it arrived this way, and one collapsible row per agent showing its report and how it ended (finished, stopped at the time limit, report written, cancelled, report salvaged by the runtime, and so on). Each row ends with Full record: task_output <id>.
  • A notification is recorded at the same time, so the bell in the header tells you results are ready even if you are in another session.
  • An answer follows. If a turn happens to be running, the reports are folded straight into it, the same way a message you type mid-turn is. If nothing is running, the assistant takes one round to read the reports and answer your original question. That answer appears as a normal assistant message with a small label reading "Answered from the agents' reports" and the team name, so you can tell it was written without you prompting for it.

The answer is skipped, with a notification explaining why, when your session cost cap is already reached; the reports stay in the chat and your next message can use them. Turn the whole behaviour off with wake_parent_on_reports: false in settings, and reports will still land as cards, just without an answer written for them.

Asking a finished agent a follow-up

An agent that has finished or been stopped is not gone. Ask the assistant to follow up with it by id ("ask the auth agent whether it checked the refresh path") and it picks the run up with its full context intact: the same agent id, the same transcript, your question appended as the next message. The follow-up runs in the background, and its reply comes back as a report card just like the ones above. An agent that is still running gets a plain message in its mailbox instead, which it reads on its next round.

To read an agent's record yourself at any time, ask for task_output with its id. It tails a live agent's progress log and returns a finished one's report, whether it finished an hour ago or before the last restart.

Every extra agent is a full model run with its own token bill. Fan-out is powerful, but a five-agent team is roughly five conversations at once. Keep teams small, prefer read-only explore agents where you can, and watch the usage counter. See Cost tracking & budgets.

When to reach for agents

Good fits

Independent parallel work (per-file, per-module, per-source), a draft-then-verify loop, or a broad search you want split across directories.

Skip it when

The work is a single linear thread, or each step depends on the last. A normal chat turn with the tool loop is simpler, cheaper, and easier to follow.
