Agent flight recorder

An agent's work used to live only in the tool result its parent read once. The flight recorder makes the on-disk record primary: every run is journaled from its first round, every run ends with a report, and a report that arrives with nobody waiting for it still reaches you.

Three things would otherwise lose an agent's work. A tool result lives only as long as the parent's context holds it. An in-memory registry does not survive a restart. A row written on a normal return records nothing when a member is cancelled or crashes. The recorder answers all three by writing the record while the run is alive, and by reserving the run's last round for a report someone can act on.

The journal directory

Each run gets a directory under the app's storage root, keyed by session and agent id:

<storage>/agents/<session_id>/<agent_id>/
    meta.json       task, type, model, budgets, status, stop reason, usage
    events.jsonl    every progress event as it happened
    messages.json   the API message list, rewritten at every round start
    report.md       the final report: the model's own, or a salvage one

A team also gets teams/<team_id>.json in the same session directory: a manifest of which agents made up the team, so a restart can find every member's journal from the team id alone. Storage lives under the app data root, not ~/.whisper, so a hand-edit in the user directory cannot destroy it. See Sessions & persistence.

What is written, and when

MomentWritten
Open, before the first model callmeta.json with the task, agent type, model, turn cap and deadline, plus a started event. The background-task registry row is created here too, pointing at events.jsonl.
Every progress eventOne JSON line appended to events.jsonl: started, turn_start, text, tool_call, tool_result, and the terminal phase. The same events feed the live report card.
Every round startmessages.json is rewritten atomically with the full API message list. This checkpoint is what lets a killed run be resumed later with its context intact.
Finish, however it endsreport.md, and meta.json updated with the terminal status, the stop reason, the round count and token usage. The registry row is closed with the report as its result text.

The terminal write is idempotent: the first one wins. A cancelled run's salvage report can never be overwritten by a later teardown. Every journal write is best-effort by contract, wrapped so it can never take the run down, and a disk that cannot be written to simply means the run has no journal rather than no run.

Because the registry row exists from the first round, task_output <agent_id> tails a live agent's progress log and returns a finished one's report, regardless of how it ended and regardless of whether the turn that launched it is still around.

The report, and the round reserved for it

An agent's last message is its return value, so the runtime makes sure the last message is a report rather than the tail of a narration. The reminder that forces the final round carries a fixed template: findings (most important first), evidence (file, URL, or command output per finding), not checked (what remains open and why), confidence (high, medium or low with a one-line reason), touched (files, artifacts, branches, PRs), and one line the caller can quote. The template ends by telling the agent the caller has seen nothing it wrote before that message.

That final round has to happen inside the budget, not after it. Three limits start it:

  • The turn cap. A wind-down reminder fires with five rounds left ("consolidate, do not open new lines of work"), and on the last round the report template rides along with it. That round is sent with tool choice set to none, so it genuinely produces an answer instead of another tool call.
  • Time. The wall-clock deadline is reached at 90 percent of the budget (SOFT_LIMIT_FRACTION). The last tenth is reserved for writing the report, so the report is written inside the budget rather than after it, where an outer limit could still kill it unsaved.
  • Cost. The session or daily cost cap is checked before every round, first at the hard limit, then at 90 percent of it. The first trip forces one final no-tools round with the report template; the second ends the run. The same soft check governs the main chat turn, so a capped conversation also gets a last round to answer. See Cost tracking & budgets.

Reminders that force the final round are appended to the last user message, not injected per request. A request-only injection would fork the token prefix between rounds and break the moving cache checkpoint, so the wind-down text, the report template, and any mid-turn message all become part of the persisted history.

Stop reasons

Run status stays coarse (completed, failed, stopped) for callers that branch on it. The stop reason names the limit that actually ended the run, and it is what the cards and the parent's summary show:

Stop reasonMeaning
completedThe agent finished its own task and wrote its report.
turn_limitThe round cap was reached. The capped round wrote the report.
deadlineThe wall-clock budget hit its soft limit. The reserved round wrote the report.
cost_capThe session or daily cost cap was reached. The final round wrote the report.
cancelledThe run was killed (Stop, the parent stream closing, a shutdown). The runtime assembled a salvage report.
errorThe run raised. The runtime assembled a salvage report with the error in it.

A turn or time limit still reports status="completed", but it also sets an stopped_early flag, and that flag is what gates the worktree harvest: partial work is kept in its worktree for inspection rather than applied.

Salvage reports

When the model never got to write a report, the runtime writes one for it. A salvage report is deterministic, built from the journal: an opening line saying plainly that the runtime assembled it and after how many rounds, the error if there was one, the last three things the agent wrote (tail-capped), a count of the tools it called, and a pointer to the full record (task_output <agent_id>). It never pretends to be the agent's own conclusion.

A cancelled team gets a short grace period, five seconds, for its members to land their salvage reports before their reports are collected and delivered.

Getting the report to the parent

In the ordinary case the parent turn is still running and the report comes back as the tool result. A team_create result carries each member's full report (bounded at 6,000 characters), not a trailing slice of it, with the member's stop reason, its round count and a task_output pointer per member. Ahead of them sits the relay note, which tells the assistant in as many words that these reports were not shown to the user, so it must relay what matters, say how confident each report is, and point at task_output for the full record.

When no turn is waiting

Reports also arrive when nothing is listening: you pressed Stop, the app restarted, the agent ran detached, or it was resumed after it had stopped. Those reports are persisted into the session as an agent report row (role agent_report) and rendered as a report card, one collapsible row per agent, the report as markdown and the stop reason named in words. A notification is recorded alongside it, so it shows up in the bell panel even if you are looking at another session.

The row is backend-owned rather than written by the SPA, and it is one of the few non-chat roles the model is still shown: on the next turn visible_chat_history relabels it as a user message carrying the same reports, the same per-agent headings and the same relay obligation. At most MAX_AGENT_REPORTS_PER_SESSION (20) such rows are kept per session, oldest dropped first. The full records stay on disk and in the task registry, so trimming the chat never loses a report.

Waking the parent

A row in the chat is not an answer. Once reports land, the parent gets its turn anyway:

  1. A turn is still live

    The reports are pushed into the mid-turn inbox, exactly like a message you type while the assistant is working, and folded into the running turn at its next round. "Live" means the session's chat slot is held and its heartbeat is fresh, the same pair that decides whether a typed message is queued mid-turn.

  2. No turn is running

    A synthesis turn starts: one round, no tools, on the model the agents themselves ran on (resolved from a member's journal, falling back to the default chat model). Its prompt is the original request, the assistant's last message before the agents finished, and the reports. Its system hint says the turn was started by the runtime, not by you, and that it must answer from the reports without calling tools or starting agents.

  3. The answer lands as an assistant bubble

    The reply is persisted as an agent_answer row and rendered as a normal assistant message with a small label reading "Answered from the agents' reports" plus the team name. A notification is recorded too. On later turns the model reads the row back as its own previous assistant message, so the conversation stays coherent.

The guards are deliberate. Only one wake per session at a time. If the session cost budget is already reached the wake is skipped and a notification says so, pointing out that the reports are in the chat and your next message can use them. If the synthesis turn produces nothing, the row still gets a plain line saying so rather than staying silent. And the whole behaviour is behind the wake_parent_on_reports config key (default true); turn it off and reports still land as rows, they just do not get answered on their own.

agent_answer rows are capped per session at the same MAX_AGENT_REPORTS_PER_SESSION limit as the report rows.

Resuming and extending

Because messages.json is checkpointed at every round start, a finished or interrupted agent can be picked up where it stopped.

Resume - send_message to a stopped agent
When send_message targets an agent that is not running but has a journal, the runtime resumes it instead of dropping the message into a mailbox nobody drains. The agent keeps its id and its record; the stored messages are replayed and the sender's text is appended as a follow-up user turn. The resumed run is detached (the caller's turn does not wait), and its reply comes back as an agent report row, which then wakes the parent like any other. The tool result says so explicitly and names task_output for progress.
Extend - more budget for a run that is still going
A run's cap and deadline are fixed when it starts, so a slow agent had to stop at the limit and be resumed later with a cold context. POST /api/agents/{agent_id}/extend grants a running agent extra rounds or seconds while its context is still hot. The turn engine re-reads the extension dict at every round start, so a grant applies to the very next round. The endpoint accepts at most 200 extra rounds and four extra hours per call, refuses a request with neither, and returns 404 for an agent that is not running (a finished agent is resumed, not extended). The Extend button on an agent row asks for 20 rounds.

The budget readout

Every turn_start event is stamped with the run's budget state, computed by budget_readout from values passed in rather than read from ambient state, so a reloaded history renders exactly the same bars. The fields:

FieldWhat it carries
max_turnsThe round cap including any live extension.
elapsed_sSeconds since the run started, to one decimal.
deadline_sThe wall-clock budget including any extension, or absent when the type has no time limit.
cost_usdEstimated spend so far from the run's own token usage. Absent rather than zero when the model has no price entry.
budget_statefinishing once the next round is the last one (the cap, 90 percent of the time budget, or a cost cap already tripped), otherwise working.

The card turns those into one thin bar per dimension with the reserved final tenth drawn as a hatched slice, and a pill that reads working, finishing up, done, hit limit, salvaged or failed. Nothing in the pill or the bars is computed from the browser's own clock.
