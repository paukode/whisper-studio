Persistence

Everything Whisper Studio remembers between requests lives in one SQLite file. This page walks the schema, the per-session config latch, the companion tables, the startup migrations, and the locking that keeps a background write from clobbering a foreground save.

There is no external database and no server-side session cache to warm. A single file, storage/sessions.db, holds every chat, transcript, cost line, and scheduled-run record. It opens in WAL mode so the app can read while a write is in flight, and the schema evolves through numbered migrations that run once at startup. The data-access code lives in server/infrastructure/sessions.py.

One database, WAL mode

Every connection is opened through a small context manager in server/infrastructure/sessions.py that sets three pragmas on the way in:

PragmaValueWhy
journal_modeWALReaders and a single writer proceed concurrently, so a list query never blocks on an in-flight save.
busy_timeout5000 msWhen the writer is held, a second connection waits up to five seconds instead of raising database is locked.
synchronousNORMALFewer fsyncs than FULL; safe with WAL for a local-first, single-node app.

The connection is opened with a timeout=5.0 as well, and each context exits by committing then closing. If a pragma cannot be applied the code logs a warning and continues rather than failing the request. Rows come back as sqlite3.Row, so columns are read by name.

WAL writes a sessions.db-wal and sessions.db-shm sidecar next to the database. They are normal, and SQLite checkpoints the WAL back into the main file on its own. If you copy the database for a backup, copy all three files together.

Two roots: app home and user root

Every on-disk location resolves through server/infrastructure/paths.py, which owns a deliberate split by who edits what:

RootPackaged .appDev checkoutHolds
app_home()WHISPER_HOME, that is ~/Library/Application Support/WhisperStudioThe repo rootExactly two things: storage/ (sessions.db and the workspace indexes) and logs/.
user_root()~/.whisperThe repo rootEverything a person browses, edits, or deletes by hand: models/, skills/, plugins/, agents/, the config layer (config.user.json, pricing.json, PROMPT_RULES.md), and data/.

storage_root() sits under app_home() and not under the user root on purpose: the session history is the one thing a hand-edit or an rm in ~/.whisper must never be able to destroy. data_root() goes the other way, resolving WHISPER_DATA_DIR, then the data_dir config key, then <user_root>/data, and holds memory, session summaries, workflows, attachments, and the JSON stores. In a dev checkout the two roots are the same directory, so nothing about the layout changes.

On the first packaged boot, relocate_legacy_home() runs before the server modules import and moves any pre-split copies out of Application Support by same-volume rename, so no multi-gigabyte copy runs inside the app shell's health deadline. It leaves no compatibility symlinks behind; instead, migration 017 rewrites the absolute paths recorded in sessions.db on the same boot. Both halves are idempotent and a no-op in a dev checkout.

Not everything durable is in SQLite. Agent runs are journaled as plain files under <storage_root>/agents/<session>/<agent>/ (meta.json, events.jsonl, messages.json, report.md), written while the run is alive. The agent_tasks row exists from the first round and points at that journal; the record itself is the directory, which is what lets a crashed or cancelled agent still be read back and resumed. See The agent flight recorder.

The sessions table

The sessions table is the heart of the store. Its base shape is created on import by _ensure_db(); later columns are added by migrations (see below). A session carries both the chat conversation and, for recorded sessions, the transcript.

id
Primary key. A UUID for user sessions, or the fixed sentinel __cron_inbox__ for the pinned Scheduled Reports inbox.
title, custom_title, generated_title
The display title plus two flags recording whether the user renamed it or the app auto-generated it.
created_at, updated_at
ISO-8601 UTC timestamps. The list query sorts by updated_at DESC, and an index backs that sort.
segments
JSON array of transcript segments (text plus speaker) for recorded sessions. Empty [] for chat-only sessions.
chat_history
JSON array of chat messages. Holds prompt roles (user, assistant) and the backend-owned rows cron_event, task_event, session_message, agent_report, and agent_answer (see below).
speaker_names
JSON map of speaker id to a human-assigned name for diarized transcripts.
workspace_path
The folder this session is bound to, if any. The path is read from the DB, never the client, when opening a workspace externally.
latched_config
JSON snapshot of the config fields frozen for this session on its first turn (see the session latch).
pinned, archived
Sidebar flags. Pinned floats to the top; archived hides from the default list.
compaction_count
How many times history compaction has run for this session, surfaced in the UI so a long conversation shows it is being trimmed.
goal, goal_state
The WS-E goal loop's target text (goal) and its progress as a JSON blob (goal_state), added additively via _MIGRATED_SESSION_COLUMNS and surfaced in _row_to_dict() as goal / goalState.

Reads go through _row_to_dict() (full detail) or _row_to_summary() (list view). Both use a _safe_col() helper that returns a default when a column is absent, so a row written before a migration still deserializes cleanly.

The sidebar's list is the one read that runs on every refresh, so it is shaped for that. list_session_summaries() needs only two counts out of the JSON columns, and it asks SQLite for them with json_array_length() instead of loading every session's chat history and transcript into Python just to take a len(). On a store with a few long agentic sessions that difference is hundreds of megabytes of JSON parsed per refresh. A SQLite built without the JSON functions falls back to the parsing path.

Both the list and the single-session load also run await asyncio.to_thread(...) rather than inline: a SQLite read that waits on a writer through busy_timeout would otherwise stall every other request with it, and a long session is megabytes of JSON to decode.

The session latch

Settings can change mid-conversation, but you do not want the model or effort level to switch out from under an in-flight chat. The latch solves this. On the first turn, latch_session() in server/infrastructure/config.py snapshots a fixed set of fields and reuses that snapshot for every later turn in the session. Changing Settings afterward affects new sessions, not this one.

The latched fields are:

  • default_chat_model and chat_models - which model runs, and the enabled set.
  • chat_model_meta - per-model metadata used to render and price the choice.
  • effort_level and brief_mode - the thinking budget and response length.
  • permission_mode - the approval posture for the turn.
  • bedrock_region - the region the request is routed to.

The live snapshot lives in an in-memory dict (_latched_sessions) guarded by a lock, and the same values are persisted in the latched_config column so a session survives a restart with its choices intact. When a session is deleted, its snapshot is dropped via unlatch_session() as part of the delete cascade.

Latching happens at the very start of the turn, before the prompt is built. See Chat & tool orchestration for where it sits in the request flow.

chat_history: the backend-owned rows

chat_history holds more than what the model sees. Alongside user and assistant messages, the backend appends row types of its own, none of which is a PROMPT_ROLE, so the frontend renders each as its own card and the save-merge preserves them. What happens when a prompt is built differs per role, and visible_chat_history() is the single place that decides:

RoleWritten whenIn the promptCap per session
cron_eventA scheduled task fires, or a job is created, updated, or deletedDropped. A cron card you can see never inflates the token bill.50 (MAX_CRON_EVENTS_PER_SESSION)
task_eventA background task changes stateDropped, same reasoning.Not separately capped
session_messageAnother session sends this one a messageRelabelled user, with the sender named inline ([Message from session "…"]). The content is meant to reach the model, and the API accepts only user or assistant, so the stored row is never mutated, only its prompt view.50 (MAX_SESSION_MESSAGES_PER_SESSION)
agent_reportAgent work finished with no live turn to carry it: you pressed Stop, or a detached or resumed agent endedRelabelled user, rendered as a header per member (name, type, stop reason, rounds used, and a task_output <id> pointer at its record) above each report, prefaced with an instruction to relay what matters and how confident each one is. The next turn must see these, or the work is lost a second time.20 (MAX_AGENT_REPORTS_PER_SESSION)
agent_answerThe wake turn answered from those reportsRelabelled assistant: it is the assistant's own previous reply, so the conversation stays coherent.20 (the same constant)

_enforce_backend_row_caps() applies every cap on append, dropping the oldest of each kind first. Trimming loses nothing durable: the per-run cron record still lives in cron_runs, and an agent's full report still lives in its journal on disk.

The same distinction, "everything not in PROMPT_ROLES", is also what _ui_only_rows() uses to pick out backend-owned rows for the save-merge below, so an agent report that lands mid-save survives the round-trip exactly like a cron_event does.

Reactive compaction is the other force acting on chat_history. When a prompt grows too long, the oldest message pairs are summarized or dropped and the turn retries; compaction_count is incremented so the UI can show it. See Chat & tool orchestration for the compaction path.

The companion tables

Nine other tables share the same database file. Most are created by a numbered migration; tasks and the session-search mirror are created inline by their own modules instead, which is also what lets a test database bootstrap without running migrations.

The virtual table carries session_id, msg_index, role and the indexed text; the state table assigns each session a numeric slot. Every row's rowid is derived from that slot plus the message index, so a save rewrites only the rows that changed and a delete is a rowid-range delete rather than a table scan. Created inline by server/infrastructure/session_search.py and rebuilt by migrations 019 and 020.

The search mirror is the one companion that is pure derived data: it is rebuilt from chat_history and segments, so losing it costs nothing but a reindex. It is also the only one that can be absent by capability rather than by version: if the interpreter's SQLite lacks FTS5, available() reports false and both callers fall back to their pre-index behaviour (a regex scan for the sidebar, an explicit "unavailable in this build" for the tool).

The status lease is a recurring pattern: cron_runs, agent_tasks, and workflow_runs each write a running row that a boot-time reconcile flips to a terminal state (failed / interrupted / stale) if it is still open after a restart, so nothing hangs forever; notifications is instead the durable record behind the header bell, read over GET /api/notifications, and attachments ages out by its own retention GC rather than a lease. Each table is indexed for its hot query - session_costs by session_id and created_at, cron_runs by (job_id, started_at DESC), agent_tasks / workflow_runs by session and status, notifications by session and by unread state (read_at, created_at DESC), and attachments by session_id. See Cost tracking & budgets and Cron / scheduled tasks for how each is written and read.

Attachments

Uploaded files used to live only in a process-global dict with a 3-hour TTL, so their extracted content silently left the conversation on the next turn and died with every restart. The attachments table makes that content durable: an attachment is bound to the session that uploaded it, survives for a 30-day sliding retention window from its last use (RETENTION_DAYS in server/attachment_store.py), and is re-injected into the prompt on later turns via its id rather than being re-extracted. A periodic GC sweep drops attachments whose window has lapsed. Deleting a session deletes its attachments rows as part of the delete cascade below. See Attachment extraction for how a file becomes a row here in the first place.

Migrations

The schema is not frozen. server/migrations/runner.py runs once during the app lifespan (called from server/main.py) and applies any pending migration modules in order. Each module in server/migrations/ is a file named NNN_description.py that exports a VERSION, a DESCRIPTION, and a migrate(conn) function.

The runner discovers those modules, compares their versions against a schema_version tracking table, and applies only the ones not yet recorded. Each migration runs in a transaction: on success its version is inserted into schema_version and committed; on any exception the runner rolls back and stops, so a half-applied migration never leaves the database in an unknown state.

Two of these carry an instructive pattern. Migrations 014, 015 and 016 each widen a table whose CREATE in an earlier migration already includes the column, so they are no-ops on a fresh database and only exist to upgrade older ones in place. And 019 and 020 do their work by calling the owning module's own ensure and rebuild helpers rather than restating DDL, which is why a derived table can be rebuilt by a later migration without a schema rewrite.

Column-adding migrations wrap each ALTER TABLE in a guard so a re-run over a database that already has the column is a no-op, while genuine errors still propagate. SQLite requires one ALTER TABLE per column, which is why those migrations loop.

A migration that raises stops the whole runner, so the app will fail to finish startup rather than serve against a partial schema. Migrations should be idempotent and forward-only; there is no automatic down-migration.

Saves, locks, and the merge

Two writers can touch the same session at once: the frontend saving the whole session, and a background cron fire appending a cron_event. A naive full save from the frontend would overwrite the cron row that landed a moment earlier. Two mechanisms prevent that.

  1. A per-session lock

    Every writer takes an asyncio.Lock keyed by session id (_lock_for()). The save endpoints, the beacon save, append_message(), and the delete cascade all hold the same lock, so a read-modify-write can never interleave with another writer for the same session.

  2. A UPSERT that merges backend rows

    A session save is a single UPSERT (INSERT ... ON CONFLICT(id) DO UPDATE). Before writing, _upsert_session() reads the existing chat_history, pulls out the backend-owned UI-only rows, and appends any (by timestamp) that the frontend payload does not yet include. So a cron card written between the last hydrate and this save survives the round-trip.

The caps on both cron_event and session_message rows are re-applied after the merge, so merging can never push either count over its 50-row limit. Two save paths share this logic: the normal PUT /api/sessions/{id} and a navigator.sendBeacon POST used on page unload. Deleting a session is also lock-guarded and cascades (_delete_session_sync in server/infrastructure/sessions.py): it removes the parent row, session_costs, attachments, grounding, and the session's slice of the search mirror (by rowid range, via session_search.drop_session); hands cron jobs to cron_scheduler.on_session_deleted, which disables them, flags them orphaned and re-homeable, and repoints their run history to the Scheduled Reports inbox rather than silently dropping them; and clears every per-session in-memory cache (tasks, diarization, shell snapshot, cwd tracker, file state, the config latch, and the memory extraction/update-cadence state). Each step is best-effort and independently guarded, so one failing cleanup cannot block the rest.

Session export & import

A session can also leave the database entirely, as a portable file, independent of /branch's in-database fork. The format is newline-delimited JSON (JSONL): one export_meta line (session id, title, export timestamp, speaker names), then one segment line per transcript segment, then one message line per chat_history entry. _session_export_lines() in server/infrastructure/sessions_routes.py builds this once and is shared by every export path below, so a single-session export and a zip entry are byte-identical for the same session.

EndpointDoes
GET /api/sessions/{id}/exportStreams one session as a .jsonl download (session-export-<slug>.jsonl).
POST /api/sessions/import-transcriptCreates a brand-new session from an uploaded export: either a raw JSONL body or a multipart upload (field file). Unknown line types are ignored rather than rejected, so a future export field cannot break older imports.
POST /api/sessions/bulk-exportThe sidebar multi-select "Export": zips many sessions' portable exports into one download (sessions-export-<date>.zip). Body is a JSON id list, capped at 500, de-duplicated, unknown ids skipped rather than failing the batch.
POST /api/sessions/bulk-importThe sidebar "Import": accepts multiple uploaded files, each either a plain .jsonl export or a .zip bundle (detected by content, not filename, so a renamed file still works) whose .jsonl entries are imported individually, capped at 200 total. Returns per-file imported / failed lists so one bad file does not sink the batch.

Both import routes funnel through the same _insert_imported_session() helper, so a single-file import and a bulk-import entry produce an identical new session row. Because the format only carries segments, chat_history, and speaker_names, an import is a fresh session: cost rows, attachments, grounding sources, and cron bindings from the source session are not part of the portable file and do not travel with it. The backend-owned rows inside chat_history do travel, since they are just entries in that array, so a re-imported session still renders its cron cards and agent reports.

The Scheduled Reports inbox

A scheduled task can outlive the session that created it. If that session is deleted or archived, the firing must still land somewhere. ensure_cron_inbox() creates a fixed, pinned session with id __cron_inbox__ and title "Scheduled Reports" that catches orphaned runs. It is a fixture, not a user session: the delete endpoints refuse to remove it, so orphaned cron runs are never stranded.
