Goals & autopilot

Usually, you type a message. For a task with many steps, give Whisper Studio a goal. The app then continues the work until the task is complete, and does not stop at the halfway point. This page shows which method to use, and how to set a goal.

There is no mode to change, and there are no settings. The method of your request sets the level of autopilot:

  • A usual prompt, for a quick task.
  • /goal, for a task that must run until it is complete.
  • A workflow, for wide work that runs in parallel.

Click a box in the diagram to see when to use each method.

Three methods

The three methods are not different products. They set how much work Whisper Studio does before it stops and gives control back to you.

MethodWhenHow
A usual prompt A question, or a small change. One turn or a short tool loop is sufficient. This is the default. Type the prompt and press Enter. Refer to Your first chat.
A goal A task with many steps that must run until it is complete. Without a goal, the model can stop after it does one part. /goal <text> sets the goal and starts the work. A completion gate examines each turn and continues until the goal is met. A limit applies. Refer to the steps below.
A workflow Wide work, work in parallel, or work that a second agent must examine. Examples are an audit of 20 files, five designs with a judge, or the migration of a full folder. Ask in ultracode mode, or type /workflow <saved-name>. The model writes a script that starts subagents. You approve the preview. Refer to the workflow runtime.

A simple rule: if you usually type "keep going" or "you are not done yet", set a goal. The completion gate then sends these reminders. If you have more than one independent task to do at the same time, use a workflow.

Set a goal

A goal is one line that tells what "done" is for this work. Whisper Studio keeps the goal in the prompt. At the end of each turn, it examines if the goal is met.

  1. Set the goal

    Type /goal and the objective, for example /goal make the login page pass tsc, eslint, and its tests. The command sets the goal of the gate. It also sends the same text as your first message, so the work starts immediately. If a turn runs at that time, the app adds the goal text to that turn, and does not start a second turn.

  2. Read the goal banner

    A goal banner shows above the chat box. Its chip shows "working…", "achieved", "blocked", or "not checked". "Not checked" tells you that the app did not judge the goal this time. Put the pointer on the chip to see the reason. The goal stays set, and the app examines it again after the next turn.

  3. Optional: add a check that must pass

    Type /goal gate add <command>, for example /goal gate add npm test. The command must exit with code 0 before the goal is done. If the command fails, the app gives its output to the model as the reason to continue. The evaluator does not run.

  4. Optional: change the checks

    Type /goal gate to list the checks. Type /goal gate remove <N> to remove a check by its number. Type /goal gate clear to remove all the checks.

  5. Let the work continue

    When the model stops, the completion gate runs these checks, in this sequence:

    1. The Stop hooks.
    2. The files that the reply says it wrote must be on disk.
    3. A test, lint, typecheck, or build must pass after the last code change.
    4. Your gate commands.
    5. A judge: a cheap cloud evaluator, or the own model of an on-device session.

    If an item is missing, the gate tells the model what is missing, and the turn continues. You do not type "keep going".

  6. Clear the goal

    Type /goal clear to end the goal. An "achieved" result also ends it.

On an on-device model, add a check with /goal gate add <test command>. A test that must pass is a better signal than the judgment of a small model on its own work.

Some limits stop the loop for the current message, but the goal stays set:

  • The limit of blocks in sequence. The default is 8.
  • A clear "cannot do this" result from the judge.

On your next message, the gate starts again. If a gate command fails 3 times in sequence, the app pauses the goal. It then tells you to correct the command, remove the check, or set the goal again.

Two of the checks run also without a goal. If a reply says that it saved a file or made an artifact card, the file must be on disk and not empty. The artifact call must also be in that turn. If the model changed code and no test, lint, typecheck, or build passed after the change, the assistant must run one. If it cannot, it must tell you why. Thus, a turn can continue without a goal.

A goal works best when you can examine "done". Examples are "make the build pass" and "all tests green". The built-in verify_change tool runs the real check and returns VERIFY PASS or VERIFY FAIL. The evaluator gives this result more weight than a summary. Write your goal as a result that the app can examine. If you know the exact command, add it with /goal gate add.

Full-stack and UI work

For a change to the interface, the check is more than the tests. Whisper Studio uses a live browser preview. It starts your development server, loads the changed page, and reads the console errors. Then it clicks through the changed flow and makes a screenshot. Then it gives a pass or fail result.

A goal is not done until the page passes. Thus, the app examines and corrects the page until it works.

Write a UI goal as a result that the app can see. For example, write "the login form submits and shows the dashboard", not "make the form nicer". Set the permission mode first, because a goal can run for many turns. For the details and the two limits, refer to Verifying the UI in the loop. Install the browser tools first. Each UI examination in parallel starts its own development server.

When not to use a goal

Do not set a goal for a simple question or a change of one line. A goal adds a judge check at the end of each turn. On an on-device model, this is one more answer from the model of the session. Use goals for work with many steps. You can also change the direction during a goal. Your next message is a usual message, and the goal stays in the background.

More than one worker

A goal continues one line of work. For work in parallel, use one of these tools:

Sub-agents & teams

Start a helper in the background with /subagent, or let Whisper Studio run a small team. Each agent has its own tool loop.

Ultracode workflows

For wide work, the model writes a script that starts many subagents in a budget. You approve the script before it runs.
