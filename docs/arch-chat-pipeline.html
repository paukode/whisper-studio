Chat & tool orchestration

This is the component every other subsystem plugs into. A single streaming endpoint builds the prompt, calls the model, and drives an agentic tool loop - emitting Server-Sent Events the whole way.

Turn assembly lives in server/chat/routes.py; the agentic loop itself is the unified turn engine in server/chat/engine/runner.py, shared verbatim by Claude, GPT, and local models. The same run_turn also serves every unattended consumer: sub-agents, cron runs, and the Python-only run_headless_turn entrypoint (server/exec/headless.py, with output_schema and ephemeral options, callable from code but exposed on no HTTP route). Click a box below to trace a path - for example, click Streaming loop to see everything a single round can reach.

The request

A turn is a POST /api/chat whose body carries the question, prior history, the selected model and effort_level, the session_id, any attachment_ids, and the session_approvals map (the categories you have already pre-approved this session, for example {"write": "allow"}). The response is an SSE stream, not a single JSON body - tokens and tool activity arrive as they happen. An approval continuation re-enters the same endpoint with an approved_tool_result instead of a fresh question.

The busy slot and mid-turn messages

A session may have only one turn in flight. The endpoint claims that slot synchronously, at the top of chat_endpoint(), before any of the turn's own setup work (transcript condensation, attachment analysis, index grounding, hooks) runs, which can take seconds on a heavy turn. Every turn claims it, approval continuations included.

What happens to a second request depends on what it is:

RequestOutcome
A new message while the slot is liveIt is pushed into the session's mid-turn inbox (server/chat/engine/midturn_inbox.py) and the endpoint answers {"queued_into_running_turn": true}. No second stream opens.
A message flagged midturn when nothing is runningRefused with a JSON 409 carrying {"queued_into_running_turn": false, "error": "no_running_turn"}, so the composer can keep the text and tell you nothing was sent instead of silently starting a second answer.
Anything elseThe slot is claimed and the turn runs.

run_turn drains the inbox once per round, at the same checkpoint that injects wind-down reminders, and folds each queued message into the live message list wrapped in a <user_message_mid_turn> block that tells the model this is not a separate request. The model addresses it before its next tool call, in the same turn.

Keeping the slot honest

A slot nobody releases would 409 the session until a restart, so staleness is tracked separately from ownership. _active_chat_streams holds the claim token; _stream_heartbeat holds the time of the last observed progress. The engine beats once per round, and _with_heartbeat wraps the whole stream so it also beats on every chunk and every 30 seconds of silence (_HEARTBEAT_KEEPALIVE_S) - a single tool call can outlast a round, so a team of agents working for an hour must not look abandoned. A slot whose last heartbeat is older than 900 seconds (_STREAM_STALE_AFTER_S, above a single Bedrock read timeout) is presumed abandoned and reclaimed by the next turn. The pulse lives exactly as long as the stream generator, so Stop or a closed connection stops it immediately.

Building the turn

Before the model is ever called, the endpoint assembles everything the model will read:

  • Latch the session config. On the first turn, the model, effort level, and related settings are snapshotted so mid-session Settings changes never disrupt an in-flight conversation.
  • Assemble the system prompt. Base rules, the workspace WHISPER.md, selected memories, and per-session memory are registered as named sections on a PromptLayer (server/prompts/__init__.py): IDENTITY, MODE, WORKSPACE, DYNAMIC, TOOL_GUIDANCE, EXTENSION. The split is exactly one line - everything at or below WORKSPACE is the static, cacheable block; everything above it is the per-request tail. So anything that varies within a session (live git status, recalled memory, tool guidance) must sit on DYNAMIC or later, and session-stable text parked on a dynamic layer is re-billed on every round. Plan mode rides DYNAMIC on purpose: it is about a hundred fixed tokens in the uncached tail, against invalidating the whole cached prefix twice per planning session. A third, moving cache checkpoint is placed on the last message each round (annotate_messages_cache, server/chat/caching.py), so the conversation history caches round-over-round instead of being re-billed as uncached input.
  • Build the tool catalogue. The catalogue is deliberately stable across the per-turn state flips that would otherwise rewrite it: plan mode, strict-RAG grounding, and workspace connect or disconnect do not strip tools. The rule is register always, refuse at execution - a blocked write still has its schema, and the executor explains why it will not run. Rewriting the tools array instead would invalidate the prompt cache on every flip. See progressive tool disclosure.
  • Resolve @file mentions inline into the user message.
  • Expand attachments - documents are capped (around 150K characters) and images become vision blocks. See attachment extraction.
  • Index grounding. If the turn passes the grounding intent gate (contentless smalltalk skips retrieval; @index forces it) with workspace indexes selected, relevant passages are retrieved and injected, the sources are persisted per session, and a "grounding" chip is surfaced over SSE - clicking it opens the passages behind the answer. See Index / GraphRAG.
  • Condense an oversized transcript. A transcript above a size threshold is condensed to per-chunk extracts before it enters the prompt - both the transcript block and the transcript handed to the summary skills, so the prompt never overflows. It self-gates: below the threshold the transcript passes through unchanged. See Transcript summarization.

The streaming loop

The engine enters a loop of up to 50 rounds (the CHAT policy; the same loop serves every provider, and other consumers bring their own TurnPolicy). A policy can also carry a deadline_seconds wall-clock brake - agents set per-type deadlines (for example 900s for general) - and at the deadline the engine forces one final no-tools best-effort round instead of truncating. The cap and the deadline are re-read at the top of every round, so an Extend granted to a running agent (server/agents/extensions.py) applies from the next round on. Each round:

  1. Wind down near the cap

    With five rounds left (WIND_DOWN_AT) the engine appends a wind-down reminder, and on the last round (FINAL_ROUND_AT) the consumer's final_round_hint, if it set one. Interactive chat sets none; an agent sets the fixed report template (REPORT_TEMPLATE, server/agents/journal.py). The reminder is persisted onto the last user message by inject_reminder (server/chat/loop_hints.py) rather than injected request-only, because a request-only injection forks the token prefix between rounds and destroys the moving cache checkpoint.

  2. Drain the mid-turn inbox

    Anything you sent while the turn was running is folded into the live message list at this same checkpoint.

  3. Heartbeat and checkpoint

    The round beats the session's busy slot, and the on_round callback writes the message list to the agent journal, so a killed run resumes from here.

  4. Check the budget

    check_budget is the hard session or daily cost cap; below it, check_budget_soft trips at SOFT_LIMIT_FRACTION (0.9) of the cap. The first trip does not end the turn: it turns tools off, injects a "this is the final round, answer with what you have" reminder, and lets the model write its answer inside the budget. Only the second trip ends the turn. A wall-clock deadline works the same way, starting its final round at 90 percent of the time budget so the report is written inside the budget rather than after it.

  5. Invoke the model, streaming

    invoke_model_with_response_stream is wrapped in server/infrastructure/bedrock_retry.py - exponential backoff on throttling, and reactive compaction if the prompt is too long. A transient mid-stream provider fault surfaces as a retryable RoundError and the round re-runs, up to _ROUND_RETRIES_MAX (2) times with linear backoff, instead of ending the turn. Each retry still consumes a round from the budget, so a flapping provider is doubly bounded.

  6. Parse content blocks

    Chunks are parsed into text, thinking, and tool_use blocks and streamed onward.

  7. Act on the stop reason

    tool_use runs the tools, appends the results, and loops again. Any other stop reason (such as end_turn), when the policy enables the gate, does not end the turn on its own: the non-tool-use branch first runs the completion gate (see below).

Every round also writes a request snapshot - the exact tools, messages, and provider envelope it sent - through server/chat/request_snapshots.py, so any past request is reconstructable from disk.

The completion gate

run_completion_gate (server/goals/gate.py) is the one decision function every loop calls at end of turn. It runs four phases in order, and the first block wins:

  1. Stop hooks

    The blocking Stop hooks always run, whatever the goal state. A block re-injects the hook's reason and the turn continues.

  2. Claimed deliverables

    server/goals/deliverables.py reads the final assistant text, pulls out every file path it presents as a finished deliverable, and checks the file exists and is non-empty. A claim about an artifact card is checked against a real create_artifact call in the same turn. "Saved to report.docx" with no file is a block, not an answer.

  3. Verification evidence

    server/goals/verification.py is passive and deterministic: it never runs a suite itself. It reads the turn's messages and asks which code files were edited and whether a test, lint, typecheck, or build command ran green afterwards. Stopping right after editing code with no fresh passing evidence becomes a bounded nudge (at most MAX_VERIFY_NUDGES, 2, per turn) to run the check or say plainly what blocks it. Prose-only edits (markdown, text, data files) never trigger it.

  4. Goal gates, then the goal evaluator

    With the goal_loop flag on and an active goal, any quality gates you named with /goal gate add <command> run first: a red gate is deterministic proof the goal is not met, its output tail becomes the feedback, and the evaluator is not consulted. A gate that fails GATE_MAX_RETRIES (3) times in a row pauses the goal instead of looping. Only when the gates are green does an auxiliary model judge the goal.

A block re-injects [completion gate] feedback as a user message and the loop continues, bounded by goal_max_consecutive_blocks (default 8). The local preset turns the gate off entirely, so an on-device turn stays fully offline. See The goal loop & completion gate.

Executing tools

When the model asks for tools, execute_tool_batch() (server/tool_executor.py) runs them safely:

  • Partition for parallelism. Consecutive read-safe tools run concurrently; each write tool runs on its own. So [read, read, write, read] becomes [[read, read], [write], [read]].
  • Permission checks. Every tool is evaluated against the current permission mode and per-tool rules - allow, ask, or deny.
  • Approval gate. A tool that needs consent pauses the turn (state is stashed in the unified pause store, server/chat/engine/pause.py, keyed by session), and waits for the client to confirm.
  • Hooks. Hooks are a blocking subsystem (server/hooks/): run_hooks(event, payload) fires PreToolUse, which can deny or rewrite a call, and PostToolUse, which can inject additionalContext. A Stop gate (check_stop_hooks, server/hooks/engine.py) runs at end of turn via the completion gate, shared by every chat loop (Claude, GPT, and local, all on the unified engine) and cron runs; sub-agents and headless turns run with the gate off, and cron additionally verifies its runs separately (cron_verify). See Blocking hooks.

Dispatch itself is a pure mapping in server/tool_router.py; the implementations live in server/executors/. See Tool dispatch & executors.

The loop guard

Rounds and the completion-gate cap bound how long a turn runs; they notice nothing about a model calling the same tool with the same arguments over and over. That is server/chat/loop_guard.py, a pure per-turn tracker the executor consults before and after every dispatch. It refuses a call (returning a synthetic result, with no dispatch) in four situations:

  • An identical call that already returned an identical result twice in a row (IDENTICAL_STREAK_LIMIT, 3). The second identical result already gets a short notice appended, so the model has a chance to change course before the refusal.
  • An identical call that keeps failing, unchanged, three times (FAILURE_STREAK_LIMIT).
  • A repeating cycle of up to four distinct calls (MAX_CYCLE_PERIOD) repeated three times over (CYCLE_REPEATS).
  • A per-turn cap for a runaway-prone tool. The defaults are web_search 50, spawn_agent 50, and team_create 20, overridable with the tool_loop_caps config key.

Polling is legitimate repetition, so task_status, task_output, sleep, ci_status, git_status and their kind are exempt from the streak and cycle checks; the caps still apply. A byte-identical large payload (512 characters or more) coming back a second time is replaced by a stub pointing at the earlier result, so a repeated read does not re-enter the context in full.

Streaming back to the client

Throughout the turn, the endpoint yields typed SSE frames the SPA folds into the UI:

EventMeaning
textA streamed text chunk.
thinking / thinking_start / thinking_stopAn adaptive thinking block and its boundaries (all providers; the local path routes its reasoning here too).
skill / skill_input / skill_resultA tool call started, its parsed input, and a truncated preview of its output.
skill_progressHow many characters of a still-streaming tool call's arguments have arrived. A whole HTML app can take minutes to stream, so the running step shows the size so far next to its spinner.
usageToken counters, cost estimate, and remaining context (context_used/context_max).
tool_poolProgressive-disclosure telemetry: how many tools were advertised, how many deferred, and the estimated token cost of the deferred index.
team_progress / team_resultsSub-agent and team events (spawn, progress, completion) and the final per-agent reports.
groundingIndex-search metadata (folders searched, passages retrieved, and the id of the persisted sources behind the expandable chip).
statusCoarse turn-setup stage. The stream opens from byte zero, so these frames replace a silent wait while condensation, grounding, and dispatch run. Every turn starts preparing then connecting.
approval_request / user_questionThe turn paused on an approval, or on an ask_user_question.
stop_hook_block / goal_eval / goal_cap_reachedCompletion-gate decisions: a block and its reason, a goal verdict, or the consecutive-block cap being reached.
budget_warningThe session or daily cost cap tripped, carrying budget_kind, budget_limit, and budget_current. The first one announces the reserved final round; the second ends the turn.
tool_result_truncatedA tool's output was trimmed before it reached the model; the full text stays in the result cache for read_cached_result.
errorA mid-stream failure, appended inline so a partial answer is not lost.
[DONE]The stream is complete.

The frame vocabulary is pinned by tests. tests/golden_fixtures/ holds six recorded turns (plain text, thinking then text, a tool round, an ask_user_question pause and its resume, and a mid-stream error) as the full ordered list of frames each one emits, payloads included, with only the cost estimate and the tool-pool counts scrubbed. A change to the frame order or shape fails tests/test_engine_golden.py; when the change is intended, you re-record with GOLDEN_RECORD=1 pytest tests/test_engine_golden.py. The client half of the contract is src/types/schemas/chat.schema.ts, described on the frontend page.

Some session-scoped frames never ride the chat stream at all. Cron runs, background-task lifecycle events, memory writes, and agent reports that arrive with no live turn are published on a separate long-lived EventSource per session (/api/sessions/{id}/events), so they reach a session you are not currently watching. See Frontend architecture.

Compaction & persistence

If a prompt grows too long mid-stream, reactive compaction (server/chat/compaction.py) works down a ladder: first a local pre-pass that truncates older tool_result blocks by age, then the session's own accumulated memory as the summary when there is enough of it, then a real summarisation call, and only then blunt truncation. The summary model is the auxiliary_models.compaction entry when set, otherwise the session's own model. Thresholds are per model: 95 percent of its usable input budget triggers compaction, 98 percent is the ceiling. When even that cannot fit, the engine runs one final no-tools salvage round on a hard-trimmed tail, so a long agentic session ends with a synthesized answer instead of an error.

A summary paraphrases; two things must not be paraphrased. Whatever summary compaction produces, server/chat/compaction_anchors.py appends two deterministic blocks to it. Your own messages from the summarized region ride along verbatim, newest first, within a budget (up to 800 characters each, 4,000 characters in total), because a summary that turns "use the existing retry helper, do not add a new one" into "discussed retries" is how an agent confidently does the forbidden thing six turns later. Synthetic user rows the loop itself wrote (reminders, gate feedback, mid-turn wrappers) are excluded. Alongside them goes an anchor index: file paths, PR and issue numbers, commit SHAs, URLs, and error strings extracted mechanically, exactly as they appeared. A recovery pointer says the rest is not lost: the full history is still on disk and session_search can pull any message back verbatim.

When the turn ends, the assistant message is appended and the session is UPSERTed into SQLite under a per-session lock, so background rows written by other subsystems are never clobbered. visible_chat_history (server/infrastructure/sessions.py) decides what the next prompt sees of those rows. A cron_event or task_event row renders in the chat and is dropped before the prompt, so it never inflates the token bill. Three roles are translated rather than dropped: a session_message from another session becomes a user turn; an agent_report becomes a user turn that names the team, the reason the reports arrived with no turn running, each agent's stop reason and rounds used, and the task_output <id> pointer to its full record, with an instruction to relay what matters and how confident each report is; an agent_answer becomes the assistant's own previous message, so the conversation stays coherent. Each of these roles is capped per session, oldest dropped first. See Persistence, the agent flight recorder, and Cron.
