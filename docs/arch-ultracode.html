The ultracode workflow runtime

Ultracode is the mode where the assistant stops improvising a chain of tool calls and instead writes a program - a deterministic JavaScript orchestration script - that a locked-down Node vm harness runs detached from the turn. The script fans out many subagents with real concurrency, budgets, and a resumable journal, and it runs the same way on Claude and on GPT-on-Bedrock.

The runtime lives in server/workflows/. The model authors a script; a single Node process parses and validates it; the user approves it (unless the permission mode launches it directly, see Approval and trust); then the run executes detached while the Python side enforces the limits and streams progress back as a live card. Why a script instead of a tool loop

An ordinary chat turn is a loop: the model emits one tool call, waits for the result, decides the next call, and so on. That is fine for a handful of steps but it serializes everything and the model re-reasons the whole plan on every hop. Ultracode inverts it. For work that is wide (audit twenty files), deep (generate five designs, judge them, synthesize), or that must be confident (find bugs, then adversarially verify each), the model writes the control flow once as a script. Loops, conditionals, fan-out, and fan-in are ordinary JavaScript; the expensive leaf calls - agent() - run concurrently under a real scheduler. The plan is deterministic and inspectable before a single agent runs.

Ultracode is a tier, not a separate model. It is offered at the top of the effort dial and turns on the workflow tools plus the script-authoring directive (server/prompts/ultracode.py). Simple questions are still answered directly - the directive tells the model to reach for a workflow only when the work is genuinely parallel, comprehensive, or adversarially verified.

The script contract

A workflow script is plain JavaScript (not TypeScript) that must begin with a pure export const meta literal - no variables, calls, or interpolation - so it can be extracted and shown for approval without executing the body. After meta, the body runs in an async context and may await directly.

export const meta = {
  name: 'review-changes',
  description: 'Review changed files across dimensions, verify each finding',
  phases: [{ title: 'Review' }, { title: 'Verify' }],
}

const DIMENSIONS = [{ key: 'bugs', prompt: '…' }, { key: 'perf', prompt: '…' }]

// pipeline: each item flows through all stages independently - no barrier,
// so a 'bugs' finding verifies while 'perf' is still being reviewed.
const results = await pipeline(
  DIMENSIONS,
  d => agent(d.prompt, { label: `review:${d.key}`, phase: 'Review', schema: FINDINGS }),
  review => parallel(review.output.findings.map(f => () =>
    agent(`Adversarially verify: ${f.title}`, { phase: 'Verify', schema: VERDICT })
      .then(v => ({ ...f, verdict: v.output }))
  ))
)
return { confirmed: results.flat().filter(f => f.verdict?.isReal) }

The body has a small, fixed set of hooks. Everything else is ordinary JavaScript built-ins: there is no fs, require, process or fetch, so reading the repo means going through tools.ws_read_file and friends.

HookWhat it does
agent(prompt, opts?)Spawn one subagent. Always resolves to an object: { text, output, usage, status, agent_id, stop_reason, stopped_early, model_warning }. status is 'completed' when the agent finished, 'incomplete' when a round, time, or cost limit stopped it (text is partial and stop_reason names the limit), and 'failed' when it failed. text is the agent's final message; model_warning is set when opts.model was refused; output is the schema-validated object when opts.schema was given, so read result.output.findings, not result.findings. A failed agent resolves with status: 'failed' rather than throwing. opts: label, phase, schema, model, effort, isolation:'worktree', agentType.
pipeline(items, …stages)Run each item through all stages independently, no barrier between stages. Item A can be in stage 3 while B is still in stage 1. A stage that throws drops that item to null and the error is logged. AgentCapError, BudgetExceededError and a cancel are not dropped: they reject the whole call, so the script can catch them. The default for multi-stage work.
parallel(thunks)Run tasks concurrently and await them all - a barrier. A thrown thunk becomes null and the error is logged (filter before use). AgentCapError, BudgetExceededError and a cancel reject the whole call, so the script can catch them. Use only when you truly need every result together.
phase(title)Name the stretch of work the run is in. The card shows the current phase name; it does not nest agents under it, and a title absent from meta.phases logs a warning.
log(...parts)Append a line to the run's journal (console.log and console.error are aliases). It is a record for you to read afterwards, not something the card renders.
tool(name, args?) · tools.<name>(args)Call a read-only tool directly, with no model in the loop, and get its output string. tools is a proxy, so tools.ws_grep({ pattern }) and tool('ws_grep', { pattern }) are the same call. Write tools are refused, and unknown names fail closed. MCP tools that are marked read-only are allowed too. agent() and tool() calls share one counter, and tool() is refused after 500 calls of either kind in a run.
workflow(name, args?)Run another saved workflow inline as a sub-step (one level of nesting; shares the parent's caps and budget). The called workflow must be saved and approved (from its preview card once, or earlier in this session); if not, workflow() returns status: 'failed'.
budget{ total, spent(), remaining() } - the run's output-token budget. spent()/remaining() are async (a live RPC read of the token ledger), for dynamic loops (while (await budget.remaining() > 50_000) …).
argsThe JSON value passed into the run, verbatim - the way a saved workflow is parameterized.

Determinism and the sandbox

The script runs inside a Node 22 vm context created by server/workflows/harness/harness.mjs. The context is deliberately bare: there is no require, process, fs, fetch, or module system - only the hooks above and the standard JS built-ins. The harness runs on the node that WHISPER_NODE_PATH names, or else the first node on PATH. When there is neither, the run fails with "Node.js was not found". On top of that, harness/guards.mjs installs determinism guards so a resume always replays identically:

Math.random()
Throws. Randomness would make a resume diverge - derive variety from agent() results or an index instead.
Date.now() / new Date()
Throw (a Date with explicit arguments still works). The Date.prototype.constructor back-door is redirected to the guarded constructor too.
setTimeout / setInterval / setImmediate
Throw; queueMicrotask is kept (deterministic).

The single hardest boundary is host code execution. Node is launched with --disallow-code-generation-from-strings, so the classic vm escape - reaching the host Function constructor via anAgent.constructor.constructor('return process')() - raises EvalError instead of returning the host process. The harness's own vm.runInContext is unaffected.

Honest caveat: a vm context is not a certified security boundary. The real anchor is defence in depth - the user approves every new script before it runs (unless the Workflow runs mode is Bypass, or Auto with a budget of 600,000 output tokens or less), the context has no dangerous globals, the child's environment is scrubbed, and codegen-from-strings is disabled. Treat a workflow script the way you treat any code you are about to run: read the preview.

The runtime and its limits

server/workflows/runtime.py is the Python side of the bridge - a WorkflowRun that acts as the JSON-RPC server for the harness and owns the limits the script cannot bypass, no matter what the JavaScript does:

  1. 16-way concurrency

    An asyncio.Semaphore caps live agent() calls. A script may hand parallel() a thousand thunks; only sixteen run at once and the rest queue.

  2. A 1000-agent lifetime cap

    A runaway-loop backstop. The cap is checked before dispatch; exceeding it raises an AgentCap error into the script and marks cap_reached.

  3. An output-token budget

    A hard per-run ceiling on agent output tokens - the work measure a user can read off any provider's pricing page. Every run gets one; a launch that sets none gets the 600,000-token default (DEFAULT_WORKFLOW_BUDGET_TOKENS). Tokens accrue when an agent completes, so the budget is re-checked after acquiring a slot as well as before dispatch - that bounds a parallel burst's overshoot to the concurrency window instead of the whole cap.

  4. A 500-call read-only tool ceiling

    tool() and tools.<name>() use the run's sequence counter, which agent() calls also advance, so tool() is refused once the run has made 500 calls of either kind. Each name is checked against the executor registry and refused unless it is registered read-only (or is an MCP tool marked read-only), failing closed on a name the registry does not know.

  5. A pinned workspace

    The run's root is frozen when it is previewed or launched, so every agent in it resolves workspace tools against that path rather than whatever folder happens to be connected by the time it starts. An explicit path must already exist. Outside Bypass, it must be inside the connected workspace. The preview card shows the path it will use.

  6. A resumable journal

    Every phase and agent call is appended to the run's journal; the resume cache is built from it (see below).

None of these is a config key: they are code constants, so they cannot be widened from the config (config.user.json). The only per-run limit is budget_tokens, which a launch may set and which the approval gate reads; workspace_path pins the folder.

USD cost is still priced per agent against the model that actually ran (a per-agent opts.model override is billed at that model's rate) and rolls up into the run's ledger and the session cost log, but it is display only - enforcement is the token counter. Because agent() is a run_agent call, a workflow agent can run on an on-device model as long as that model supports tool calling; a chat-only local model is refused with a readable reason, and the run fails early only when no configured chat model can drive an agent loop at all. The one hard cloud requirement is a schema: structured output still goes through the cloud-only distillation call. A nested workflow() inherits the parent's remaining budget and merges its spend, agents, and cap back into the parent, so nested work can never exceed the outer cap.

The Node harness to Python bridge

The script and the runtime speak line-delimited JSON-RPC over the child's stdio, framed by server/workflows/rpc.py (a 10 MB line ceiling, typed error constants for budget / cap / cancel / depth). agent(), nested workflow(), tool() (and tools.<name>()), and budget.spent() / budget.remaining() are requests to Python; phase() and log() are notifications; every other statement is pure in-sandbox JS. This is what lets the same script run unchanged on either provider - the harness never talks to a model directly.

On the Python side, server/workflows/agent_adapter.py turns one agent() RPC into one run_agent call. It maps the harness opts (schema to structured_schema, effort, model, isolation, agentType) and normalizes the result back to { text, output, usage, status, agent_id, stop_reason, stopped_early, model_warning }. run_agent keeps status: 'completed' for an agent that a limit stopped, so the adapter reads stopped_early and reports 'incomplete'. The journal records the stop_reason, workflow_status lists the incomplete agents, and the run's result text counts them. Because it rides the provider-agnostic runtime, a workflow launched from a GPT-on-Bedrock session spawns GPT subagents, and one launched from a Claude session spawns Claude subagents - structured output is validated on both.

Workflow subagents can reach every session-connected tool - the same tool router and executors the chat pipeline uses - so a workflow agent can read files, run the built-in verify_change tool, search the index, or drive the browser, exactly like a hand-spawned sub-agent.

Journal, resume, and lifecycle

Runs are registered in the workflow_runs table (see Persistence) with an immutable on-disk script snapshot and an append-only journal under workflows/runs/<run_id>/ in the data root (~/.whisper/data for the Mac app, data/ in the checkout for a source install; WHISPER_DATA_DIR or data_dir move it). Saved scripts are under workflows/scripts/<name>/ in the same root. The run is driven detached via the shared async-task machinery; its outcome is published on a per-run event-bus channel (workflow:{run_id}) so a reloaded session re-attaches. On boot, reconcile_stale() flips any orphaned running row to stale - its journal stays resumable.

Resume is the payoff of determinism. Every agent() call is keyed by a call_hash of its prompt and opts (display-only fields like label and phase are dropped). When a run is resumed, every call whose prompt and opts match a completed call of the earlier run replays from the cache, wherever it is in the script. Results with the same hash replay first in, first out in issue seq order (not completion order), so two identical parallel calls replay into the right positions. Calls with a changed prompt or opts run live, and so do calls whose inputs depend on changed results. Failed and incomplete calls are not cached, so a resume runs them again. Same script and same args means a 100% cache hit.

Waiting without polling

The model does not poll a run. It ends the turn or does other work, and the run's completion wakes the chat. To block in the same turn, it calls workflow_wait (or task_wait for detached agents). One call waits until the runs end or a timeout passes (600 seconds by default, 1800 at most). The server reads the stores once a second inside that call, so the model spends no rounds while it waits. Both tools are in WAITS_ON_AGENTS, so a wait on agents or workflows does not count against an agent's time limit. A task_wait on a shell command is the agent's own work: that time counts (waits_on_agents in server/tasks/wait.py). A wait that counts, and every wait in a cron or headless run (no ToolScope), stops at the run's soft time limit (WaitBounds.deadline). In the chat turn, a message from the user stops the wait at once with interrupted: "user_message", so the next round reads it. The loop guard caps sleep at 10 calls a turn, and from the third call it points at the wait tools.

While a run is live, workflow_status reads the counters (agents, tokens, cost) from the running ledger. The table row holds them only from the run's end. A tool script may call workflow_status, workflow_list, task_status, task_output, and session_search: the executor registry marks them read-only.

Budget floor and workspace

workflow_run refuses a budget_tokens below 100,000 output tokens with a message, and the run does not start. A smaller budget ran out part way through a run. In the Bypass permission mode, a run may be pinned to any existing folder with workspace_path, also a folder outside the connected workspace. In the other modes, open the folder with ws_open_folder first. Its card follows the mode.

Deliverable verification

A script that produces files lists their paths in its return value under deliverables (strings, or {path} objects; relative paths resolve against the run's workspace), and verify_deliverables checks each one before the run is finalized. Any path that is missing or zero bytes downgrades the run to failed with an error naming the first few, which is what the card shows and what the model reads next turn. The script contract in the ultracode prompt tells the model to take each path from the tool result that saved it, never from an agent's claim that it wrote one.

Readable results

What the Background tasks list shows and the model reads next turn is prose, not JSON. _render_result walks the script's return value (strings as written, lists as - item lines, dicts as key: value, nested with indentation). The excerpt is capped at 2,048 characters, and a workflow result keeps its head rather than its tail, because a workflow report leads with its headline (status, agent count, cost).

Approval and trust

A brand-new inline script, or a saved workflow that has not been approved, returns a workflow_preview side-effect rather than running. WorkflowPreviewCard shows the phases as a stepper, the whole script, and the run's output-token budget; approving POSTs to /api/workflows/runs and the run begins. The card's buttons are exactly Approve & run and Deny: there is no separate trust step, because approving is trusting. The launch route grants that exact script hash for the rest of the session, and when the approved bytes match a saved workflow of the same slugified name it marks that saved script trusted too, so future runs by name skip the card (the response says which slug it trusted). The byte-match guard means an inline script that merely shares a saved workflow's name can never trust bytes you did not just approve. Trust is revoked automatically if the saved script is later edited, since it is pinned by hash, and session grants are process memory that a restart clears. A resume replays a run you already approved. This preview-then-approve gate is the same mechanism the CI autofix below reuses.

The permission mode decides whether a new script shows the card (server/workflows/launch_policy.py): Bypass launches with no card, Auto launches runs budgeted within the 600,000-token default and shows the card for anything bigger, Don't ask declines the launch, and every other mode (Asks first, Plan, Accept edits) shows the card. Trusted saved workflows and resumes never consult this gate, and no mode loosens the runtime's server-side limits above - the concurrency semaphore, the agent cap, the token budget, and the vm jail apply regardless.

CI watch and PR autofix: ultracode applied

The clearest use of the runtime is the CI loop in server/ci/. After you push, ci_watch follows a branch's GitHub Actions run to its conclusion as a detached background task. When it fails, ci_autofix reads the failing logs, diagnoses each failure into structured findings, and generates a workflow script that applies the minimal fixes and then runs the verify_change tool. That generated script is handed to you through the very same workflow_preview card - so nothing is edited or pushed until you approve it, and once approved it runs under the runtime's budget, journal, and run card. Untrusted CI-log text is embedded as double-encoded JSON and clearly delimited as data in the fix agent's prompt, so a hostile log line cannot inject instructions.

This is the pattern to copy: a subsystem does its own scouting (find the failing checks, read the logs), then emits a workflow for the runtime to execute under human approval. Diagnosis is read-only; the write path is gated by the preview.

How it composes with the rest of the system

Ultracode is the capstone of a larger harness; it leans on the pieces around it rather than duplicating them.

Provider-agnostic agents
Every agent() is a run_agent call, so workflows inherit Claude/GPT parity, usage accounting, effort, structured output, and worktree isolation.
The task registry
A CI watch is a row in the unified background-task registry, so it appears in the header's task list. A workflow run is mirrored into that same registry as a workflow-kind row, on top of its own workflow_runs row and WorkflowRunCard, so it shows up in the header's Background tasks list too, and its result is injected into the next turn (server/agents/completion_inject.py).
Tool disclosure and hooks
The workflow and CI tools surface only in the ultracode tier; workflow subagents still pass through the same Pre/PostToolUse hooks and tool executors.
The built-in verify_change tool
Generated fix workflows end by running the repo's verification gate, which emits a deterministic VERIFY PASS / VERIFY FAIL line - the same tool the goal completion gate keys on.
