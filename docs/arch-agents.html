Sub-agents & the event bus

The assistant can hand work to focused helper agents that run their own tool loops in the background. This page covers the runtime that executes them, the agent types, how a team is spawned, the mailbox agents talk through, and the per-session bus that streams their progress back into your chat.

Sub-agents exist so a single turn can do several things at once, or delegate a narrow job to a cheaper, more constrained worker. A sub-agent is not a separate service. It is a plain run_agent call in server/agents/runtime.py that reuses the same tools, the same dispatch path, and the same session as the chat that spawned it. What makes it feel live is the event bus: a per-session queue the runtime publishes to, which the turn engine drains and forwards as team_progress frames.

Everything a run leaves behind - its journal on disk, its report, the budget that reserves the reporting round, and how a report reaches you when the turn that launched it is gone - lives on its own page: Agent flight recorder. This page is the runtime that produces those records.

The agent runtime

run_agent() is the entry point. The agent loop is the unified turn engine: _run_agent_loop runs run_turn (server/chat/engine/runner.py) under a per-type TurnPolicy (a turn cap plus a wall-clock deadline, completion_gate=False so a child can never trip the parent turn's goal gate, unattended=True, and a turn_scope_id of agent:<id>), and drains the engine's SSE frames into progress events. Provider adapters are the chat engine's own (AnthropicAdapter or OpenAIResponsesAdapter, chosen by the model's provider), so agents run on both Anthropic-on-Bedrock and OpenAI GPT-on-Bedrock (the Responses API via bedrock-mantle). server/agents/providers/ survives only for _distill_structured, the one-shot structured-output distillation. On calling run_agent, the runtime:

  1. Guards recursion

    Depth is capped. An agent that spawns an agent that spawns an agent stops at MAX_DEPTH = 5 and returns a failed result rather than recursing forever.

  2. Registers an id, a mailbox, and a journal

    A short random agent_id is minted (a caller may pre-assign one so a run that never returns can still be found), a mailbox is created on the message bus, and the agent is recorded in the server/agents/registry.py registry so list_agents and the UI can see it. The on-disk journal opens here too, before the first model call, and with it a row in the unified task registry (server/tasks/registry.py, the agent_tasks table from migration 007, kinds shell|agent|workflow|ci) pointing at the journal's event log. That is what makes task_output work for any agent, not just a detached one, and what emits task_event lifecycle events through server/tasks/events.py into the global background-tasks panel.

  3. Resolves the model

    Agents inherit the session-selected model through a model_id_override threaded from /api/chat. There is no hardcoded per-type model. A spawn_agent call can override it with a chat_models key; an unknown key resolves through the family alias ("sonnet" to the newest configured sonnet*), and an override that still cannot be honoured falls back to the session model with a model_warning on the tool result rather than failing silently (server/agents/model_resolve.py). With no override at all it falls back to your configured default chat model (then sonnet, then the first configured model). On-device models are first-class here when they support tool calling: those run through the same LocalAdapter interactive chat uses, served with mark_busy so a model switch cannot stop the server mid-run. A chat-only local model is refused up front with a readable error, as is a structured-output schema on a local model, and when no configured entry can drive an agent loop the run fails early instead of erroring at the provider call.

  4. Builds a filtered tool pool

    Agents use the same progressive tool disclosure as chat: activate_from_history plus assemble_partitioned_pool, with the deferred index appended to the agent's system prompt, so tool_search works inside an agent. The runtime then adds the agent-only tools (receive_messages, complete_coordination, and spawn_agent while below the depth ceiling), deduplicates by name, and applies the agent type's tool filter (see below).

  5. Runs the loop

    Up to config.max_turns rounds, bounded also by the type's deadline_seconds wall-clock budget (the primary "don't loop forever" brake) and by the session cost cap. The mailbox is drained once at run start into the initial user message; each round invokes the model, executes any tool_use blocks, checkpoints the message list into the journal, and emits progress events. It ends on any stop reason other than tool_use, at the round cap, at the deadline, or at the cost cap - and each of those limits reserves one final no-tools round for the agent's report rather than truncating mid-plan. The completion gate is deliberately off for agents. Whichever limit ended the run is named in the result's stop_reason. See Agent flight recorder.

Bedrock calls for agents run on a shared 16-worker ThreadPoolExecutor, off the request's event loop. Its size is taken from the single AGENT_CALL_CONCURRENCY knob rather than a literal of its own, because that pool is what actually gates how many agent model calls can be in flight. Running the calls off-loop is why publishing progress must be thread-safe (see the event bus).

Bounding the fan-out

Two checks sit in front of every new agent, in server/agent_tools/spawn.py, and both apply to team_create members and blocking spawn_agent calls alike:

  • A concurrency cap. At most MAX_CONCURRENT_AGENTS_PER_SESSION = 16 agents run at once in one session. The slot is reserved with a deliberately await-free check-then-increment, so a whole asyncio.gather of siblings cannot race past it, and released in a finally. Over the cap, the agent is refused with a message telling the model to wait or shrink the team. The number is locked to AGENT_CALL_CONCURRENCY on purpose: a second, independently chosen number is how 16 agents once got dispatched against a 4-wide pool, leaving 12 blocked.
  • A pre-flight cost check. The session cost cap is checked before dispatching each agent, not only reactively inside its own round loop, so agent N+1 never starts once the combined spend of agents 1 through N has already cleared the cap. Without it each sibling found out only after starting, having already paid for its system prompt and tool catalog.

Per-type turn and time budgets are user-overridable through agent_limits in config.json, per type or under a "default" key.

Detached (background) agents. The loop above runs inline and blocks the turn. Passing detach: true to spawn_agent (in server/agent_tools/) does not: it returns a task_id immediately through start_detached_agent in server/tasks/agents.py and runs the agent in the background. A detached agent runs read-only by default, since no human is present to clear the [WS_APPROVAL] write gate, unless isolation: 'worktree' gives it its own git worktree to write into. Its result is folded into a later turn by server/agents/completion_inject.py (inject_completions); the model polls with task_status / task_output and cancels with task_cancel. Two separate limits apply: at most DETACHED_PER_SESSION_CAP = 8 detached agents are accepted per session, and a server-wide semaphore, DETACHED_CONCURRENCY = 2, decides how many of those actually run at a time, so fire-and-forget spawns cannot starve the shared model-call pool that blocking spawns use. When the run finishes after its launching turn has ended, its report is delivered into the session as an agent report row rather than lost (see Agent flight recorder).

Worktree harvest. When a worktree-isolated agent finishes, its changes are auto-applied uncommitted onto the spawning branch and the worktree is removed (harvest_agent_worktree, server/git/worktree_harvest.py). The harvest diffs against the branch-point base commit, so work the agent committed inside its worktree is included, and it reports one of five statuses: applied (all changes landed, worktree removed), partial (some landed, conflicts kept the worktree), clean (nothing to bring back), kept (not applied - the agent did not finish, or every file conflicts; worktree kept), or error. Nothing is ever committed on your behalf; the changes show up in git status.

Inside one turn

Each iteration of the loop is small and deliberate. Any mail waiting when the run starts is drained into the initial user message; after that, an agent reads new messages by explicitly calling the receive_messages tool. Each round the engine invokes the model through its adapter, parses the returned content blocks into text, thinking, and tool_use, and acts on the stop reason:

  • If the stop reason is not tool_use (or there are no tool uses), the collected text is the agent's final output and the loop returns a completed result.
  • Otherwise each tool use is executed and the results are appended as a user message, then the loop runs again.

Tool execution mirrors chat. Every tool routes through route_tool() in server/tool_router.py (the same dispatch the chat loop uses), so a sub-agent reads files, greps, runs commands, and calls the web tools exactly as the assistant does. The agent tools (spawn_agent, send_message, receive_messages, complete_coordination, list_agents) dispatch through the router too, with the caller's id, depth, and team threaded via the ambient agent_nesting_ctx context variable; complete_coordination is a normal tool call whose summary is captured from the engine's frames rather than a hard mid-round stop. Tool output is budgeted the same way chat budgets it, around 50,000 bytes per result, keeping the head and the tail and naming a cache file the model can read in full with read_cached_result. Results that are themselves model prompts (prompt and folder skills, summarize_transcript, analyze_document) are exempt, because their instructions sit at the tail.

Approvals auto-resolve inside an agent. There is no user present to click a card, so a [WS_APPROVAL] response is executed inline. A tool that needs a workspace but finds none returns an explanatory error rather than pausing. Keep this in mind when you choose which agent type does the work, and lean on read-only types when you do not want unattended writes. See Approval & permissions and Sandbox & security.

Agent types

Every type is a frozen AgentConfig in server/agents/config.py. A config sets the turn limit, a wall-clock deadline, the token budget per response, and how the shared tool pool is filtered (a whitelist and a read-only flag that strips the write tools). Every type carries a deadline_seconds budget - the code documents it as the primary "don't loop forever" brake - and both limits are user-overridable per type via agent_limits in config.json. The types the assistant can spawn:

TypeToolsMax turnsDeadlinePurpose
generalFull pool120900sThe default worker. Reads, writes, runs, and can itself spawn children.
exploreRead-only30600sFast search-and-read to answer questions. Write tools are removed.
planRead-only40600sAnalyzes the codebase and returns a structured, step-by-step implementation plan.
verifyFull pool30600sRuns tests and validates behavior, ending with a VERDICT: PASS / FAIL / PARTIAL line.
coordinatorOrchestration only1001800sSpawns and messages other agents; has no file access at all.

The coordinator's whitelist is exactly spawn_agent, send_message, list_agents, and complete_coordination. It cannot touch files by design. Three further types back the memory subsystem - memory_extractor, memory_consolidator, and session_summarizer - and are not ones you spawn directly. See Memory system.

Each user-facing type shares a common working method appended to its system prompt: restate the task, list steps, gather evidence per claim, then run a short self-check before the final answer. That self-check is emitted as a text event, so it shows up in the live log.

How read-only is enforced

filter_tools_for_agent() applies two rules in order: an allowed_tools whitelist first, then the read_only flag - applied even when a whitelist is set, so a custom type cannot whitelist a write tool past its own read-only flag. With read_only set, every tool in the WRITE_TOOLS set is removed. That set covers the obvious writers (ws_write_file, ws_edit_file, ws_run_command, the git write commands, config_set, memory_write, cron_create, and more), and a registry backstop catches the rest: any native executor registered read_only=False counts as a write even when absent from WRITE_TOOLS. So an explore or plan agent physically cannot mutate your project.

Custom and ephemeral agent types

The built-in table is not the whole story (server/agents/custom_config.py):

  • Custom types are persistent presets stored as .whisper/agents/<name>.md files: YAML frontmatter over a markdown system prompt. They load from two scopes - project (<workspace>/.whisper/agents/) and user (~/.whisper/agents/ in an installed app, the checkout's own .whisper/agents/ in a source install) - with project winning name collisions, and they resolve before the built-in AGENT_TYPES, so a custom type can shadow a built-in name. The frontmatter keys that are read are name, tools, read_only, model and max_turns; the markdown body is the system prompt.
  • Ephemeral types are built in-memory at spawn time from an inline agent_definition object passed to spawn_agent instead of a registered type name; they are never written to disk.
  • promote_agent_type saves an ephemeral type used earlier in the session out to a .whisper/agents/ file, re-validating it through the same builder on the way rather than trusting the stored definition. Its scope parameter picks project (the default) or user.

Every custom or ephemeral config passes through the exact same WRITE_TOOLS plus registry-backstop filtering as the built-in presets, so a file- or model-authored type cannot grant itself write tools its read_only flag forbids.

Teams

team_create (in server/agent_tools/) spawns several agents in parallel in the same session, each with its own agent id, and aggregates the results. The flow:

  1. Announce the team

    A team_started event is published with a team_id, the team name, and each member's name, task, and type. The SPA uses this to draw the report card scaffold before any agent produces output.

  2. Run members concurrently

    Each member is a run_agent call, gathered with asyncio.gather. Every member inherits the session model and is tagged with the shared team_id, so its events land in the same card.

  3. Aggregate and finish

    When all members finish, a team_completed event is published and the tool returns a JSON summary back to the model. That summary carries each member's full report (bounded at 6,000 characters), never just a trailing slice, headed by its status in words, its round count, and a task_output <agent_id> pointer. Ahead of the members sits the relay note, which states outright that the user has not seen any of this. A manifest of the team's members is written to disk at the same time, so a restart can find every member's record from the team id alone.

A running team can be stopped mid-flight: POST /api/teams/{team_id}/stop sets a stop flag and cancels the gather task, and each member publishes a stopped event as its loop is cancelled. The flag is what distinguishes the two ways a gather can be cancelled. With it set, the model gets each member's salvage report in place of a bare "stopped by user". Without it the outer turn was cancelled and nobody will read the tool result at all, so the members are stopped, given a few seconds to write their salvage reports, and those reports are delivered into the session as a row the next turn reads. Agents can also spawn their own children with spawn_agent; the child inherits the parent's team_id and event channel, so "agents spawning agents" renders as badged child rows under the same card rather than vanishing.

Inter-agent messaging

Agents coordinate through a mailbox, not shared memory. The MessageBus in server/agents/messaging.py is a thread-safe dictionary of per-agent message lists. It offers a small, deliberate API:

send(from_id, to_id, content)
Enqueue one message into a specific agent's mailbox.
broadcast(from_id, content)
Enqueue to every other mailbox in the sender's own session; returns the recipient count. Mailboxes are session-scoped: the bus records each agent_id's owning session via create_mailbox(agent_id, session_id=...), so a broadcast never crosses into another session.
receive(agent_id)
Drain and return all pending messages (clears the mailbox by default).

The send_message tool wraps send and broadcast: pass a to_agent_id for a direct message, or set broadcast=true to reach every other agent in the same session. Delivery is pull-based. Mail waiting when a run starts is drained into the agent's initial user message; after that, a recipient sees a message only when it calls the receive_messages tool, at which point the messages are injected as a user turn. When an agent finishes, its mailbox is deleted in the runtime's finally block.

The mailbox (MessageBus) and the event bus (AgentEventBus) are separate systems. The mailbox is agent to agent, drained once at run start and then pulled explicitly with receive_messages. The event bus is agent to user, one-way progress that streams live.

The event bus

The AgentEventBus in server/agents/event_bus.py is a per-session publish/subscribe queue. A subscriber calls subscribe(session_id) and gets a bounded asyncio.Queue (max around 512 events); the runtime calls publish(session_id, event) at every milestone. Multiple subscribers per session are supported, and each event fans out to all of their queues.

Two properties matter:

  • Thread-safe publishing. Agent Bedrock calls run on a thread pool, so publish must work off the subscriber's event loop. Each subscriber records the loop it lives on; a cross-thread publish hops into that loop via loop.call_soon_threadsafe, while a same-loop publish does a direct put_nowait. (Cron no longer needs the cross-thread path: it runs as a native asyncio task on the same loop as its subscribers.)
  • Bounded and lossy on purpose. If a subscriber falls behind and its queue is full, the event is dropped with a log warning rather than blocking the producer. Progress is best-effort; the aggregated result the tool returns is the source of truth.

Event phases

Runtime events are plain payloads (no type field) carrying an agent_id, the agent's name and type, the optional team_id and parent_agent_id, and a phase. Every event the runtime emits is journaled as well as published, so the on-disk log and the live card see the same sequence; the publish is a no-op when a run has no channel, the journal write always happens. The phases you will see over a run:

PhaseWhen
team_startedA team is announced with its member roster.
startedAn agent begins; carries the task preview, the resolved model, max_turns and deadline_s.
turn_startA new loop iteration starts, stamped with the budget readout below.
textThe agent produced text this turn (including its self-check). Buffered per round and flushed once, not once per streamed delta.
tool_call / tool_resultA tool was invoked, then returned. Each carries a short preview and a fuller one, so a row can expand to the whole input or output.
completed / turn_limitThe agent finished, or stopped at a limit. turn_limit carries the stop_reason that names which limit.
stopped / failedThe agent was cancelled by the user, or raised an error.
team_completedEvery member of a team has finished.

Two more phases exist only in the journal, never on the bus: resumed, written when a stopped agent is picked up again, and finished, the terminal record with the status, stop reason and round count.

The budget readout on turn_start

Every turn_start is stamped by budget_readout (server/agents/runtime_support.py), a pure function whose every input is passed in, so a reloaded history renders identical bars:

FieldValue
max_turnsThe round cap including any live extension granted by the Extend button.
elapsed_sSeconds since the run started, to one decimal.
deadline_sThe wall-clock budget plus any extension; null for a type with no time limit.
cost_usdEstimated spend so far from the run's own usage totals. null, rather than zero, when the model has no price entry.
budget_statefinishing once the coming round is the last one (the cap, 90 percent of the time budget, or a cost cap already tripped), else working.

The SPA reads exactly these fields for an agent row's budget bars and its state pill (src/hooks/chatStream/agentBudget.ts); nothing there is computed from the browser's own clock.

Getting to the client

The event bus does not talk to the browser directly. While the chat turn runs the tool batch, the engine (server/chat/engine/runner.py) subscribes to the session channel and drains it in a tight loop, re-emitting each event as a team_progress SSE frame. Draining happens during the batch, so a long-running team_create streams activity in real time instead of arriving in one burst when the tool finally returns.

Eight event types are filtered out here: cron_event, memory_event, task_event, cron_progress, ci_progress, ci_result, session_message, and workflow_event are skipped, because a separate long-lived stream, /api/sessions/{id}/events, delivers those (task_event is the unified background-task lifecycle role, and a workflow run also has its own per-run stream). Skipping them prevents double-rendering: without the workflow_event entry a detached workflow rendered mid-batch as if it were this turn's own subagent team. On the client, the SPA groups team_progress frames by team_id and agent_id into the live report card, badging spawned children under their parent. See Chat & tool orchestration for the wider SSE frame set and Frontend architecture for how the card is rendered.
