MCP & plugins

Add tools from external MCP servers, and add Python plugins to the backend. Both methods give the assistant new capabilities without a change to the core code.

Whisper Studio has many built-in tools. You can add more tools in two ways:

  • An MCP server connects an external system and gives its tools through the Model Context Protocol (MCP). MCP servers are on when you add them. When you add a server, the app enables and starts it. You disable the servers that you do not use.
  • A plugin is a local Python file that registers new executors, API routes, or pre-tool hooks in the backend. Plugins are off until you enable them. A file in the plugins folder does nothing until you enable it in "Settings".

Which one to use

Select the method from the location of the capability and its owner.

MCP server

The tool is already available as an MCP server, for example a database bridge or a ticket system. You connect it without Python. It runs as its own process or as a remote endpoint, separate from the backend.

Plugin

The function must run in the backend: a tool executor, a new REST route, or a PreToolUse hook that examines or blocks other tools. You write a small Python file.

Connect an MCP server

MCP (the Model Context Protocol) is a standard protocol between an application and external tool providers. Whisper Studio uses two transports:

  • A command entry starts a stdio child process. The backend sends JSON-RPC messages to the process over the standard input and output. A stdio server uses the network only when the server itself connects to it.
  • A url entry connects to a remote server over streamable HTTP. The optional bearer_token_env_var gives the name of an environment variable that contains the bearer token. The server entry contains only the variable name, not the token.

A stdio server gets your shell environment without your credentials. The environment comes from your login shell. Thus, AWS_PROFILE and AWS_REGION from ~/.zshrc get to the server. This also applies when you start the app from the Dock.

The app first removes these credential variables: GH_TOKEN, GITHUB_TOKEN, GH_ENTERPRISE_TOKEN, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN, ANTHROPIC_API_KEY, OPENAI_API_KEY, and TAVILY_API_KEY. Then the app adds the env entries of the server. Thus, a key that you give to one server gets only to that server.

  1. Open the MCP settings

    Click the gear icon. Open "Tools and automation", then "MCP servers".

  2. Add a server

    Add a command (an executable and its arguments), or a url for a remote server. You can also ask the assistant to add a server, import one with a project, or edit mcp_servers.json in the data folder.

  3. Let the backend connect

    The backend finds the change in less than 1 s. It starts the command as a stdio process, or it opens an HTTP connection to the url. Then it gets the tools, resources, and prompts of the server. You do not restart the app. To open the "MCP servers" settings from the chat box, type /mcp.

  4. Examine the server state

    If the connection fails, the error shows below the server name. The app tries again when you click "Restart" or change the start settings. If a server adds tools after the start and sends a notice, the app reads the list again.

  5. Use its tools in the chat

    The tools of the server show with the built-in tools, and the model can call them. To run a prompt of the server, type / and select /server:prompt. Then type the arguments of the prompt. To add a resource of the server to your message, type @ and select @server:uri. Refer to MCP prompts and MCP resources.

Each server has an enabled flag in "MCP servers". The app keeps the flag after a restart. When you change the flag, the app starts or stops the server, and the next message uses the change. A disabled server also refuses its tools when they run. Thus, a session cannot continue to call a server after you disable it.

The model does not get the full schema of each MCP tool on each turn. The tools of an enabled server show in a short index of names and one-line descriptions. The app sends the full schema only after the model loads the tool with tool_search. Thus, many enabled tools add only a small number of tokens to each turn. Refer to Agent tools.

Approval, tool lists, and limits for each server

Each server has an approval_mode in "MCP servers". The default is auto.

ModeBehavior
autoThe default. The tool runs immediately, with no approval card.
promptEach call goes through the usual approval steps: your permission mode, the session approvals, and your rules.
writesA call with a read-only name (get_, list_, search_, and similar prefixes) runs immediately. Other calls get the same steps as prompt.
approveEach call asks you. A "yes for all" approval and the bypass mode cannot skip this card. Use it for a server that you do not fully trust.

WARNING: With the default auto mode, an MCP tool runs with no approval card. For a server that can change data, set approval_mode to prompt, writes, or approve.

The entry of a server can also contain these keys:

tool_overrides
A different approval mode for one tool of the server.
enabled_tools
A list of the tools to use. The other tools are not available.
disabled_tools
A list of the tools to hide. If a tool is in both lists, this list has priority.
read_only
true marks all the tools of the server as read-only. false ignores the read-only hints of the server.
read_only_tools
A list of the tools that are read-only.
call_timeout_seconds
The time limit of one tool call. The default is 1800 s (30 minutes).

The read-only marks control the agents that cannot write: the explore and plan agents, and each agent that starts from a plan-mode turn. These agents can call an MCP tool only when the tool is read-only. A tool is read-only when your entry marks it, or when the server marks it with the MCP readOnlyHint. These agents cannot call other MCP tools.

When a server asks you a question

MCP has elicitation: a server can stop its tool call to ask the user a question. An example is a question before a destructive action. The question shows as an approval card, and you answer on the card. If nobody answers in 5 minutes, the app declines the request. In a cron run or a detached agent, nobody can answer. Thus, the app declines the request immediately.

MCP resources

MCP servers can also give resources, for example documents or records. Two built-in tools let the assistant use them:

ToolFunction
list_mcp_resourcesLists the resources of the connected MCP servers.
read_mcp_resourceReads one resource into the conversation.

You do not call these tools. Ask a question that uses the data, for example "what tables does the connected database expose?". The model then calls the two tools.

You can also add a resource to a message. Type @ and select the resource, for example @github:issue://12. The app reads the resource when the turn starts. The text of the resource goes into the message before your text.

Write a plugin

Plugins are in the plugins folder: ~/.whisper/plugins/ for the Mac app, and plugins/ in the checkout for a source install. A plugin is one Python file of maximum 512 KB. Its name contains only letters, digits, and underscores. The file gives a version and a description. It also has a register() function, which the backend calls when you enable the plugin.

__version__ = '1.0.0'
__description__ = 'My custom plugin'

def register(app, executor_registry):
    # Register a new executor tool
    def my_tool(tool_input, transcript, attachments):
        return 'Hello from plugin!'
    executor_registry['my_tool'] = my_tool

register() receives two objects:

app
The FastAPI application. A plugin can add REST routes to it.
executor_registry
The map of tool executors. Add a function under a tool name, and the assistant can call that tool.

An executor function receives (tool_input, transcript, attachments) and returns the result for the model. Plugins run in the backend process. Thus, they can import backend modules, for example to register a hook.

Enable a plugin

The app does not load a plugin automatically.

  1. Put the file in the folder

    Put my_plugin.py in the plugins folder. The app does not import the file, and it does not call register().

  2. Enable the plugin

    Open "Settings", then "Plugins". Enable your plugin. You enable each plugin separately.

  3. Use the plugin

    The app calls register() immediately. A new tool executor is available on your next message. When you disable the plugin, the app unloads it immediately.

  4. Restart when the app tells you

    In these cases, the response of "Settings" contains a restartRequired flag and a note:

    • You enable a plugin that adds FastAPI routes.
    • You disable a plugin that added routes or hooks.
    • The plugin did not load. Correct the plugin first.

    To restart, quit and open the Mac app again. In a source install, press Ctrl+C in the terminal, and then run bash setup.sh.

  5. Restart after an edit

    The backend imports a plugin one time. If you change the code of a loaded plugin, restart the app.

Why plugins are off by default. A plugin runs Python code in the backend with the permissions of the app. If the app loads each .py file automatically, an unknown file can run code at the next start. An example is a file from a dependency or a clone. Thus, only the plugins that you enable can run. Refer to Sandbox & security and the security model.

Pre-tool hooks: examine and block calls

A plugin can also examine each tool call before it runs. To do this, the plugin registers a PreToolUse hook. It imports the hook registry and calls register_pre_tool_hook() in register():

def register(app, executor_registry):
    from server.infrastructure.plugin_hooks import register_pre_tool_hook
    register_pre_tool_hook(check_security)

A hook is an async function fn(tool_name, tool_input):

  • To let the call run, return None.
  • To block the call, return a dict, for example {"reason": "...", "findings": [...]}. The tool does not run, and the model receives the reason.

The hooks run in sequence, and the first block stops the call. register_pre_tool_hook() uses the register_hook(event, fn) API. With that API, fn(payload) returns a dict with decision, reason, updatedInput, and additionalContext. Use register_hook for more than the two results "run" and "block".

The bundled plugins/security_checks.py is an example. It is a protected plugin: it is always enabled, and you cannot disable it in "Settings". It examines ws_write_file, ws_edit_file, and ws_create_file. It finds dangerous patterns in the new content, for example an eval( call, an os.system( call, or a secret in the code. Then it blocks the write and gives a summary of the findings.

Read plugins/security_checks.py before you write a plugin. It shows the full structure: __version__, __description__, a register() function, and an async hook that returns a block dict. Copy it as a start.

Import a Claude Code or Codex project

"Settings", "Import project" reads a Claude Code or Codex CLI project folder. It copies the contents into the formats of this app. The app only reads the source project. It does not change it.

SourceDestination
CLAUDE.md (Claude Code) or AGENTS.md (Codex)The project WHISPER.md in rules/<project>/ in the user folder.
.claude/skills/, or .codex/skills/ and .codex/.agents/skills/The skills folder of the app. The two tools use the same SKILL.md frontmatter. Thus, the app copies the folders without a change.
.mcp.json (Claude Code) or the [mcp_servers.*] tables in config.toml (Codex)The MCP server list, with the servers that you added before.

  1. Give the source folder

    Type the path in "Source project folder".

  2. Optional: give the workspace

    Type the path in "Workspace to import into". If the field is empty, the app uses the connected workspace.

  3. Select the source type

    Select "Claude Code" or "Codex CLI". With "Auto-detect", the app finds the type from the folder layout.

  4. Read the summary

    The app does not overwrite items. It skips a WHISPER.md that is available, a skill folder with the same name, and an MCP server with the same name. The summary lists the skipped items.

No imported item runs during the import. Instructions and skills are text until a chat or a skill reads them.

Troubleshooting

  • MCP tools do not show. Make sure that the enabled flag of the server is on in "MCP servers". Examine enabled_tools and disabled_tools. A tool in disabled_tools is hidden, also when the server is on.
  • The MCP server shows an error. For a command entry, the start failed. Make sure that the executable and the arguments are correct, and that they run in your login shell. For a url entry, examine the address. If you set bearer_token_env_var, make sure that the variable contains a token.
  • The plugin does not load. Enable it in "Settings". A plugin with only executors is available on the next message. For a hook, find the line "In-process hook registered for <event>" in the server log. If the response contains restartRequired, restart the app.
  • A plugin edit has no effect. The backend imports a plugin one time. Restart the app after you edit the file.
