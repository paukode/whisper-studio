MCP & plugins

Add tools from external MCP servers, and extend the backend with opt-in Python plugins. Both paths hand the assistant new capabilities without touching the core code.

Whisper Studio ships with a large built-in tool pool, but you can grow that set two ways. An MCP server connects an outside system and exposes its tools over the Model Context Protocol. A plugin is a local Python file that registers new executors, API routes, or pre-tool hooks inside the backend. Plugins are opt-in: dropping a file into plugins/ does nothing until you enable it in Settings. MCP servers are opt-out: adding a server enables and starts it immediately, and you explicitly disable the ones you don't want connected.

Which one do you want?

Pick the mechanism by where the capability lives and who owns it.

MCP server

A tool already exists as an MCP server (a database bridge, an issue tracker, a filesystem gateway). You want to connect it without writing Python. It runs as its own process or a remote endpoint, isolated from the backend, and you enable it once in Settings.

Plugin

You want custom behaviour that lives inside the backend: a bespoke tool executor, a new REST route, or a PreToolUse hook that inspects or blocks other tools. You are comfortable writing a small Python file, and enabling it takes effect live for most changes.

Connecting an MCP server

MCP (the Model Context Protocol) is a standard way for a host application to talk to external tool providers. Whisper Studio speaks it over two transports. A command entry is launched as a stdio child process, and the backend exchanges JSON-RPC messages with it over standard input and output. A url entry instead connects to a remote server over streamable HTTP, with an optional bearer_token_env_var naming an environment variable that holds the bearer token (the token itself is never stored in the server entry, only the variable name). Nothing goes over the network for a stdio server unless the server itself reaches out.

  1. Open Settings and add a server

    Click the gear icon, go to the MCP tab, and add a server entry: either a command the backend runs to start the server (an executable plus its arguments, the same shape you would put in an MCP client config elsewhere), or a url for a remote server.

  2. Let the backend connect

    On enable, the backend either spawns the command as a stdio child process or opens a streamable-HTTP connection to the url, then performs the MCP handshake to discover the tools and resources the server offers. If the connection fails, the server shows as unavailable rather than silently doing nothing.

  3. Enable it in Settings > MCP

    A configured MCP server does not force itself into every conversation. Each server has its own persisted enabled flag in Settings > MCP, not a per-turn chat-toolbar toggle: flipping it starts or stops the server live, and the tool pool picks up the change on your next message. A disabled server's tools also refuse at execution time, so a session that used a server earlier cannot keep calling it after you turn it off.

  4. Use its tools in chat

    Once enabled, the server's tools appear alongside the built-ins and the model can call them during the tool loop, gated by the same permission mode as everything else (unless you have set a per-server approval mode, below). You can also mention a server directly in the composer by typing @mcp: and its name to browse its tools.

MCP tools count against your per-turn token budget just like built-in tools: every enabled tool's schema is sent to the model before your message. Enable only the servers a conversation needs, and disable the ones you are done with in Settings > MCP. See Agent tools for how tool schemas are billed.

Per-server approval and tool allowlists

By default an MCP tool call is approved exactly like any other gated tool, under your current permission mode. You can tighten or loosen that per server from Settings > MCP with an approval_mode:

ModeBehavior
autoNo approval needed; the tool executes immediately. The default, so an unconfigured server behaves the way it always has.
promptEvery call goes through the normal approval pipeline, subject to your permission mode and any rules.
writesCalls that look read-only by name (get_, list_, search_, and similar prefixes) auto-execute; anything else is gated like prompt.
approveEvery call always asks, and this floor cannot be bypassed by a blanket "yes for all" setting. For a server you do not fully trust yet.

A per-tool tool_overrides map lets one tool on a server use a different mode than the server's default. Two more per-server lists narrow which tools are exposed at all: enabled_tools (an allowlist) and disabled_tools (a denylist, which wins when a tool appears in both). All of these live in Settings > MCP next to the server entry.

When a server asks you something mid-call

MCP defines elicitation: a server can pause its own tool call to ask the human a question before it finishes (for example, confirming a destructive action or picking among options). When that happens, the request surfaces through the same approval pipeline as everything else, as a card you answer with the mcp_elicit_respond action. If nobody answers within a few minutes, it times out and the server's request is declined on your behalf. In an unattended context such as a cron run or a detached agent, there is nobody to ask, so an elicitation is auto-declined immediately rather than stalling the run.

Reading MCP resources

Beyond tools, MCP servers can expose resources (documents, records, or other readable content). Two built-in tools let the assistant work with them:

ToolWhat it does
list_mcp_resourcesLists the resources exposed by the connected MCP servers.
read_mcp_resourceReads a specific resource so its content enters the conversation.

You do not call these yourself. Ask a question that needs the data ("what tables does the connected database expose?") and the model uses list_mcp_resources and then read_mcp_resource to pull in what it needs.

Writing a plugin

Plugins live in plugins/ at the repository root. A plugin is a single Python file that declares a version and a description, then exposes a register() function the backend calls at startup.

__version__ = '1.0.0'
__description__ = 'My custom plugin'

def register(app, executor_registry):
    # Register a new executor tool
    def my_tool(tool_input, transcript, attachments):
        return 'Hello from plugin!'
    executor_registry['my_tool'] = my_tool

register() receives two handles:

app
The FastAPI application, so a plugin can mount custom REST routes.
executor_registry
The tool-executor mapping. Add a callable under a tool name and the assistant can call that tool.

An executor callable takes (tool_input, transcript, attachments) and returns the result the model sees. Because plugins run in-process, they can also import backend modules, for example to register a hook (covered below).

Enabling a plugin

This is the important part, and it is deliberately not automatic.

  1. Drop the file in

    Place your plugins/my_plugin.py in the folder. On its own, this does nothing. The file is not imported and its register() is never called.

  2. Enable it in Settings

    Open Settings, go to the Plugins tab, and turn your plugin on. Enablement is per plugin, so you choose exactly which files load.

  3. It loads live, mostly

    Enabling a plugin calls its register() immediately, so a new tool executor is offered on your very next message, no restart needed. Disabling live-unloads it the same way. Two things still need a restart, and the Settings response says so with a restartRequired flag when it applies: a plugin that mounts new FastAPI routes cannot be hot-mounted, and fully unloading a hook on disable is not clean (enabling a hook plugin does take effect live; it is the disable side that cannot cleanly unhook). Restart with Ctrl+C then bash setup.sh when one of those applies.

  4. Editing needs a restart

    This part has not changed: backend modules are imported once at startup, so changing the code of an already-loaded plugin needs a restart to pick up the edit. Only enable/disable is live; editing is not.

Why opt-in? A plugin runs arbitrary Python inside the backend with the same privileges as the app. If dropping a .py into plugins/ auto-executed it, a drive-by file (pulled in by a dependency, a clone, or a careless copy) would run code the moment the server started. Requiring an explicit enable in Settings means nothing runs that you did not choose to run, live-loading or not. See Sandbox & security and the security model.

Migrating from the old opt-out behaviour is lossless: anything already loaded stays loaded, and only new files stop auto-executing.

Pre-tool hooks: inspecting and blocking calls

Plugins are not limited to adding tools. They can also intercept every tool call before it runs. A plugin registers a PreToolUse hook by importing the hook registry and calling register_pre_tool_hook() from inside register():

def register(app, executor_registry):
    from server.infrastructure.plugin_hooks import register_pre_tool_hook
    register_pre_tool_hook(check_security)

A hook is an async function fn(tool_name, tool_input). Return None to allow the call. Return a dict such as {"reason": "...", "findings": [...]} to block it: the tool never runs, and the reason is surfaced back to the model. Hooks run in order and the first block wins. register_pre_tool_hook() is a thin adapter over the underlying register_hook(event, fn) API, where fn(payload) returns a structured {"decision", "reason", "updatedInput", "additionalContext"} dict; reach for register_hook directly if you need more than a plain allow/block.

The bundled plugins/security_checks.py is a working example, and it is not a normal opt-in plugin: it is a protected plugin, always enabled and not something you can toggle off from Settings. It hooks ws_write_file, ws_edit_file, and ws_create_file, scans the content being written for risky patterns (an eval( call, an os.system( shell call, a hardcoded-looking secret), and blocks the write with a summary of what it found. Read it as the reference example for the hook shape, even though you cannot disable it.

Read plugins/security_checks.py before writing your own. It shows the full shape: module __version__ and __description__, a register() entry point, and an async hook that returns a block dict. Copy it as a starting point.

Troubleshooting

  • MCP tools are not showing up. Confirm the server's enabled flag is on in Settings > MCP, not just configured. A configured-but-disabled server contributes nothing, and check enabled_tools / disabled_tools too, a tool named in disabled_tools is hidden even if the server is on.
  • The MCP server shows unavailable. For a command entry, the launch failed; check that the executable and arguments are correct and runnable from the same shell that started Whisper Studio. For a url entry, check the address and that bearer_token_env_var (if set) names an environment variable that actually holds a token.
  • My plugin does not load. Enablement in Settings is required, but a restart usually is not. If the plugin registers only executors, it should appear on your very next message once enabled. Watch the server logs at startup for the "In-process hook registered for <event>" line if it installs a hook, and check the Settings response for restartRequired if it mounts routes or you just disabled a hook plugin.
  • My plugin edit did not take. Loaded plugins are imported once at startup. Restart the server after editing the file; enable/disable alone does not re-import changed code.
