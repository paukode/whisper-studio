Live preview & browser automation

The assistant can spin up your dev server, open a headless browser against it, click through the running app, and stream the whole thing into a dock so you watch it happen. All of it is named, sandboxed, and consent-gated.

Live preview turns "let me build this UI" into "let me build this UI and check it renders." A handful of tools spawn a real dev server (server/preview/process.py), drive a real Playwright Chromium (server/preview/browser.py), and surface the result two ways: a screenshot the model can see inline, and a live screencast you can watch in the right dock. Click a box in the diagram to trace the flow.

The manager and its sessions

server/preview/manager.py holds a PreviewManager that tracks multiple concurrent, named PreviewSession objects (its shape mirrors the MCP manager). Each session bundles an optional dev-server process, its own lazily created browser, and a bit of metadata (port, base URL, creation time, owner). Names are unique across the app, because they resolve against the workspace's .whisper/launch.json. Each session also records its owner: the chat session that started it. Only the owner may stop, replace or drive a preview (navigate, click, fill, eval, resize). Another chat can list and inspect it (screenshots, snapshots, logs), but its attempt to stop it or to start a session under the same name is refused with an error naming the owning chat, so it picks a different name for a preview of its own. Starting a name the same chat is already running is an error too: reuse that session, or stop it first to restart it.

PreviewSession
One named unit: a DevServerProcess | None, a BrowserSession, plus port, url, created_at, and owner (the starting chat's session id, empty when none was known). A session can be browser-only (no subprocess) if you point it at an already-running server.
start_session(name, command, cwd, port, url, env, owner)
Under an async lock: refuse a duplicate name (with PreviewNotOwned when another chat owns it), spawn the dev server if a command was given, register the session under its owner, and return it. Spawning is separate from loading a page.
stop_session(name, caller)
Under the same lock, refuse a caller chat that is not the owner (PreviewNotOwned); an empty caller, the Settings kill switch, may stop any preview. Then pop the session and tear it down: kill the process group first, then close the browser. The teardown runs as its own task awaited under a shield, so a caller cancelled mid-stop cannot leave a server running that nothing can reach any more. Returns whether anything was actually stopped.
list_sessions()
A status snapshot per session: id, url, port, process_alive, browser_started, created_at, and owner.

Spawning the dev server

Unlike a one-shot terminal command, a dev server must stay alive across many tool calls. So process.py spawns it as a plain asyncio subprocess (no PTY) and drains its output continuously in the background. DevServerProcess.spawn() does this in order:

  1. Validate the command

    The raw joined argv is run through validate_command() from the security layer. Validation happens on the raw argv (not a shell-quoted form) because the process is exec'd directly with no shell, so quoting would only hide sensitive paths from the scanner.

  2. Sandbox-wrap it

    The command is wrapped by build_pty_sandbox_wrap() (the same wrapping long-lived terminal sessions use), producing the real argv plus a temporary sandbox profile path.

  3. Exec under a new session

    It is launched with start_new_session=True, not a preexec_fn. A preexec_fn callable would fork Python, which under uvloop can deadlock and wedge the whole event loop; setsid in C between fork and exec avoids that while still making the child a process-group leader so it can be killed cleanly.

  4. Drain the output

    Two reader tasks copy stdout and stderr into bounded ring buffers, so preview_logs can tail them and a chatty server can never grow memory without bound.

Bounds, not guesses. The stdout/stderr ring buffer is capped at 1 MB per stream (older bytes are dropped in half when it overflows). Spawn itself is bounded at 30 seconds as a safety net against a pathological sandbox-wrap or exec hang, so starting a server can never block a chat turn forever. A validation failure raises DevServerSpawnError, which is surfaced to the model as text, never a silent fallback.

Where does the command come from? Either a per-workspace .whisper/launch.json entry resolved by name (same shape as Claude Code's own launch.json: a list of configurations, each with a name, runtimeExecutable, runtimeArgs, and optional port), or an ad-hoc command passed directly on the tool call. If neither is present, preview_start returns a clear error explaining both options.

The two sources are approved differently. A start by name, with cwd omitted or inside the workspace, needs no approval in any permission mode once a person has approved its command: the first start of a new or changed command follows the mode, and a Yes on that card records the command's SHA-256 for the workspace in launch_trust.json (server/preview/launch_trust.py). The file alone earns nothing, since it can come from a cloned repo or an edit a permissive mode applied with no card; only a person's answer to a card records trust. An ad-hoc command follows the permission mode like any other command. A deny rule and a session "No for all" on the preview category (outside Bypass) and the rm-class floor (checked against the resolved command, inside sh -c too) still apply to a named start. See Previews from launch.json.

What runs is what was decided. The preview router pins the resolved config into the call's payload (launch_config) when preview_start is dispatched; the card shows that pinned command, the executor runs it, and the exemption is withheld when launch.json no longer resolves to it. The Live pane's Restart button sends no pin and reads the file.

The Playwright browser

Each session owns one BrowserSession (server/preview/browser.py). The Chromium browser, its context, and its page are created lazily on first navigation, so a session that only needs its dev server never pays for a browser. ensure_started():

  • Launches headless Chromium, bounded at 60 seconds for the cold start (the first launch is slow). A timeout raises a clear error pointing at an incomplete Playwright install.
  • Uses an ephemeral context (new_context(), never launch_persistent_context()): no cookies or profile persist across sessions, and nothing is shared with your real browser.
  • Sets default timeouts on the context: 15 seconds for actions and 30 seconds for navigation, so a not-yet-ready or unreachable dev server fails fast instead of hanging the turn.
  • Installs a scheme guard at the context level (before any page exists, so it also covers popups): every request whose scheme is not http or https is aborted. This blocks file://, data:, and chrome:// escapes as a last-line technical backstop under the approval gate.
  • Captures diagnostics into bounded ring buffers (500 entries each): console messages, uncaught page errors (recorded as error-level entries so a thrown TypeError is not invisible), and finished/failed network requests with their status.

Actions on the page

Once a browser exists, the assistant drives it with a small vocabulary. Actions that change state or spawn work are approval-gated; pure inspection is read-only and runs freely.

That is 14 tools in all: 7 approval-gated and 7 read-only. They are dispatched from an async branch in server/tool_router.py rather than the usual sync executor path, because Playwright's async API must stay bound to the single running event loop. See Tool dispatch & executors for how that split works. The read-only inspection tools are worth reaching for before a screenshot: preview_inspect reads computed styles exactly, so it is the honest way to confirm a color or a spacing value.

Screenshots the model can actually see

A screenshot is not returned as a base64 blob buried in JSON text. server/preview/screenshot.py captures the page as a PNG, downscales it so the long edge is at most 1280px, re-encodes it as a quality-70 JPEG, and returns a [WS_PREVIEW_IMAGE] sentinel carrying the payload and a caption. The tool executor detects that sentinel and rewrites it into a real Anthropic image content block, so the model sees actual pixels in the tool result.

The tool description nudges the model to prefer preview_console_logs, preview_network, and preview_snapshot for precise checks, and to use a screenshot for visual judgment (does this look right?) rather than for reading exact values.

Verifying the UI in the loop

These tools are not just for ad-hoc looking. They are the UI half of verification, and that is what makes "check the page, then keep fixing until it renders" feel automatic during full-stack work. There is no separate component that decides to screenshot; the behavior emerges from three pieces cooperating:

  1. The tools drive the page

    Everything above: spawn the dev server, navigate, read the console and the DOM, click and type, and capture a screenshot the model can see.

  2. The built-in verify_change tool decides to use them

    server/prompt_tools/verify_change.py has a ui_facing branch. When a change touches rendered UI, the tool tells the model to start (or reuse) the dev server, load the changed view, check preview_console_logs for errors and preview_snapshot for the expected structure, drive the changed interaction (preview_click / preview_fill) and re-read to confirm it took, and capture a screenshot as evidence, then emit exactly VERIFY PASS or VERIFY FAIL: <reason>.

  3. The goal gate makes it non-optional

    The completion gate's evaluator weights a verify_change result above the model's own prose claims (server/goals/evaluator.py). So under a goal, a turn is not judged done until a passing verify token appears: a console error or an interaction that didn't persist yields VERIFY FAIL, the gate returns not-achieved, and the model re-drives the preview and screenshots again until the UI genuinely holds up (capped at 8 blocks).

The net effect: give a goal like "make the settings page save correctly" and Whisper will keep spinning the live preview, clicking through the flow, and reading the console on its own until the page actually works, so you don't have to keep saying "check it in the browser". The same verify_change step ends a generated CI-autofix workflow, so an automated fix proves its UI before it's handed back.

Two honest limits. The check only runs when the preview tools are available, gated by the preview_tools flag and a live capability probe (preview_capability_ok() in server/preview/capability.py: Playwright importable, and Chromium installed). "Installed" means Playwright's own INSTALLATION_COMPLETE marker is present for both builds a headless launch needs, at the revisions this Playwright version pins, so a stale browser cache cannot report ready and then fail at launch. The probe runs on every call, so deleting the browsers makes the tools disappear from the catalog without a restart; if either check fails, the tools hide themselves and verify-change falls back to the CI gate (tsc, tests, build) only. (Under progressive tool disclosure the preview tools are also not in the core set, so they are advertised in the deferred index and activated via tool_search.) And in a parallel workflow, each agent that verifies UI spins its own dev server on a distinct port, fine for a few, but fanning out many concurrent browser checks is where you'd feel resource pressure.

Practical tip: phrase a full-stack goal so the UI check is the proof: "the form submits and the row appears" gives the evaluator a concrete thing to verify, where "improve the form" does not. The Goals & autopilot tutorial covers how to write goals that pin down "done".

Watching it live: the right dock

The screencast is the human-facing half. server/preview/screencast.py exposes a WebSocket at /ws/preview/{name}/screencast. When the SPA's live-preview pane connects, it ensures the browser page exists (blank if the model has not navigated yet), opens a CDP session, and calls Page.startScreencast to receive JPEG frames, which it forwards to the panel.

View-only by design

Frames flow one way. No clicks or keystrokes are forwarded back from the pane, so watching never interferes with the model driving the page. You see exactly what its browser does: a navigation, a click, dark mode, an overlay swallowing a click.

Fresh over complete

A tiny frame queue (cap 2) drops the oldest frame under backpressure to keep latency low, while every frame is acked immediately so Chromium never pauses the stream. Each viewer opens its own CDP session, so multiple watchers and the agent coexist.

The pane finds its session by polling GET /api/preview/sessions and following the latest server that is still alive and owned by the chat on screen, so starting a new one switches the pane to it, a crashed one is skipped instead of shown as a dead frame, and another chat's server never appears there. The pane's Stop and Restart send that chat's session id, so they only ever act on its own server; Stop is offered only while the pane is showing that server. The cadence adapts (src/hooks/useDockLiveWatcher.ts): every 2 seconds while a preview is live or the dock is open, every 15 seconds otherwise, and not at all while the window is hidden. Coming back to the foreground polls immediately, so the pane is current the moment you look at it.

The path lives under /ws/... deliberately: Vite's dev proxy upgrades only /ws as a WebSocket, while /api stays plain HTTP. A session that does not exist gets an accept-then-close with code 4404, so the browser sees a clean close rather than a handshake failure. See Frontend architecture for how the dock and its SSE/WebSocket runtimes are wired.

The status API and kill switch

server/preview/routes.py is a small status API for the Live pane and the Settings "Live preview" panel. The Settings panel is the user-visible kill switch for whatever the model has spun up, in any chat. It is intentionally not a full remote-control surface (the page actions above are agent tools, not REST endpoints). The same panel's enable/install flow lives in server/preview/install_routes.py.

Method + pathPurpose
GET /api/preview/sessionsList sessions and their status. Each row carries owner, the chat session id that started the preview: the Live pane uses it to show only its own chat's server, and Settings to say which chat each preview belongs to.
POST /api/preview/sessionsStart (or reuse) a session by name for the chat in session_id, resolving its command from .whisper/launch.json. Both fields are required (400 otherwise). A name another chat's preview holds is refused with 409 naming that chat. Powers the Live pane's Restart button, so a stopped dev server can come back without the assistant.
DELETE /api/preview/sessions/{name}?session_id=Stop a session; 404 if there is no such session. With session_id (the Live pane) only that chat's own preview is stopped, and another chat's is refused with 409 naming the owner. Without it (the Settings kill switch) any preview is stopped; Settings asks for confirmation first when the preview belongs to another chat.
WS /ws/preview/{name}/screencastThe view-only live screencast described above.
GET /api/preview/statusInstall-flow status for the same panel: whether Playwright is importable, Chromium is present, an install is running, and the preview_tools flag is on (server/preview/install_routes.py).
POST /api/preview/installKick off the Playwright + Chromium install on a background thread; the panel polls status until it completes and the preview_tools flag flips on. A packaged .app never pip-installs: its browsers are bundled (PLAYWRIGHT_BROWSERS_PATH), so Enable just flips the flag.
POST /api/preview/disableTurn the preview_tools feature flag back off.

Lifecycle and cleanup

Stopping a session (via the tool, the Settings panel, or a full shutdown) cancels the reader tasks, kills the dev server's process group, closes the browser context and browser, stops Playwright, and unlinks the temporary sandbox profile. PreviewManager.stop_all() tears down every session at once. Because the context is ephemeral and the profile is temporary, nothing survives a session, which keeps the preview browser cleanly isolated from your real one.
