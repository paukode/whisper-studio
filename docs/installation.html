Installation

Two ways to install on macOS: drag the Mac app out of a DMG, or clone the repository and run one script. This guide assumes no prior tooling, so it starts with Homebrew and the Xcode Command Line Tools. Budget 15 to 25 minutes the first time.

Install the Mac app (recommended)

The fastest path on Apple Silicon is the packaged app: no Homebrew, no Python, no cloning a repo. It is the same codebase as the from-source setup below, built into a native shell around the same backend and the same compiled frontend.

  1. Download the latest DMG from the GitHub Releases page.
  2. Open the DMG and drag Whisper Studio into Applications.
  3. Open it from Applications, not from the disk image.

Requirements: an Apple Silicon Mac (M1 or newer), macOS 14 or later. You still choose the model mode, set your Bedrock region, and pick a model on first run, as described in First run & verify; the app skips Steps 1 to 4 below entirely.

Release DMGs are signed with a Developer ID and notarized by Apple, so the app opens like any other Mac app, with no extra Gatekeeper step.

Mac app or source: what is the same, what differs

Both installs run the same FastAPI backend, the same compiled frontend, the same tool catalog, and the same config defaults, so a feature described anywhere in these docs behaves the same in both unless a page says otherwise. Two things genuinely differ: where files live, and Apple on-device translation, which only the native Mac shell can provide.

Install from source

Whisper Studio is one local process that serves both the API and the React SPA on a single origin. Getting there is a short chain: install two prerequisites, connect AWS (only for cloud models), clone the repo, run setup.sh, and configure the app. Click a box below to see what each step does.

Already tooled up? If brew --version and xcrun --find swiftc both succeed, and you do not need cloud models yet, skip ahead to Step 4: Get the code and run. Otherwise start at Step 1.

Step 1: Install prerequisites

Two things have to be present before setup.sh can do its work. The script installs the rest (Python 3.13, Node, Git and the AWS CLI when missing, ffmpeg, llama.cpp).

ToolWhyCheck
HomebrewSupplies Python 3.13, and Git and the AWS CLI when they are missingbrew --version
Xcode Command Line ToolsThe Swift compiler for the capture helper, and Git to clone the projectxcrun --find swiftc

First install Homebrew (skip this if brew --version already works):

/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

Do not skip the two eval lines. When the installer finishes it prints two eval commands that add Homebrew to your PATH. Run both, then close and reopen Terminal. Without this, the very next command reports brew: command not found.

Then install the Xcode Command Line Tools (skip this if xcrun --find swiftc already prints a path):

xcode-select --install

Python and Node.js are handled for you. setup.sh installs python@3.13 from Homebrew when it is missing and builds the project venv/ from it, then installs the Node version pinned in .nvmrc inside that venv using nodeenv. Your default python3, any system Node, and your shell files are never changed.

Step 2: Connect AWS

Cloud chat (Claude or GPT) and voice mode run on Amazon Bedrock, so they need AWS credentials. Skip this step if you will use only on-device models. setup.sh installs the AWS CLI when it is missing; you can run this step after Step 4. Run:

aws configure

It prompts for an access key ID, a secret access key, a default region, and an output format. For the full walk-through of creating keys and profiles, see the AWS CLI configuration docs. SSO profiles (aws sso login) and a Bedrock API key in AWS_BEARER_TOKEN_BEDROCK work too.

Regions must match. Whichever region you type here is where Claude must be enabled in your account. Set the same value as the Bedrock Region in Settings later. A mismatch is the most common first-run error (see Troubleshooting). You also need Bedrock model access granted for the Claude models you intend to use. If you want spoken conversations, grant access to Amazon Nova 2 Sonic in that region as well: see Requirements.

Step 3: (Optional) Tavily key for web search

A Tavily key powers the web_search tool. It is optional: without one, web_search uses an Amazon Bedrock AgentCore browser MCP server if you have enabled one, and web_fetch (fetching a URL you give it) works with no key at all. Everything else (chat, transcription, the workspace tools) works regardless. You can add this now or any time later.

  1. Sign up

    Create a key at app.tavily.com. The free tier covers personal use.

  2. Export it in your shell (recommended)

    echo 'export TAVILY_API_KEY=tvly-...' >> ~/.zshrc
source ~/.zshrc

    The env var overrides any value stored in config.user.json, so rotating the key is one export away and the secret stays out of the config file.

  3. Or paste it into Settings

    You can instead paste the key into the Settings UI. If both are set, the environment variable wins.

See Environment variables for the full list of what the shell layer can override.

Step 4: Get the code and run

There are two ways to get the project onto your machine. Both finish with one command that builds and serves the app, so pick whichever suits you.

Option A: Clone with Git (for developers)

Clone the repository, enter it, and run the setup script:

git clone https://github.com/paukode/whisper-studio.git
cd whisper-studio
bash setup.sh

Option B: Download the ZIP (no Git needed)

If you would rather not touch the command line to get the code, download the project as a ZIP and run the same script.

  1. Download

    On the GitHub repository page, use Code → Download ZIP and save it (for example to your Downloads folder).

  2. Extract

    Double-click the downloaded .zip in Finder. It expands into a whisper-studio-main folder.

  3. Run setup.sh

    Open Terminal, go into that folder, and run the script there. The script uses paths relative to the folder it runs in, so it must start inside the project folder:

    cd ~/Downloads/whisper-studio-main
bash setup.sh

    The script runs and prints the URL when the app is ready.

From here on both options are identical: the rest of this guide applies either way.

What setup.sh does, step by step

On a first run the script works through the whole provisioning pass in this order. Every noisy install step logs to setup.log and prints a single progress line; if a step fails, the tail of that log is printed on the terminal so you do not have to go find it.

  1. Checks the machine and the prerequisites

    It stops on anything but macOS 14 or later on Apple silicon, and when WHISPER_HOME or WHISPER_USER_DIR is exported (a source install keeps its data in the checkout). Before it installs or deletes anything it checks Homebrew, the Xcode Command Line Tools, curl, and lsof, and lists every unmet item in one pass.

  2. Creates the venv and installs Python deps

    Installs python@3.13 from Homebrew when it is missing, builds an isolated venv/ from it, and installs from requirements.txt (ripgrep comes from there). The Python must be an arm64 build whose SQLite can load extensions, because vector search uses sqlite-vec; setup stops with an error otherwise. A kept venv gets the same checks on every run. Python packages are reinstalled whenever requirements.txt changes. Your default python3 and shell config are left untouched.

  3. Fetches Playwright Chromium

    The Playwright pip package carries no browser, so the script runs playwright install chromium for the live-preview browser tools. An existing build is reused.

  4. Installs Node inside the venv

    Uses nodeenv to put the version pinned in .nvmrc into the venv, then runs npm ci whenever package-lock.json changes.

  5. Installs the remaining tools

    git (skill and plugin cloning, the workspace Git tools) and the awscli through Homebrew, only when missing. Installing the AWS CLI does not configure it; you still run aws configure once. The pinned static ffmpeg and ffprobe builds (audio decoding) go into vendor/ffmpeg.

  6. Builds the capture helper

    Compiles the Mac app's native microphone and system audio capture code into vendor/capture/whisper-capture. The server starts it for the page, so recording in the browser works like in the Mac app. It is rebuilt only when its sources change, because macOS ties the microphone and System Audio Recording permissions to the program.

  7. Builds the frontend

    In production mode (the default) it runs npm run build, so the backend can serve the compiled bundle. --dev skips the build and starts Vite instead.

  8. Seeds your config on a fresh install

    When there is no config.user.json, it calls the same seed_user_config() the packaged app runs on its first launch. That writes a config.user.json holding the first-run defaults: local mode, with the on-device index backends recorded for later. An existing config.user.json is never read or changed. An old config.json is not read; the script prints a note about it.

  9. Installs the on-device serving runtime

    The llama.cpp build that server/local/llama_pin.env specifies (the llama-server binary), in all modes. It is the same release build that the Mac app bundles. The script installs it into vendor/llama, checks its checksum, and installs it again when the file specifies a different build. If you install a model from Discover after this step, you do not run setup.sh again. GGUF models run on llama-server; MLX models run on mlx_lm from the Python dependencies.

  10. Fetches the always-on speech models

    About 190 MB: the language-ID model (VoxLingua107) and the two speaker encoders (ReDimNet2, the default, and ECAPA, the one you can select instead). Every transcription path needs them and the Mac app ships the same three inside its bundle, so a source install matches. The step is idempotent, and a failed fetch stops the script.

  11. Starts the backend and opens the app

    It uses port 41430 (or the nearest free port within 5 either way, and stops with an error if all are taken), starts python -m server.main, waits up to 90 seconds for /health, prints the URL, and opens it in your default browser. In --dev it also starts Vite on port 41460 (searched the same way) and points you at that instead. Press Ctrl+C to stop.

No chat, transcription, or index weights are downloaded by setup. Apart from the three always-on speech models above, every model arrives on demand with an in-app progress banner, exactly like the Mac app's first launch: the transcription engines on your first recording, the on-device index weights (Qwen3 embed and rerank, GLiNER, about 5 GB) on your first index build in hybrid or local mode, and chat models when you install them from Settings → Models → Discover (a fresh install ships none).

Subsequent runs are fast. Each install step checks what is already there and skips it when it matches: Python packages against requirements.txt, npm packages against package-lock.json, and the pinned ffmpeg, llama.cpp, and capture helper builds. A plain bash setup.sh then mostly rebuilds the frontend and serves it.

setup.sh flags

Flags fall into two groups: what to reinstall and how to serve. With no flags you get production serving in the mode your config already has, or local mode on a fresh install.

FlagEffect
--newDelete venv/, node_modules/, static/dist/, and vendor/, then reinstall them. pricing.json (your rate overrides, if any) is backed up with a timestamp and removed, so rates come from pricing.example.json. config.user.json is never touched.
--devDevelopment mode: run the backend plus the Vite dev server with hot-module reload, on port 41460 (or the nearest free port). Open the Vite URL, not the backend; the script opens it for you. Mutually exclusive with --prod.
--prodProduction mode (the default): build the frontend and serve it from FastAPI. No Vite, no HMR.
--no-openDo not auto-open the browser (also honored via the NO_OPEN=1 env var). Useful for SSH or headless sessions.
-h, --helpShow all options and exit.

The model mode is not a flag: a fresh install starts in local mode, the same first-run default as the Mac app, and you change it under Settings → Model mode. The --dev and --new flags combine, for example bash setup.sh --new --dev. Any other argument is rejected with a pointer to --help.

Two environment variables are worth knowing here. NO_OPEN=1 does the same as --no-open, and HOST=0.0.0.0 binds the backend to your LAN instead of localhost. The default bind is 127.0.0.1 on purpose: read Security model before you change it.

Model modes

Model mode controls where indexing and retrieval run, and which chat models the picker offers: Local only on-device models, Cloud only Bedrock models, Hybrid both. You change it any time under Settings → Model mode (changing it prompts a reload so the app re-initializes).

ModeEmbeddingsRerankerEntity extractionOn-device weights
CloudCohere Embed v4 (Bedrock)Cohere Rerank 3.5Claude Haikunone (lean install)
Hybridper-capability pickper-capability pickper-capability pickdownloaded on first index build
Local (first-run default)Qwen3 (on-device)Qwen3 RerankerGLiNER~5 GB index stack on first index build; chat models installed from Discover

The mode alone ships no on-device chat model. To chat locally, install one first from Settings → Models → Discover, which lists a recommended set (Gemma 4 12B, Gemma 4 Coder, Qwen3.5 9B, Ministral 3 14B) and grades each against your machine's memory before you download. Until you install one, the picker in local mode shows an install hint, because Local mode offers and runs only on-device models and refuses cloud calls. To chat on Bedrock instead, switch the mode to Hybrid or Cloud.

Each embedder keeps its own index. Switching modes never rebuilds the other backend's index, so you re-index a folder once under a given backend to search it there. Cohere embed and rerank run in the Bedrock Region you set, like chat (embed through its global profile). Transcription is always on-device (Whisper or Parakeet) in every mode.

For the full picture of how each backend is wired, see Model modes and the architecture page Model backends & modes.

Step 5: Configure in the app

Open the URL the script printed (usually http://127.0.0.1:41430). A one-time notice explains the three model modes and tells you that you are in Local mode; dismiss it, or let it take you straight to the Model mode tab. For Claude or GPT, set the mode to Hybrid or Cloud. To stay on-device, install a model from Settings → Models → Discover and skip the region. Then click the gear icon, go to Access and usage → Keys and permissions → API keys, and fill in:

Bedrock Region
The same region you used in aws configure, where Claude is enabled. The shipped default is us-east-1.
Tavily API Key
Only if you did not set the TAVILY_API_KEY environment variable in Step 3.

Click Save. The chat model is not a Settings field: pick it from the model chip in the composer toolbar, or with /model. Then type hello in chat. If the answer streams back, the install is verified.

Transcription needs no setup. The speech model auto-downloads on your first recording and runs entirely on your machine. There is nothing to configure to record; the Canary translator downloads the same way the first time it translates.

Update to a new release

The app checks GitHub for the newest release. It does this when it starts, and at most a few times each day. The check sends no user data. If the check fails, for example with no network, the app shows nothing.

When your version is older than the newest release, a notice shows below the header: A newer version of Whisper Studio is available, with the new version number.

  • Click Update to open the release page in your default browser. Download the new DMG from that page and install it as in Install the Mac app.
  • For a source install, the notice also shows the commands to update. Run git pull, then bash setup.sh, in the project folder.
  • Click Dismiss to hide the notice for that version. A later release shows the notice again.

A build from source with commits after the newest release is not older, so it shows no notice. The notice only gives information. It does not change your settings or permissions.

Where settings live

Your settings live in config.user.json (in the checkout for a source install, under ~/.whisper for the Mac app). It is gitignored and holds your Tavily key, region, and anything else you change. It is not a copy of the template: config.example.json stays live as a read-only system layer beneath it, so shipped defaults and new catalog models reach you with no sync step, and your file carries only your own deltas. The TAVILY_API_KEY environment variable overrides everything, and a per-project .whisper/settings.json sits between them. Startup never changes config.user.json. An old single-file config.json is not read; the app shows a notice when one is present. See Configuration for the full layer model.

Import an existing Claude Code or Codex project

If you are coming from Claude Code or the Codex CLI, you do not have to re-create your project setup by hand. Connect the workspace, open Settings → Import project, and point it at the project. It migrates:

  • The instructions file: CLAUDE.md (Claude Code) or AGENTS.md (Codex) becomes the project's WHISPER.md under ~/.whisper/rules/.
  • Skills: skill folders (the SKILL.md convention both tools share) are copied into Whisper Studio's app-wide skills directory.
  • MCP servers: .mcp.json entries (Claude Code) or the [mcp_servers] tables in config.toml (Codex) are translated into Whisper Studio's MCP configuration.

The import is copy-only: your source files are never modified, nothing it writes is executed, and it never overwrites an existing WHISPER.md, skill folder, or MCP server entry.

Troubleshooting

Most first-run problems fall into a handful of buckets. Match the symptom, apply the fix, re-run.

SymptomFix
brew: command not foundRun the two eval lines the Homebrew installer printed, then reopen Terminal.
ERROR: prerequisites are not met.Fix every item in the list the script printed (for example run xcode-select --install), then re-run.
... is not an arm64 (Apple silicon) Python or ... cannot load SQLite extensionsFollow the advice in the message: delete venv/ and re-run, or brew reinstall python@3.13.
setup.sh: Permission deniedRun it as bash setup.sh, not ./setup.sh.
npm ci network errorsYou are behind a proxy or firewall. Try another network, or npm config set registry https://registry.npmjs.org/.
Any install step failingRead the 40 lines the script prints from setup.log, or open the full log at the repo root.
AccessDeniedException / Could not invoke model in chatThe AWS user lacks Bedrock permissions, or the Claude model is not enabled in your region.
You don't have access to the model with the specified model IDRegion mismatch: the model is enabled in a different region than Settings says. Align the Bedrock Region.
The Talk button is disabledHover it: the tooltip names the reason. Usually the app is in Local mode (switch to Hybrid or Cloud), the AWS credentials are missing, or voice.enabled is off. If Talk starts but fails, check that Nova 2 Sonic is enabled in the voice region.
An on-device model fails with unknown model architectureThe llama.cpp build is older than the build in server/local/llama_pin.env. Run bash setup.sh.
Port 41430 or 41460 already in useThe script takes the nearest free port. Read the URL it actually prints.
The page says Frontend build missingThe frontend bundle is missing. Re-run bash setup.sh, or bash setup.sh --new for a clean rebuild.

When in doubt, run /doctor. Type it in the chat input for an automated AWS-credentials and Bedrock-connectivity check that reports exactly what is missing or misconfigured.
