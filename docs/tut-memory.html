Memory & WHISPER.md

Give Claude a memory that survives past the current thread, and a place to write down the standing facts about your project so you never repeat them.

Memory is on out of the box. Claude quietly records the facts worth keeping, writes a running summary of the conversation, and reads both back on later turns. Add a WHISPER.md to your workspace and it gets the project context you would otherwise re-explain every time.

There are three separate mechanisms here, and it helps to keep them straight from the start: workspace memory (durable facts that carry across sessions), session memory (a structured summary of the thread you are in), and WHISPER.md (a file you write by hand). The diagram traces how they meet in the prompt.

On by default, in two tiers

Memory is on out of the box. The underlying flags, auto_memory for the persistent memory and extraction and session_memory for the per-session summary, both default on, so everything below happens automatically without you calling any tools or running any commands. If you would rather turn it off, flip the Memory row in the "+ More" menu of the chat toolbar, or type /memory off.

Persistent memory has two tiers, so there is always somewhere for a fact to go, workspace or no workspace:

  • Global memory is cross-workspace and stays alive even in plain chat with no workspace open. It holds facts about you: preferences, role, and general feedback on how you like Claude to work.
  • Project memory is scoped to the open workspace. It holds workspace-specific facts such as goals, deadlines, and repo references.

Project memory lives under a slug derived from the workspace folder name plus a short hash of its full path, so two projects named alike still keep separate memories and never bleed into each other. Global memory sits apart from all of them, shared across every chat.

Workspace memory: durable facts

Workspace memory is a small set of Markdown files that persist across every session in a project. They live in memory/<workspace-slug>/ under the data directory (see Where it all lives) and are pulled into prompts on demand. Each file carries YAML frontmatter (a name, a one-line description, and a type) followed by a short Markdown body. An index file, MEMORY.md, lists them one line each.

Not everything is worth remembering. The post-turn review is deliberately selective, and it saves into a closed set of four types:

TypeWhat it captures
userWho you are: preferences, role, expertise.
feedbackCorrections and guidance on how you want Claude to work.
projectProject context, goals, and deadlines not already in the code.
referencePointers to external systems and resources.

It deliberately does not save things that are already recoverable from the codebase: architecture and code patterns (read the code), git history (read the log), or one-off debugging fixes (the fix is already committed). It also refuses a few categories that would harden into bad habits: environment problems you can fix yourself (a missing binary, an unconfigured credential), claims that some tool "does not work", errors a retry resolved, and narratives of a single task. The point is to remember what only you can tell it, not to duplicate the repository.

The post-turn learning review

Memories are written by a review that runs in the background after a turn, roughly every third turn, and never blocks your reply. The review does not re-send a summary of the chat. It replays the turn you just had (same system prompt, same tools, same messages) with one extra question appended: what here is worth remembering? Because everything before that question is already in the prompt cache, the review is cheap, and it reads the whole conversation instead of an excerpt.

The review can only touch the memory store, your skills, and read-only workspace files, so it can never continue or redo your task. It writes two kinds of thing:

  • Memories when you revealed a durable fact about yourself, your preferences, or the project.
  • Skills when you corrected a workflow or a repeatable procedure emerged. Memory holds facts that apply everywhere; a skill holds how to do one class of task. See Skills.

If the model already wrote a memory itself during the turn, the review stands down for that turn so the two never fight over the same file.

How memory is recalled

Memory is read back on demand, not dumped wholesale into every prompt. On a new query the system scans the memory files for a manifest. If there are five or fewer files, it simply loads them all. If there are more, it runs a quick side-query on Claude Haiku that ranks the manifest against your current question and picks up to five relevant files. That keeps the prompt lean: only what is likely to matter is injected. On-device (local) turns skip the ranking side-query to stay fully offline and just take the most recent memories instead.

Which model does that ranking is yours to choose. The auxiliary_models setting routes side tasks like this one to a model of your choosing; leave it alone and recall stays on Haiku, the cheapest option. See Settings & config keys.

Session memory: a running summary

Session memory is a different animal. Rather than durable cross-session facts, it summarizes the conversation you are in right now, so a long thread stays coherent without the model re-reading every earlier turn. It is a single Markdown file with four fixed sections:

SectionContents
## GoalsWhat you are trying to accomplish this session.
## DecisionsKey choices made along the way.
## ContextImportant background that has been established.
## BlockersIssues hit or problems still unresolved.

The summary is written incrementally by a background agent and injected into later turns wrapped in a <session-memory> block. Because it is a compact digest rather than the raw transcript, a thread that has run for hours can resume without paying to re-read everything.

When it updates

The update runs as a background task after a turn, and only once the conversation has grown enough to be worth re-summarizing. Cloud sessions wait for both a large size threshold and some tool activity before updating; on-device sessions summarize far more often (every few turns) and on the local model itself, since local chats often have no tools to gate on. Either way it never blocks your reply, and if the summary fails it is simply skipped rather than disrupting the chat. For the exact thresholds and the injection format, see the architecture page.

Session memory and workspace memory are stored separately. Workspace memory carries facts between projects' sessions; session memory is a digest within one thread. You do not have to choose, both run at once when memory is on.

WHISPER.md: project context you write

Everything above is automatic. WHISPER.md is the opposite: it is a file you author, dropped in your workspace root, for the standing facts about a project that you want Claude to have on every turn. If you have used the Claude Code CLI, it is the same idea as CLAUDE.md. Unlike recalled memory, which is selected per query, the root WHISPER.md is loaded on every chat turn.

It is a tree, not one file. The root file is the project overview and always loads. You can also drop a WHISPER.md inside a subdirectory for rules that only matter there, and it loads only on turns that actually concern that directory; the rest are announced by path so Claude can open one when it turns out to be relevant. That way the gotcha about your auth middleware costs nothing on the turns that never touch it.

Good things to put in it:

  • How to run, build, and test the project (the commands you always forget to mention).
  • Conventions you care about: style rules, naming, directories that are off limits.
  • Domain vocabulary and the shape of the codebase, so Claude does not have to re-derive it.
  • Standing instructions: "always branch before committing", "never touch the generated files".

You can edit it two ways:

  1. The in-app editor

    Open Project memory from the "+ More" menu in the chat toolbar and edit WHISPER.md in place. This is the quickest path and keeps you in the app.

  2. Any editor

    It is just a file in your workspace root, so the Monaco editor in the workspace IDE, or any external editor, works fine. Save and the next turn picks it up.

If your repo already has an AGENTS.md

You do not have to convert it. An AGENTS.md at the workspace root is read live, alongside WHISPER.md, and labelled in the prompt as instructions maintained for other coding tools. Where the two disagree, WHISPER.md wins, and the app says so in the prompt rather than leaving the model to guess from ordering. If there is no WHISPER.md, the AGENTS.md simply takes its place. Deeper in the tree, a directory's WHISPER.md shadows a sibling AGENTS.md outright: one instructions file per directory.

Keeping both files in sync by hand is not required, and is usually the wrong move: put the shared rules in AGENTS.md and only the Whisper Studio specifics in WHISPER.md.

Keep WHISPER.md short and stable. It is read on every turn, so it costs input tokens each time. Put durable, always-true facts here and let the automatic memory system handle the things that change from session to session.

The memory tools

Claude does not only read memory passively. During a turn it can operate on the store directly through four tools, so it can look something up mid-task or record a fact the moment you state it:

ToolWhat it does
memory_readRead a memory file from the workspace store to recall stored information.
memory_writeCreate or overwrite a memory file (with name, description, and type), and update the MEMORY.md index.
memory_listList memory files with their type, description, and modification date.
memory_deleteDelete a memory file from the store.

These are just tools, so they follow the same rules as any other. If you want to see the full catalogue and how tool permissions work, see Agent tools and Permissions & approvals.

Viewing and curating memory

You do not have to dig through files on disk to see what Claude has remembered. Open the Memory Viewer from the "+ More" menu in the chat toolbar, under Memory files. It lists both tiers side by side and lets you read and edit any file, delete ones that no longer apply, and promote a project memory up to global when a fact turns out to matter everywhere. The MEMORY.md index is read-only, since it is regenerated for you after every change.

The store also tidies itself. Roughly once a day, and only once a tier has seen a few sessions, a consolidation pass merges duplicate files, fixes facts a later session contradicted, and deletes entries that no longer earn their place. You do not trigger it and it never runs twice at once. The architecture page has the thresholds.

Memory also announces itself as it works. When the review saves or removes something after a turn, a small toast appears with the counts, for example "Memory updated: 2 memories saved, 1 removed", or "Skills updated: 1 skill updated" when the change landed in a skill instead. A turn that pulled memories into the prompt says so too, with a "Recalled 3 memories" toast. Toasts only appear for the session you are looking at, and they are not kept in the notification bell.

Try it

The fastest way to see memory work is to tell Claude something durable, start a fresh chat, and check that it remembers:

  1. Check memory is on

    It is on by default; confirm the Memory row in the "+ More" menu shows On (or type /memory status).

  2. State a preference

    Tell Claude something worth keeping, for example how you like commit messages written, or which package manager the project uses.

  3. Keep working, then start a new session

    Have a normal exchange so the review has something to save, then open a fresh chat in the same workspace. The review runs about every third turn, so give it a couple of exchanges.

  4. Check the recall

    Ask a question that touches that preference. Claude should apply it without being reminded, because the fact was recalled from workspace memory.

Peek at the project memory folder (see Where it all lives) and you will see the files it wrote, each with its frontmatter and body, plus the MEMORY.md index.

Where it all lives

These are plain Markdown files you can open, edit, and back up. They sit under the data directory: ~/.whisper/data/ in the Mac app, and data/ at the repo root in a source checkout.

memory/<workspace-slug>/
Durable project (workspace-scoped) memory: topic files plus the MEMORY.md index.
global_memory/
Global (cross-workspace) memory: user and feedback facts that apply everywhere, including plain chat.
session_memory/<session-id>.md
The running summary of one conversation.
<workspace>/WHISPER.md
Project context you write; the root file is loaded on every chat turn.
server/memory/
The memory subsystem: the post-turn review, recall, session summaries, consolidation, and tools.
