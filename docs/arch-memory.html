Memory system

Whisper Studio carries context across turns and across sessions with three distinct stores: per-session memory that summarizes the conversation so far, persistent memory that survives every session in a global and a per-project tier, and a hand-written WHISPER.md for project context. All three are assembled into the system prompt before the model is ever called.

There is no single "memory blob". Each store has its own file layout, its own update cadence, and its own wrapper tag in the prompt. Writing happens after a turn as a fire-and-forget background task; recall happens before a turn to pick what the model reads. Click a box in the diagram to trace how a store feeds the next turn.

Every data/ path on this page resolves through data_root() in server/infrastructure/paths.py: ~/.whisper/data/ in a packaged install, the repo's own data/ in a dev checkout, or whatever WHISPER_DATA_DIR / the data_dir config key names. Memory is user data, so it lives under the user root, not under storage/.

Three kinds of memory

It helps to keep the three straight from the start. They differ in scope, in who writes them, and in how they are wrapped when injected.

StoreScopeWritten byPrompt tag
Session memoryOne conversationBackground summarizer<session-memory>

Session memory

Session memory (server/memory/session_memory.py) is a single markdown file per conversation with four fixed sections: Goals, Decisions, Context, and Blockers. It lives at data/session_memory/<session_id>.md and is meant to answer one question: if you resume this conversation later, what does the model need to pick up where it left off?

When it updates

After each turn, maybe_update_session_memory() runs in the background. It tracks, per session, the character count at the last update and the message index it last processed, then decides whether an update is due:

  • Character growth. Characters added since the last update must cross a threshold: TOKEN_THRESHOLD_CHARS (200,000 chars, roughly 50K tokens) for cloud models, or LOCAL_TOKEN_THRESHOLD_CHARS (6,000 chars, a few turns) for on-device models.
  • Tool activity (cloud only). Cloud sessions additionally wait for at least TOOL_CALL_THRESHOLD (10) tool_use blocks since the last update. Local chats often have no tools, so the character threshold alone gates them.

When both applicable guards pass, the summarizer runs against the last 30 messages (each capped for the excerpt), writes the new markdown, and the per-session counters advance. The whole file is capped at MAX_TOTAL_CHARS (12,000 chars) and truncated in code if the model overshoots; the 2,000-char per-section limit (MAX_SECTION_CHARS) is instructed to the model in the prompt but not separately enforced.

Who does the summarizing depends on the model. Cloud turns use the memory_extractor agent (see Sub-agents); on-device turns run the summary on the local model itself, on its own executor thread, so a local conversation's memory never leaves the machine. Either way, a failed summary degrades to no update rather than disrupting the chat.

How it enters the prompt

On the next turn, get_session_memory_context() reads the file and wraps it:

<session-memory>
## Goals
- Ship the memory docs page and wire it into nav

## Decisions
- Use the real prompt tags, not the outline's placeholders

## Context
- Cloud path uses Haiku for recall; local path stays offline

## Blockers
(none)
</session-memory>

If the file does not exist yet, the wrapper is empty and nothing is injected.

Persistent memory: two tiers

Persistent memory (server/memory/memdir.py and server/memory/recall.py) survives across sessions. It is a two-tier store, and every memory belongs to exactly one tier:

TierLocationAlive whenHolds
Globaldata/global_memory/Always, including plain chat with no workspace openUser preferences, role, cross-project feedback
Projectdata/memory/<workspace-slug>/A workspace is open (slug = sanitized basename plus a short hash of the workspace's realpath, so two folders both named app never collide; legacy basename-only dirs are migrated)Goals, deadlines, repo-specific references

The global directory deliberately sits outside data/memory/ so it can never collide with a workspace slug. Both tiers share the same on-disk layout:

MEMORY.md
A one-line-per-entry index of that tier's topic files, auto-generated from their frontmatter after every write or delete. Capped at 200 lines and 25 KB when loaded; if it exceeds either limit it is truncated and a warning is appended telling the model to move detail into topic files.
<topic>.md
Per-topic markdown with YAML frontmatter (name, description, type). The type is a closed taxonomy: user, feedback, project, or reference.
.cursor.json
Extraction bookkeeping keyed by session id: a sessions map of per-session cursors (not a single "last message index") plus a turns map of per-session throttle counters, each capped in size. Persisted in the global tier so a session keeps its place even when it connects or disconnects a workspace mid-life, and a restart resets neither the cursor nor the throttle.
.dream_meta.json
Per-tier consolidation bookkeeping (last run time and turn-end count). See consolidation below.

Recall: choosing what to inject

Because the two tiers together can accumulate many topic files, they are not all injected. Before each turn, recall_memory_context() scans both live tiers and chooses which files are relevant:

  1. Scan both tiers

    List the topic files across global and project. If there are none, nothing is injected.

  2. Few files? Take them all

    At or below MAX_SELECTIONS (5) files, every file is returned and no model call is made.

  3. Local turn? Stay offline

    For on-device models, the ranking side-query is skipped and the most recent files (up to 5) are returned. This trades smart ranking for isolation.

  4. Otherwise, rank with a side-query

    A cheap model receives a manifest of file names, types, and descriptions plus the user query, and returns up to 5 filenames as JSON. If it fails, recall degrades to the most recent files.

The side-query is deliberately tiny: MAX_RECALL_TOKENS is 256 and it runs with a single retry and short timeouts. It then reads the selected files, always prepends each tier's MEMORY.md index, and tags each entry with a freshness note ("today", "yesterday", or "N days ago"). The whole block is wrapped in <memory-context>.

Which model runs it is configurable. aux_model_id("memory_recall") reads the auxiliary_models config map (server/infrastructure/auxiliary.py); unset, it stays on Haiku, the cheapest entry. The call site is a direct Bedrock invoke, so an on-device key is refused there and falls back to Haiku.

The selector's reply is parsed leniently. It is asked for bare JSON, but a model that wraps the object in a ```json fence is still accepted: _bare_json() strips the fence before parsing. Without that, one stray fence made every recall fail and every turn ran with no memory at all.

The post-turn learning review: writing new memories

After a turn (when the model is not asking for more tools), maybe_extract_memory() fires in the background. It runs with or without a workspace: with one the reviewer sees both tiers and routes each write by scope; without one, everything lands in global memory. It is guarded five ways:

  • Feature flag. auto_memory must be enabled. ensure_global_memory_dir() returns nothing when it is off, so the whole pipeline (and recall) short-circuits.
  • Throttle. The review runs only every DEFAULT_EXTRACT_INTERVAL (3) turns. The counter is persisted, so a short session keeps accruing toward the cadence across restarts.
  • Mutual exclusion. If the model already called memory_write this turn, the cursor advances and the review is skipped, so the model and the reviewer never fight over the store.
  • In-flight. Only one review runs per session at a time.
  • Cursor. Cursors are keyed by session id and persisted in the global tier; only messages after this session's saved cursor are considered. The cursor is claimed before the review runs, so overlapping turns cannot double-write.

The cache-parity fork

Past the guards there are two implementations, and the default is the fork (server/memory/review_fork.py). Instead of re-sending an excerpt of the conversation to a separate agent with its own system prompt, the fork replays the turn's own request: the same adapter, the same system prompt with the same cache breakpoints, the same tools array byte for byte, the same messages, plus one appended user message asking what should be remembered or encoded as a skill (build_learning_review_prompt()). Every token before that message is a warm prompt-cache read, and the reviewer sees the whole conversation rather than a lossy excerpt.

The fork is deliberately boxed in:

  • Only ALLOWED_TOOLS may run: the four memory tools, skill_list and skill_manage, and the read-only workspace reads (ws_read_file, ws_grep, ws_glob). Anything else the model calls gets a refusal tool_result.
  • At most MAX_ROUNDS (6) rounds.
  • It never touches the live conversation and never emits SSE. Its usage is recorded against the session, at turn numbers counted from REVIEW_TURN_BASE (900), so the cost shows up in the Costs panel instead of hiding.
  • The review message tells the model plainly that it is not from the user, its reply is not shown, and it must not continue, redo, or critique the task.

Routing is decided by _fork_route(): the learning_review_fork flag must be on (it is by default), the provider must be forkable (Anthropic or OpenAI), and auxiliary_models.learning_review must be unset, "main", or the turn's own model. Naming a different model there is read as "run the cheaper review on that model", which the fork cannot do, so it falls back to the excerpt path.

That fallback is the original memory_extractor agent: an excerpt of the new messages (last 20, truncated) plus a per-tier manifest of existing memories, told to save what would be valuable in future sessions, at depth=1 so it cannot recurse.

Memories and skills

The review writes two kinds of thing. Durable facts go to memory. A repeatable procedure the user corrected or walked through goes to a skill via skill_manage, in a fixed preference order: patch a skill used this turn, else patch an existing skill that covers the class of task, else add a references/ file under one, and only create a new class-level skill when nothing fits. That half is gated by the skill_self_improvement flag (on by default); see Skills.

Both halves share one set of writing rules (LESSON_RULES and DO_NOT_CAPTURE in server/memory/prompts.py), so the stores converge on rules instead of incident narration: procedure first, a pitfall stated as an imperative with its mechanism, no ticket numbers or quoted user text, the same lesson learned twice strengthened in place rather than duplicated. And a hard "never save" list: environment failures the user can fix, negative claims that a tool "does not work", transient errors a retry resolved, one-off task narratives, and dead ends dressed up as guidance. If nothing qualifies the reviewer is told to reply exactly "Nothing to save".

Local-model turns feed this pipeline too: the local path fires the same maybe_extract_memory() and record_and_maybe_dream() hooks after a turn. Both skip gracefully when model_mode is local (fully offline), because the extractor and consolidator agents run on cloud models; in hybrid or cloud modes a local chat gets the same two-tier extraction and dream cadence as a cloud chat. It always takes the excerpt path, never the fork: the local path passes no ReviewFork, and supports_fork() only accepts the Anthropic and OpenAI adapters. (Session memory's local story is different again: there the summary runs on the local model itself.)

Neither path stores what the environment already teaches: code patterns, git history, and one-off debugging fixes are derivable from the repository, and WHISPER.md and AGENTS.md are already in the prompt. What gets saved is what only the user can supply: preferences and role, working guidance, project goals and deadlines, and pointers to external systems.

WHISPER.md

WHISPER.md is markdown you author by hand, loaded on every turn by get_whisper_md_context() in server/whisper_md.py. It is the Whisper Studio analogue of CLAUDE.md: durable project context that you write rather than have the system extract. It is injected inline as a [WHISPER.md - project-specific instructions] block.

It is a tree, not a single file. The root WHISPER.md at the workspace top always loads (capped at ROOT_MAX_CHARS, 12,000 characters). Directory-scoped WHISPER.md files deeper in the tree (up to MAX_DEPTH 4, at most MAX_SCOPED_FILES 25) load only when the turn's question concerns their directory, each capped at SCOPED_MAX_CHARS (6,000 characters); the rest are announced by path so the model can read them with ws_read_file when needed. Truncation is honest: a capped file gets a note appended telling the model to read the rest with ws_read_file.

AGENTS.md, the instructions filename other coding tools maintain, is honored live as a read-only supplement rather than imported once and left to go stale. At the root it is loaded alongside WHISPER.md under an explicit precedence note ("where this conflicts with WHISPER.md above, WHISPER.md wins") and given the scoped budget; with no WHISPER.md present it takes the root budget instead. It is skipped entirely when its text already appears verbatim inside WHISPER.md, which is the post-import state, so the same text is never billed twice. In a scoped directory a WHISPER.md shadows a sibling AGENTS.md outright: one instructions file per directory.

Unlike the other two stores, it is fully under your control. The in-app Project Memory dialog is backed by a small CRUD API:

EndpointAction
GET /api/whisper-mdRead the current file (returns content plus whether it exists).
PUT /api/whisper-mdSave new content to the workspace root.
DELETE /api/whisper-mdRemove the file.

Because it is read every turn and never summarized, keep it tight. It is a good home for stable conventions (coding style, deploy steps, domain vocabulary), not for transient task state.

Assembling all three

All three stores are resolved in the chat endpoint (server/chat/routes.py) and handed to the prompt builder in server/prompts/__init__.py, which owns section ordering. Session memory is placed before workspace memory (it carries a higher-priority slot), and WHISPER.md is its own project-instructions section. When prompt caching is on, these dynamic sections sit after the cacheable static prefix so they do not invalidate the cache. See Chat & tool orchestration for where this fits in a turn, and Settings for the caching flag.

Memory tools

Beyond the automatic pipeline, the model can manage persistent memory directly during a turn via four tools defined in server/memory/tools.py. They are registered through the executor, not exposed to the model as HTTP routes. Each read, write, and delete takes an optional scope parameter (global or project) that routes to the right tier; without it, a write updates a matching file in place or routes a new file by type, and reads and deletes search the project tier first, then global.

ToolWhat it does
memory_readRead a memory file by relative filename (optional scope).
memory_writeCreate or overwrite a topic file (frontmatter is added automatically) and rebuild the index (optional scope).
memory_listList every memory file across both tiers with type, description, and modification date.
memory_deleteDelete a memory file (optional scope).

Every write, from these tools or the extraction agent, is first screened for secrets by server/memory/secret_scanner.py (check_and_block()): if a credential is detected the write is blocked and the content is never persisted. See Agent tools for the full catalogue of tools the assistant can call.

Memory viewer and the /api/memory router

People manage memory through a small REST router (server/memory/router.py, mounted at /api/memory), which backs the in-app Memory Viewer modal (src/components/settings/MemoryViewerModal.tsx). Open it from the "+ More" menu in the chat toolbar via Memory files. It carries the same guards as the tools: path-traversal checks, secret scanning on every write, a read-only MEMORY.md, and an index rebuild after every mutation.

EndpointAction
GET /api/memoryList both tiers: file manifests plus each tier's index (project only when a workspace is open).
GET /api/memory/fileRead one file's raw content, by scope and filename.
PUT /api/memory/fileSave raw file content; secret-scanned, then the tier index is rebuilt.
DELETE /api/memory/fileDelete a file and rebuild that tier's index.
POST /api/memory/promoteMove a file from the project tier up to global, so every project can use it.

The review and consolidation finish after the chat stream closes, so their results surface over the session's long-lived event channel rather than inline in the turn. The payload carries writes, deletes and skills counts, which the client turns into a toast: "Memory updated: 2 memories saved, 1 removed", or "Skills updated: 1 skill updated" when only a skill changed. Recall gets its own variant, "Recalled N memories", when a turn injected memory context. Toasts are suppressed for background sessions and are not persisted to the notification bell, since per-turn memory telemetry would flood it.

Consolidation (dream)

Over time a tier can drift: duplicates pile up, facts go stale, the index grows past its cap. A consolidation pass in server/memory/dream.py periodically distills each tier independently. The post-turn hook record_and_maybe_dream() bumps a per-tier counter after every turn and runs the pass when a tier is due: at least MIN_HOURS_SINCE_LAST (24 hours) and MIN_SESSIONS_SINCE_LAST (5 recorded turn-ends) since that tier's last run, with a PID-based lock (stale after one hour) so two consolidations never run at once.

When it runs, a single agent works through four phases: Orient (list files, read the index), Gather (find stale, contradicted, or overlapping entries), Consolidate (merge related files, update facts, delete superseded entries), and Prune (delete topic files that no longer earn their place). The agent never rewrites MEMORY.md itself - the index regenerates deterministically after every write or delete, capped at 200 lines. Think of it as the persistent-memory counterpart to how a single session's memory is periodically resummarized.
