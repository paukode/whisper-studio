Sandbox & security

The OS sandbox is the boundary you should trust last and most. Everything in front of it is layered defence that catches the easy cases before code ever reaches the sandboxed subprocess.

Whisper Studio runs shell commands and executes code on your machine, so the interesting question is not "does it have security" but "which layer is a hard boundary and which just catches the obvious cases". This page walks the path a command takes, names the deny-list it runs against, and is honest about the risks that are accepted on purpose. The diagram below traces that path left to right - click a box to light up what it reaches.

The sandbox, and everything it wraps

Outside Bypass, every shell and code-execution path runs under macOS sandbox-exec(5). server/sandbox.py generates a temporary .sb profile and runs sandbox-exec -f profile /bin/sh -c "...". It has three entry points, and each one uses the same profile generator:

Entry pointKindUsed by
run_sandboxedBlocking run, output capturedrun_python, aws_cli, hook commands, goal quality gates, and office_script.
popen_sandboxedNon-blocking PopenEvery ws_run_command (approved and read-only), its 30 s background handoff in server/tasks/handoff.py, and every background shell task.
build_pty_sandbox_wrapWraps a long-lived PTYThe hidden terminal_run shell and preview dev servers.

popen_sandboxed gives its child the same scrubbed environment, the same egress proxy variables, and the same network rules as run_sandboxed. The interactive PTY runs under the identical deny-list as a one-shot command. In workspace-write mode, the write root of that shell is the connected workspace, not the folder where the shell starts. With no workspace, the shell writes only in its scratch folder and the temporary folders.

No sandbox, no run. When sandbox-exec cannot be used, all three entry points raise SandboxUnavailableError and nothing runs, in every write mode. There is no unsandboxed fallback. Bypass is not a fallback: it does not use the sandbox at all (see Bypass runs with no sandbox).

Bypass runs with no sandbox

In Bypass (bypassPermissions), commands run with no sandbox-exec and no write limits. This is the same as the bypass mode of Claude Code. All other modes keep the sandbox. Nothing changes for them.

The three entry points read a scope in server/security/bypass_sandbox.py. When the scope is on, they run /bin/sh -c "..." directly. They write no profile, and they do not need sandbox-exec. The environment does not change: the GitHub tokens stay removed, and the egress proxy variables and the scratch package caches stay as they are.

These commands run with no sandbox in a Bypass turn:

  • ws_run_command, also its read-only path, its 30 s handoff, and its background shells.
  • The hidden shell of terminal_run and the interactive shell of terminal_send. A shell that a confined turn opened is closed and opened again for a Bypass turn, and the other way around.
  • run_python, aws_cli, and office_script.
  • Hooks (SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop) and goal quality gates.
  • The commands of the subagents and workflows that the Bypass turn starts. A workflow keeps the scope of the turn or the person that started it.
  • A command on an approval card that a Bypass turn made.

These runs keep the sandbox: all modes other than Bypass, a scheduled cron job (also when a Bypass turn made the job), and a headless run that no Bypass turn started.

Because there is no sandbox, setuid programs such as /bin/ps run, a nested sandbox-exec runs (for example the test suite of a project that uses it), and a write outside the workspace succeeds. sandbox_permissions="danger-full-access" has no meaning in Bypass. The approval floor does not ask for it, and the executors accept it and ignore it, with no justification check. A failed command in Bypass does not get a sandbox-denial hint.

A read-only scope keeps the sandbox, also in Bypass. This applies to a read-only agent (for example a memory agent or an Explore agent) and to a call made in plan mode. Their commands run in the read-only profile, so the sandbox refuses a write that the command classifier missed. In this scope the executors refuse danger-full-access, because Bypass shows no card for it.

An approval card runs with the scope of the turn that made the card. The gate puts a server stamp on the card of a Bypass turn. When you approve the card, the app reads the stamp. It does not read the mode at the time of your click. Thus, if you change to Bypass before you approve a card from another mode, the command stays in the sandbox. The /subagent command and a workflow that you start yourself use the mode at the time you start them.

Three write modes

The deny-list above is only half the profile. The other half is how much of the filesystem the command may write, which run_sandboxed takes as a write_mode:

write_modeWhat the profile does
open(allow default) plus the secret deny block. Writes anywhere the user could write. Used only for a command that a person approved on its card. A command that a mode, a session answer, a rule, the classifier, or an agent approved runs in workspace mode.
workspaceDenies all writes, then allows back a specific set of roots: the working directory, a linked worktree's git directory and its common directory, the calling session's own scratch folder, the temp directories, and /dev, plus anything passed as write_paths (for example the AWS CLI caches). The app's own grant and config files stay unwritable, even when the tree contains them.
readonlyDenies all writes except /dev. A ws_run_command that the read-only classifier accepts runs in this mode, with no card.

Rule order in the generated macOS profile is load-bearing: the blanket write-deny comes first, the writable roots second, and the secret denies last. That ordering is what stops a workspace that happens to be your home directory from re-exposing ~/.ssh through the allow-back.

A session can write only in its own scratch folder, ~/.whisper/data/scratch/<session>. The folder of a different session is not writable. A workspace run also keeps its package caches in that folder. The sandbox sets three variables: npm_config_cache, PIP_CACHE_DIR, and UV_CACHE_DIR. Each one refers to a folder in ~/.whisper/data/scratch/<session>/cache. The default caches in the home folder are outside the writable roots, so an install without these variables fails.

The assistant does not choose those literals. run_python and terminal_run take a sandbox_permissions parameter with three values, mapped onto the modes above:

sandbox_permissionsMaps toMeaning
workspace-writeworkspaceThe default. Write inside the project, the session's own scratch folder, and the temp directories, nowhere else.
read-onlyreadonlyRun it, change nothing.
danger-full-accessopenWrite anywhere. The call must carry a justification. Asking for this raises an approval card in every permission mode except Bypass, because it is a request to drop the confinement. In Bypass there is no sandbox, so the app ignores the request with no card. A subagent or another unattended run is refused.

When a command fails under workspace or readonly, classify_sandbox_denial recognises the macOS refusal text ("Operation not permitted") so the assistant is told the sandbox refused the write rather than guessing the tool is broken.

What the sandbox actually enforces

The single most important fact about this sandbox is that it is allow-default plus deny rules, not deny-by-default. The macOS profile is literally (allow default) followed by a block of deny rules. Its main job is denial of a curated secret-store list. Writes to that list are denied in every mode. Reads are denied by default, but the permission mode can open them (see Secret reads by permission mode). Two more rules apply to a confined (workspace or readonly) command, the kind no person reviewed: it cannot connect to the app's own API port on loopback, so it cannot drive an approval to escape its confinement, and it cannot write the app's grant and config files (permissions.json, hooks.json, config.user.json, the plugins and custom agents folders, and the rest), even when its tree contains them.

That list is _DENIED_PATHS, built from the canonical definitions in server/security/sensitive_paths.py so the OS sandbox and the command validator can never drift on the shared core. It covers:

  • SSH and GPG keys - ~/.ssh, ~/.gnupg.
  • Cloud credentials - ~/.aws, ~/.config/gcloud, ~/.azure, ~/.docker, ~/.kube. Note that ~/.aws is denied for generic commands but re-allowed per-call, read-only, for the AWS tools (see below).
  • Git and package-registry credentials - ~/.git-credentials, ~/.config/git/credentials, ~/.netrc, ~/.npmrc, ~/.pypirc.
  • Browser cookies and keychains - Chrome / Chromium / Firefox / Brave / Safari profiles, ~/Library/Cookies, and ~/Library/Keychains.
  • Shell history - ~/.bash_history, ~/.zsh_history, fish history (these frequently contain pasted tokens).
  • Shell startup and login persistence - ~/.zshrc, ~/.zprofile, ~/.zshenv, ~/.bashrc, ~/.bash_profile, ~/.profile, fish config.fish, and ~/Library/LaunchAgents. A write there runs code at the next shell or login, and these files often hold exported secrets.
  • Password managers and other CLI token stores - ~/.password-store, 1Password / op, ~/.config/gh/hosts.yml, cargo, gem, terraform, doctl, netlify, and heroku credential files.
  • Absolute system secrets - /etc/shadow, /etc/sudoers, /etc/ssl/private.

One deliberate asymmetry: /etc/passwd is checked by the command validator but is not sandbox-denied, because NSS reads it on every user and group lookup - denying it in the kernel would break ordinary commands. A command that mentions it explicitly is still suspicious, so the validator keeps watching for it.

Secret reads by permission mode

The credential stores are the paths on the list above. The policy for reads of these stores is in server/security/secret_reads.py. It applies to the file read tools (ws_read_file, ws_list_directory) and to commands (run_python, terminal_run, ws_run_command):

Permission modeRead of a credential store
Bypass (bypassPermissions)Every read tool and every command reads the stores with no card. Commands run with no sandbox in Bypass, so the write deny does not apply to them (see Bypass runs with no sandbox).
Don't ask (dontAsk)Refused.
Asks first, Accept edits, Plan, AutoA person approves each read, every time. The Auto classifier never decides it, and a remembered "Yes, all" for commands never covers it.
Unattended runs (subagents, scheduled cron jobs), outside BypassRefused, because no person can answer the card. Agents and cron run in default mode, so in practice they never read secrets.

A file read of a credential store shows a secret_read approval card (category secret-read). A command asks with the tool input secret_access: true. Its card summary starts with "READS THE KEYCHAIN AND CREDENTIAL STORES:" and never offers to remember the choice for the session. On Yes, the command runs with the stores readable. Writes to them stay denied.

The executor marks every call with whether it runs in Bypass (__secret_reads__). It always overwrites the value that the model sent. The approval gate (server/tool_approvals.py) is the one place that decides the secret_access of a command. The command validator skips its sensitive-path check for a run that is allowed to read secrets.

A command that runs without secret access can fail because the sandbox hid a credential store (a Keychain error, or "Operation not permitted" on a path on the list). Then the tool result adds a hint that tells the model to run the command again with secret_access=true. This lets tools such as security find-identity, codesign, and notarytool find the login Keychain after approval.

Two shells do not follow this table. Your own visible terminal panel is not sandboxed. The interactive hidden shell of terminal_send keeps the full read and write deny-list.

macOS does not let a sandboxed command start a setuid program, for example /bin/ps or /usr/bin/top. The kernel refuses it, and no profile or permission mode changes this. When a confined command fails for this cause, classify_sandbox_denial adds a hint that names the program. The hint tells the model to use pgrep -fl, which runs in the sandbox. It does not tell the model to ask for danger-full-access.

The credential denylist

Denying a file does nothing if the same secret is sitting in an environment variable. The denylist lives in server/security/sensitive_env.py as two named sets: GITHUB_ENV_VARS (GH_TOKEN, GITHUB_TOKEN, GH_ENTERPRISE_TOKEN) and CLOUD_ENV_VARS (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN, ANTHROPIC_API_KEY, OPENAI_API_KEY, TAVILY_API_KEY), together CREDENTIAL_ENV_VARS. They are exact names, not prefixes or patterns. Two consumers apply them differently, on purpose:

  • MCP child processes get the full scrub. Every local MCP server spawned over stdio starts from your login-shell environment under the app's own (login_shell_env(), captured once at packaged startup by server/infrastructure/binaries.py), passed through scrub_credential_env, so a third-party server never inherits your GitHub token or cloud keys just because they are exported in your shell. Per-server env entries from mcp_servers.json are applied after the scrub, so a credential you deliberately configured for that server still reaches it. Remote HTTP MCP servers are not child processes and never see your environment at all.
  • Sandboxed shells get the GitHub subset only. run_python, aws_cli, ws_run_command, background shell tasks, and preview dev servers all build their environment through _merged_env, which drops GITHUB_ENV_VARS. The cloud keys are deliberately left in place: sandboxed code authenticates to Bedrock and AWS with them.

Why ~/.aws is denied, then re-allowed

run_sandboxed takes an allow_paths argument that subtracts specific entries from the deny-list for that one call. aws_cli and boto3 code inside run_python pass their cloud-credential paths through this allow_paths re-allow so authentication works, while every other secret (~/.ssh, git creds, /etc/shadow, and the rest) stays blocked for that command. aws_boto3 needs no such re-allow: it calls the boto3 SDK directly in-process, never through run_sandboxed at all, so it is restricted instead by a read-only prefix check rather than the filesystem sandbox. Every run_python script gets the re-allow, whatever the script does, so aws_cli and every run_python script can read ~/.aws (read-only). Other shells (ws_run_command, terminal_run) do not see it, unless the permission mode lets them read the credential stores.

The re-allow is read-only. The AWS CLI and boto3 run programs that files in ~/.aws name: credential_process in the configuration file, CLI aliases that start with !, and CLI plugins. A write to ~/.aws can thus become code that the next AWS calls run, also in the server process, which has no sandbox.

Thus run_sandboxed keeps each allow_paths entry read-only. It lets the run write only in its write_paths: the CLI cache ~/.aws/cli/cache and the SSO token cache ~/.aws/sso/cache. These rules come last in the profile, and a workspace that contains ~/.aws cannot make it writable. The sandbox cannot let a run create a new folder in ~/.aws. Thus the executor creates ~/.aws/cli/cache before the run.

aws_cli always runs in workspace-write mode, also after a person approves its card. Its write root is the connected workspace. With no workspace, the command starts in the home folder, but it cannot write there. It writes only in the session scratch folder, the temporary folders, and the AWS CLI caches in ~/.aws.

Accepted residual risk

Because the default is allow, two things follow directly, and both are accepted on purpose:

  • Network is unrestricted by default. Sandboxed git, npm, pip, aws, and build commands all need the network to function, so the default (permissive) tier leaves it open. Users who want less can opt into the network egress policy below.
  • Reads of non-listed secrets are not blocked. The deny-list is broad but not exhaustive - a secret file that is not on _DENIED_PATHS can still be read.

Flipping to a deny-default filesystem profile is still out of scope: it would break the tools above. This is the trade-off that makes the sandbox the boundary you trust last: it does not try to be a jail, it guarantees the high-value secret stores stay unwritable even if every layer in front of it is defeated. They also stay unreadable, unless the session is in Bypass or a person approved the read.

The network egress policy (opt-in)

Since the sandbox itself leaves the network open, an opt-in egress policy (server/security/egress_policy.py) restricts where a sandboxed command can send bytes. It is stored in permissions.json under network_policy and is off by default. You set it in Settings > Keys and permissions > Permissions > Sandbox Network Policy, which has three controls: Tier, Custom allowed domains, and Safe methods only.

TierMeaning
permissiveNo restriction, no proxy. The default.
curatedA seed allowlist of common package-registry, docs, and API domains, plus any custom_allowed_domains the user adds.
restrictiveNothing outbound except the user's own custom_allowed_domains.

Enforcement is an SNI-filtering local TCP proxy that never terminates TLS. The one handshake message every TLS client sends in cleartext, the ClientHello, carries the destination hostname in its SNI extension; the proxy parses just that, checks the hostname against the active tier's allowlist, and either relays the raw bytes transparently or refuses the connection. No key material, no decryption. The proxy is injected into run_sandboxed's environment via HTTPS_PROXY / HTTP_PROXY, which well-behaved HTTP clients honor voluntarily - so a non-permissive tier also appends (deny network-outbound (remote ip "*:443")) and "*:80" rules to the sandbox profile, forcing raw-socket traffic through the kernel boundary rather than merely asking nicely.

Two documented limitations: methods_only_safe (block POST/PUT/PATCH/DELETE even to allowed domains) can only be enforced on plaintext HTTP, since the method of HTTPS traffic lives inside the encrypted tunnel; and DNS on port 53 is neither restricted nor inspected, so DNS-based exfiltration is out of scope.

Layers in front (defence-in-depth)

Before a command reaches the sandbox, several cheaper checks catch the easy cases. It is worth being precise about which of these are real boundaries and which only raise the bar.

The command validator

server/security/command_validator.py runs a regex deny-list against each subcommand. validate_command() first strips heredoc bodies (so a Markdown table full of | pipes is not mistaken for a pipeline), splits compound commands on every unquoted ;, &, and | and their doubles, then runs every validator over each piece. The checks include:

  • Dangerous patterns - rm -rf /, mkfs, dd of=/dev/..., and redirects into /etc/.
  • Command and process substitution - backticks, <(...), and a $(...) that can contain a command the checks do not see. A $(...) can run a read-only command that passes all the checks, for example test "$(git branch --show-current)" = main, and the $(cat <<...) pattern of git commit -m. Its output cannot be the program name.
  • Environment-variable injection - references or assignments to $LD_PRELOAD, $BASH_ENV, $IFS, $PROMPT_COMMAND, and friends. IFS= read is permitted, because it sets IFS for that one read only.
  • Obfuscation - control characters, deceptive Unicode whitespace, hex/octal escapes, and ANSI-C quoting used to smuggle characters past the other checks.
  • Sensitive paths and file types - the shared deny-list plus extensions like .pem, .key, id_rsa, and filenames like .env.production.
  • In-place edits - sed -i is blocked with a nudge to use ws_write_file instead.
  • A subcommand cap - more than MAX_SUBCOMMANDS (50) chained segments is rejected to prevent CPU starvation from deeply nested pipelines.
  • The gh CLI - blocked inside the sandbox, because GitHub authentication is not available there; the message points at the dedicated GitHub tools instead.

The sensitive-path check deliberately strips quote characters rather than quoted contents, so cat '/etc/shadow' is still caught.

Deletes are read by a separate module, server/security/delete_sites.py, not by the validator. It recognises a deleting command (through wrappers such as sudo or xargs, and including find ... -delete). The approval floor asks only when a delete reaches outside the workspace and the app's own folders, whatever the permission mode. A delete by an unattended agent is refused. See the decision order.

The validator is regex-based and bypassable on its own, so it is explicitly defence-in-depth: it sits in front of the sandbox, never in place of it. Approval does not skip it: the approved command path re-runs the same validator before sandboxing, and both the sandboxed and the visible terminal_run modes run it too.

The approval pause

Risky commands do not run on the model's say-so. An ask decision pauses the whole turn on the server (in paused_sessions) and nothing executes until the client explicitly posts the action to POST /api/approval/execute, whose hub only runs registered approval executors; the turn itself resumes only when the frontend sends a new turn carrying the approved tool result. Approval is enforced server-side, which makes it a genuine boundary rather than a suggestion. See Approval & permissions for the full flow.

The AWS read-only guard

When boto3 runs inside run_python, server/executors/code.py prepends _AWS_READONLY_GUARD, which monkey-patches botocore.endpoint.Endpoint.make_request to reject any operation whose name is not read-shaped (the allow-list is list, get, describe, head, query, and similar prefixes). This catches a model that thought it was in read-only mode and would otherwise burn write rate-limits or trip an alarm. It is defence-in-depth only: user code in the same process can simply del _ep.Endpoint.make_request to undo it. The layer that actually contains the code is sandbox-exec, not this patch.

Boundary vs defence-in-depth

The render path (DOMPurify), the 127.0.0.1 default bind, the Origin and Host guard, and the full table of which layer is a boundary and which is defence-in-depth are in the Security model reference. This page covers only the sandbox mechanics.

Workspace path containment

File operations have their own boundary, separate from the shell sandbox. Every workspace file op validates its target with _ws_validate_path (server/workspace/paths.py): it calls os.path.realpath and confirms the result stays inside the connected workspace root, also blocking /dev and paths that start with //. The file tools (_ws_path_allowed) can also reach the calling session's own scratch folder, never another session's. Writes then go through an atomic _atomic_write_text (temp file plus os.replace).

The same module also owns the save-flow staging area. New standalone files (the direct save flow) intentionally land outside any workspace, so they bypass the workspace-root check via a separately audited path: stage_file_bytes writes the finished bytes into ~/.whisper/data/scratch/_staging (each entry in its own random subdirectory, garbage-collected after 24 hours), and the approval executor _do_save_to_path refuses any staged_path that fails the is_staged_path containment check - the path must resolve inside the staging root, or a forged approval payload could "move" an arbitrary readable file into a user-visible folder. See the direct save flow for the full picture.

Accepted TOCTOU residual. This is a check-then-use pattern, so in theory a symlink swapped between the realpath check and the write could redirect it. The atomic os.replace does not follow a symlink at the final path component (it replaces the link itself), so the realistic case is covered; only an intermediate directory swapped to a symlink mid-write would escape, which is contrived on a single-user local tool. An O_NOFOLLOW / fd-based write would close it fully but risks rejecting legitimate symlinked paths inside a workspace, so it is left as-is on purpose.
