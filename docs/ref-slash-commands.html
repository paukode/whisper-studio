Slash commands

Every / command available in the chat input. Type / at the start of an empty composer to see the full list inline, with argument hints and live autocomplete.

Slash commands are shortcuts the composer intercepts before anything is sent to the model. They tune the session (model, thinking depth, response length), run side tasks (a subagent, a one-off side question), or drive the UI (open Settings, clear the view, rename the session). Most take effect instantly and confirm with a small toast; a few open a dialog. They are handled client-side in src/hooks/useSlashCommands.tsx, with the list itself defined in src/components/chat/chatInputConstants.ts.

A command only fires when your message begins with /. Anything that is not a recognised command is treated as a normal chat message, so a stray slash never eats your text. Run /help at any time for the same reference inside the app.

Model & reasoning

These four commands change how Claude thinks for the rest of the session. They mirror the controls under the composer, so a command and a click stay in sync.

/model

/model <name> switches the model for every subsequent turn in this session. The valid names are the keys in your configured model list, so they track whatever you have enabled: haiku, sonnet, sonnet5, opus4.8, opus5.0, fable5.1, gpt6-astra, and the rest. On success you get a toast confirming the version label ("Model set to Sonnet 4.6"), not the raw key. Pass an unknown name and the composer replies with the usage string listing the models you can pick.

Switching to a model with a stricter data-retention policy routes through a consent screen first, so the change only lands after you confirm. See Model modes for the cloud, hybrid, and local backends behind each name.

/effort

/effort <level> sets thinking depth for models that expose it, which is every cloud model except Haiku. The palette offers low, medium, high, extra, max, and ultracode; the raw API name xhigh is accepted as an alias for extra, and the GPT-5.x models also take none. Which rungs a model actually has depends on its ladder: extra exists on Opus 4.8 and up and on Fable, while Sonnet and the older Opus versions go straight from high to max. ultracode is the top mode: it pairs the model's highest reasoning rung with dynamic-workflow orchestration (see The ultracode workflow runtime), and it is offered only on models that can drive a workflow. Because each model advertises its own set, the validator is model-aware:

  • Ask for a level the model supports and it is applied, with a toast naming the new level.
  • Ask for a valid level the current model does not expose and it is clamped to the nearest lower one, with a note explaining the adjustment.
  • On a model with no effort levels at all, the command reports that and does nothing.

/plan

/plan toggles plan mode: a read-only stance where Claude investigates and proposes a plan without writing files, running commands, or taking other write actions. The write tools stay advertised and are refused when called, with a note steering the model to create_plan instead. Run the command again to leave plan mode, which puts the session in Auto. It is the same dial described in Permissions & approvals, so any write step still surfaces an approval card once you leave plan mode.

/verbosity

/verbosity <level> sets the response length, the same three-level control that sits under the composer. Pass brief for short, direct answers, normal for balanced detail, or detailed for thorough, expansive ones (low, medium, and high work as aliases). A toast confirms the level you set; call it with no argument to see the usage string.

/memory

/memory on and /memory off flip cross-session memory, and /memory status reports whether it is currently on. Memory is what lets Claude carry durable facts between conversations; see the Memory & WHISPER.md guide for what gets remembered and how to curate it.

/goal

/goal <text> sets a session goal that the goal loop keeps working toward: after each turn a cheap evaluator judges whether the goal is met, and if not the turn auto-continues (capped so it cannot run away). A goal banner appears above the composer while one is active. The goal text is also sent as the first message, so the work starts immediately rather than leaving you with an empty composer; if a turn is already streaming, the text is folded into that running turn instead of starting a second one. /goal clear ends it. Both need an open session, and a bare /goal shows its usage hint. The loop is gated by the goal_loop feature flag; see Feature flags.

Quality gates are shell commands that must exit 0 before a goal can be judged done. They run at every turn boundary, ahead of the judge, so "done" means the checks actually passed:

/goal gate add <shell command>
Add a check, for example npm test or venv/bin/pytest tests/. The confirmation says how many gates must now pass.
/goal gate remove <N>
Remove gate number N, counting from 1 in the listed order.
/goal gate clear
Remove every gate.
/goal gate
List the gates, each with the number of times it has failed so far. With none set, the reply says so and repeats the add syntax.

Side tasks & agents

These run work alongside the main conversation without derailing it.

/btw

/btw <question> asks a quick side-channel question that does not enter the main transcript. It sends only your question plus a few recent messages for context, streams the answer into a small popup, and leaves the conversation history untouched. Use it for a fast aside ("btw what does this acronym mean") when you do not want to spend the main thread's context on it. With no question, the command just shows its usage hint.

/subagent

/subagent <task> spawns a focused one-shot subagent that works in the background with the full tool loop: web search and fetch, workspace access, code, and any enabled MCP tools. It does not block the composer, so you can keep chatting while it runs. Its live progress renders in a report card inside the chat, and its final answer is posted there when it finishes. Press Stop on the card to cancel a run in flight, which marks any still-running row stopped rather than leaving it spinning. It runs on the composer's current model and effort. For coordinating several agents at once, see Sub-agents & teams.

/workflow

/workflow <saved-name> launches a saved workflow by name: a deterministic script from the ultracode workflow runtime that orchestrates agents in the current session. The run starts immediately and renders a workflow card in the chat that tracks its phases, and it does not block the composer. It launches on the composer's current model and effort, so the same saved workflow behaves the same way however you start it. It needs an open session. Two failures are told apart: a workflow that was saved but never approved is refused until you run it once from chat and approve its preview card, and a name that matches nothing asks you to check that it is saved. See The ultracode workflow runtime for how workflows are authored, previewed, and resumed.

Files & tools

Colon-style commands open an inline picker as you type after the colon, so you can search rather than remember exact names.

/file: and @file

/file:<path> references a workspace file so Claude sees its contents inline. There are two behaviors depending on whether you add a question:

/file:path
With no trailing question, the file is attached to the composer as a chip (uploaded in the background) and you keep composing.
/file:path a question
With a question, your message and a working indicator appear immediately while the file is fetched, converted, and uploaded in the background, then the turn sends.

The same file reference is also available as an @file: mention from anywhere in the message. Typing @ opens a picker with five fixed entries plus your own skills and sessions:

@file:
Reference a workspace file, searchable by path as you type.
@skills:
Browse skills. A bare @<skill-name> works too and forces that skill for the message; with no text of your own, the skill runs on the conversation so far.
@mcp:
Browse the tools of your connected MCP servers.
@index
Force a search of your indexed folders for this message (see Index & semantic search).
@docs
Answer from this manual: the matching passages are retrieved and the answer is written from them, with the pages it used cited. The first use builds the manual's index, which takes a moment.
@<session-title>
Pull another chat session in as context for the turn, matched on its title.

The @index and @docs markers are stripped before the model sees the text. Attached documents are extracted to text (large ones are capped) and images become vision blocks; see Attachment extraction for the type-aware pipeline. Supported inputs include images, PDF, Office docs, audio, video, code, and text.

/skills, /skills: and /mcp:

/skills: browses the available skills and /mcp: browses the tools exposed by your connected MCP servers. Both open a searchable submenu as you type after the colon, which is the discoverable way to see exactly what is wired up in the current session. /skills without the colon is a different command: it opens the Skills panel in Settings, where you enable, disable, import, and edit them.

The colon matters. /file:, /skills:, and /mcp: are submenu commands: the argument comes right after the colon, and the picker dismisses once a space begins the message body. See Agent tools for the full catalogue those tools come from.

Conversation & session

Manage the transcript and the session record.

/export

/export downloads the current conversation as a plain-text file (chat-export-<timestamp>.txt), with each message prefixed by its role and separated by rules. It reads the messages currently in view, so pair it with a fresh session for a clean transcript. For a portable export that another install can import, use the sessions sidebar instead: it exports a single session as .jsonl or many sessions as a zip (with matching import), via server/infrastructure/sessions_routes.py.

/clear

/clear empties the chat so you can start fresh in the same tab. It drops the messages from the session's store, and because the session saves itself on a timer, the next save writes that empty history to the session record: treat it as clearing the conversation, not just the view. The session itself stays in the sidebar, keeping its title and its meeting transcript. If you want the old messages back later, start a new session instead of clearing this one, and to remove a session for good, delete it from the sidebar.

/rename

/rename <new title> sets a custom title for the current session and marks it as user-chosen, so the automatic title generator will not overwrite it later. Everything after the command word becomes the title. With no title, you get the usage hint.

/workspace

/workspace opens the Connect Workspace dialog, where you type a path, browse for a folder, or pick one from your indexed and recent lists. Connecting a folder is what unlocks the file tree, editor, terminal, and the file-aware tools. The workspace IDE tutorial walks through what becomes available once a folder is connected.

Utilities & diagnostics

App-level helpers that do not touch the model.

/theme

/theme <name> switches the interface theme immediately and remembers your choice. The accepted values are auto, dark, light, the accessibility variants dark-high-contrast, light-high-contrast, dark-daltonized, and light-daltonized, and the alternate looks dark-taw and light-taw. auto follows your system's light or dark preference.

/notify

/notify requests browser notification permission (or tells you the current state if it is already granted or blocked). With notifications enabled, long-running work like a subagent or a scheduled task can alert you when it finishes.

/settings

/settings opens the Settings panel. It is the keyboard-first way to reach model defaults, API keys, and the rest of the fields documented in Settings & config keys.

/doctor

/doctor runs an automated diagnostics pass and shows the results in a dialog: a set of checks (dependencies, AWS access, and related environment health) each marked as ok, warn, or fail. It calls the /api/doctor endpoint served by server/doctor.py. Run it first whenever chat is not responding or a model call errors.

/doctor context is a separate check for prompt health: it calls /api/doctor/context (server/context_report.py) and opens a Context report panel showing what the model is actually sent - the per-section cost of the system prompt, how much of it is cached, and any stale or duplicate tool references. Use it when turns feel expensive or slow to see where the tokens go.

/ci

/ci [branch] watches the branch's latest GitHub Actions run to a terminal state, streaming its status into a card in the chat. /ci autofix [branch] goes further: it reads the failing logs, posts a diagnosis, and emits an approvable workflow that fixes the problem and then runs verification, using the ultracode workflow runtime. Both need an open session and the GitHub CLI (gh) installed and authenticated; without it the command reports that CI is unavailable. See The ultracode workflow runtime.

There is no /hooks command. Blocking hooks (PreToolUse, PostToolUse, and the Stop gate) are managed in the Settings panel, not from the composer. See Settings & config keys and the Security model for how project hooks are trusted.

/help

/help opens a dialog listing every command grouped by category (General, AI & Model, Workspace, Settings, Debug) - the AI & Model group is where /workflow, /ci, and /goal appear - each with its icon and one-line description. It is generated from the same command list this page documents, so it always matches your build.

Names track your config. /model and /effort validate against the models and effort levels you actually have enabled, so the exact options you see may differ from the examples here. When in doubt, run the command with no argument and read the usage hint it returns.
