Slash commands

Every / command available in the chat input. Type / at the start of an empty composer to see the full list inline, with argument hints and live autocomplete.

The composer reads a slash command before it sends text to the model. A command changes the session (model, effort level, response length), starts a side task (a workflow), or controls the UI (open Settings, clear the view, rename the session). Most commands operate immediately and show a small toast. Some commands open a dialog. The client runs the built-in commands in src/hooks/useSlashCommands.tsx. Their list is in src/components/chat/chatInputConstants.ts.

The composer has two menus. / runs something: a built-in command, a skill, or a prompt of an MCP server. @ points at something that the model uses as context: a file, a folder, an agent type, a session, or an MCP resource. The two menus are in src/components/chat/composerMenus.ts. Refer to Skills and MCP prompts and Mentions.

A command only fires when your message begins with /. Anything that is not a recognised command is treated as a normal chat message, so a stray slash never eats your text. Run /help at any time for the same reference inside the app.

Model & reasoning

These commands change how the assistant works for the rest of the session. They mirror the controls under the composer, so a command and a click stay in sync.

/model

/model <name> switches the model for every subsequent turn in this session. The valid names are the keys of the models that Settings › Model mode shows: Cloud lists the cloud models only (haiku, sonnet5.5, opus5.5, fable5.2, gpt6.1-sol, gpt6-astra, gpt6-luna), Local lists your installed on-device models only, and Hybrid lists both. In Local mode with no on-device model installed, /model tells you where to get one. On success you get a toast confirming the version label ("Model set to Sonnet 5.5"), not the raw key. Pass an unknown name and the composer replies with the usage string listing the models you can pick.

Switching to a model with a stricter data-retention policy routes through a consent screen first, so the change only lands after you confirm. See Model modes for the cloud, hybrid, and local backends behind each name.

/effort

/effort <level> sets thinking depth for models that expose it, which is every cloud model except Haiku. The palette offers low, medium, high, extra, max, and ultracode; the raw API name xhigh is accepted as an alias for extra. Which rungs a model actually has depends on its ladder: extra exists on Opus 5.5, Sonnet 5.5 and Fable 5.2, while the GPT models go straight from high to max. ultracode is the top mode: it pairs the model's highest reasoning rung with dynamic-workflow orchestration (see The ultracode workflow runtime), and it is offered only on models that can drive a workflow. Because each model advertises its own set, the validator is model-aware:

On an on-device model that can think, /effort sets its Thinking level instead (off, low, medium, high, max, or only off and max on some MLX models). ultracode is not offered on-device.

  • Ask for a level the model supports and it is applied, with a toast naming the new level.
  • Ask for a valid level the current model does not expose and it is clamped to the nearest lower one, with a note explaining the adjustment.
  • On a model with no effort levels at all, the command reports that and does nothing.

/plan

/plan toggles plan mode: a read-only stance where the assistant investigates and proposes a plan without writing files, running commands, or taking other write actions. The write tools stay advertised and are refused when called, with a note steering the model to create_plan instead. Run the command again to leave plan mode, which puts the session in Auto. To carry out the latest plan, press Approve on the plan card or type plan approved: this leaves plan mode (Auto) and starts the implementation. It is the same permission mode described in Permissions & approvals, so any write step still surfaces an approval card once you leave plan mode.

/memory

/memory on and /memory off flip cross-session memory, and /memory status reports whether it is currently on. Memory is what lets the assistant carry durable facts between conversations; see the Memory & WHISPER.md guide for what gets remembered and how to curate it.

/goal

/goal <text> sets a session goal that the goal loop keeps working toward: after each turn a judge (a cheap cloud evaluator, or an on-device session's own model) decides whether the goal is met, and if not the turn auto-continues (capped so it cannot run away). A goal banner appears above the composer while one is active. The goal text is also sent as the first message, so the work starts immediately rather than leaving you with an empty composer; if a turn is already streaming, the text is folded into that running turn instead of starting a second one. /goal clear ends it. Both need an open session, and a bare /goal shows its usage hint. The loop is gated by the goal_loop feature flag; see Feature flags.

Quality gates are shell commands that must exit 0 before a goal can be judged done. They run at every turn boundary, ahead of the judge, so "done" means the checks actually passed:

/goal gate add <shell command>
Add a check, for example npm test or venv/bin/pytest tests/. The confirmation says how many gates must now pass.
/goal gate remove <N>
Remove gate number N, counting from 1 in the listed order.
/goal gate clear
Remove every gate.
/goal gate
List the gates, each with the number of times it has failed so far. With none set, the reply says so and repeats the add syntax.

Side tasks & agents

These run work alongside the main conversation without derailing it.

To give a task to one agent, use an @agent-<type> mention. Refer to Agent mentions and Sub-agents & teams.

/workflow

/workflow <saved-name> launches a saved workflow by name: a deterministic script from the ultracode workflow runtime that orchestrates agents in the current session. The run starts immediately and renders a workflow card in the chat that tracks its phases, and it does not block the composer. It launches on the composer's current model and effort, so the same saved workflow behaves the same way however you start it. It needs an open session. Two failures are told apart: a workflow that was saved but never approved is refused until you run it once from chat and approve its preview card, and a name that matches nothing asks you to check that it is saved. See The ultracode workflow runtime for how workflows are authored, previewed, and resumed.

Skills and MCP prompts

The / menu has the heading "Commands". It shows the built-in commands first. Then it shows the enabled skills and the prompts of the connected MCP servers. When you type a command and a space, the menu shows the options of the command under the heading "Options".

/skill-name

Each enabled skill is in the menu as /skill-name. Type your text after the name, for example /meeting_notes tidy these. The skill runs on that text. With no text, the skill runs on the current conversation. The chat bubble shows /skill-name and your text. The server adds a line that asks the model to call the skill.

A skill with the same name as a built-in command cannot run from /. The built-in command runs.

/server:prompt

A connected MCP server can give prompts. Each prompt is in the menu as /server:prompt. The row of the prompt shows its arguments, and an optional argument is in brackets. Type the arguments after the name:

  • The words after the name go into the arguments of the prompt, in order.
  • The last argument gets all the remaining text of the line.
  • Quotation marks keep words together as one argument.
  • If the prompt must have an argument and you do not give it, a toast shows /server:prompt needs: <names>. The text stays in the composer.

The app sends the text of the prompt as an attachment of your message. The name of the attachment is /server:prompt (MCP prompt). Thus, the model also receives the prompt in the next turns. If the prompt has more than one message, the text keeps the "User:" and "Assistant:" labels.

In the names of the server and the prompt, the app changes some characters to _. It changes each character that is not a letter, a digit, _, ., or -. The same names are in the @server:uri mentions.

/skills and /mcp

/skills opens the Skills settings. There you enable, disable, import, and edit your skills. /mcp opens the MCP servers settings, where you add, enable, and disable your MCP servers. The menu and /help show the two commands.

Mentions

Type @ at any position in the message to open the mention menu. The menu has the heading "Mentions". A mention points at something that the model uses as context:

Files and folders
The files and folders of the connected workspace. The menu searches for them when you type after @. With no text after @, the first row is "Type to search files and folders". Refer to Workspace files and folders.
@agent-<type>
Gives the task to an agent of that type. Refer to Agent mentions.
@<session>
Adds the recent conversation of a different session as context. The menu finds the session by its title, and writes the title as a slug.
@server:uri
Adds a resource of a connected MCP server, for example @github:issue://12. Refer to MCP resources.
@index
Force a search of your indexed folders for this message (see Index & semantic search).
@docs
Answer from this manual: the matching passages are retrieved and the answer is written from them, with the pages it used cited. The first use builds the manual's index, which takes a moment.

The @index and @docs markers are stripped before the model sees the text. Attached documents are extracted to text (large ones are capped) and images become vision blocks; see Attachment extraction for the type-aware pipeline. Supported inputs include images, PDF, Office docs, audio, video, code, and text.

Workspace files and folders

The file and folder search operates only with a connected workspace. When you select a file or a folder in the menu, the app adds no text to the message. It adds a chip that holds only the path. The app uploads the file when you send the message:

  • The message shows immediately.
  • The status line shows "Uploading <name>…", or "Uploading N files…" for more than one file.
  • Stop cancels the uploads.
  • Regenerate uploads the files again.

A folder chip shows name/. The chip contains the listing of the folder. The listing gives the entries that are directly in the folder, one entry on each line. The name of each subfolder ends with /. The listing gives maximum 2000 entries. If the folder has more entries, the listing tells you.

In the workspace tree, "Add File to Chat" on a file and "Add Folder to Chat" on a folder add the same path chip.

Agent mentions

@agent-<type> gives the task to an agent of that type. The types are general, explore, plan, verify, and coordinator, and your custom types. A custom type is a .whisper/agents/*.md file in your user folder (~/.whisper/agents/) or in the project. For each type, the menu shows the description from the frontmatter of the file. Refer to Custom agent types.

The mention stays in the text. The server adds a line that asks the model to call spawn_agent with that agent_type. The model writes the task of the agent from your message. The turn waits for the result of the agent.

MCP resources

@server:uri adds a resource of a connected MCP server, for example @github:issue://12. The app reads the resource when the turn starts. The text of the resource goes into the message before your text, to maximum 150,000 characters. If the server is not connected, or the app cannot read the resource, the mention stays as you typed it. The app does not read a name with a colon after it as a session.

/ runs, @ points. Use / to run a command, a skill, or an MCP prompt. Use @ to point at context: a file, a folder, an agent type, a session, or an MCP resource. See Agent tools for the full list of the tools that the model calls.

Conversation & session

Manage the transcript and the session record.

/export

/export downloads the current conversation as a plain-text file (chat-export-<timestamp>.txt), with each message prefixed by its role and separated by rules. It reads the messages currently in view, so pair it with a fresh session for a clean transcript. For a portable export that another install can import, use the sessions sidebar instead: it exports a single session as .jsonl or many sessions as a zip (with matching import), via server/infrastructure/sessions_routes.py.

/clear

/clear empties the chat so you can start fresh in the same tab. It drops the messages from the session's store, and because the session saves itself on a timer, the next save writes that empty history to the session record: treat it as clearing the conversation, not just the view. The session itself stays in the sidebar, keeping its title and its meeting transcript. If you want the old messages back later, start a new session instead of clearing this one, and to remove a session for good, delete it from the sidebar. /clear and the Clear button do the same work. They also stop a reply that runs. They close every card that waits (approval, question and folder cards), in the app and on the server.

/compact

/compact summarizes the whole conversation now. Use it when a chat gets long and you want to keep working in it. Add a note after the command to tell the summary what to keep, for example /compact keep the MCP setup steps. The compaction model writes one summary, and the chat shows a "Conversation compacted" row. Open the row to read the summary. From then on, the model reads the summary and the messages after it, not the earlier messages. The earlier messages stay on the screen and in the saved session. If the summary fails, or it is not smaller than the conversation, nothing changes and an error tells you why. You cannot run /compact while a reply streams.

/rename

/rename <new title> sets a custom title for the current session and marks it as user-chosen, so the automatic title generator will not overwrite it later. Everything after the command word becomes the title. With no title, you get the usage hint.

/workspace

/workspace opens the Connect Workspace dialog, where you type a path, browse for a folder, or pick one from your indexed and recent lists. Connecting a folder is what unlocks the file tree, editor, terminal, and the file-aware tools. The workspace IDE tutorial walks through what becomes available once a folder is connected.

Utilities & diagnostics

App-level helpers that do not touch the model.

/theme

/theme <mode> sets the interface mode immediately and remembers your choice. The accepted values are auto, light, and dark. auto follows the light or dark setting of your Mac (the header menu calls it System).

/notify

/notify requests browser notification permission (or tells you the current state if it is already granted or blocked). With notifications enabled, long-running work like a subagent or a scheduled task can alert you when it finishes.

/settings

/settings opens the Settings panel. It is the keyboard-first way to reach model defaults, the General tab (web search key, speech models, Bedrock region), and the rest of the fields documented in Settings & config keys.

/doctor

/doctor runs an automated diagnostics pass and shows the results in a dialog: AWS credentials, Bedrock connectivity, whether each GPT model resolves to a region Bedrock serves it in, the workspace, the sessions database, and the config, each marked as ok, warn, or error. Local mode skips the AWS and GPT rows, because it makes no AWS calls. It calls the /api/doctor endpoint served by server/doctor.py. Run it first whenever chat is not responding or a model call errors.

/doctor context is a separate check for prompt health: it calls /api/doctor/context (server/context_report.py) and opens a Context report panel showing what the model is actually sent: the per-section cost of the system prompt, how much of it is cached, and any stale or duplicate tool references. Use it when turns feel expensive or slow to see where the tokens go.

/ci

/ci [branch] watches the branch's latest GitHub Actions run to a terminal state, streaming its status into a card in the chat. With no branch, it uses the current branch of the connected workspace, which must be a git repository. /ci autofix [branch] goes further: it reads the failing logs, posts a diagnosis, and emits an approvable workflow that fixes the problem and then runs verification, using the ultracode workflow runtime. Both need an open session and the GitHub CLI (gh) installed and authenticated; without it the command reports that CI is unavailable. See The ultracode workflow runtime.

There is no /hooks command. Blocking hooks (PreToolUse, PostToolUse, and the Stop gate) are managed in the Settings panel, not from the composer. See Settings & config keys and the Security model for how project hooks are trusted.

/help

/help opens a dialog with the built-in commands in groups (General, AI & Model, Workspace, Settings, Debug). The AI & Model group shows /workflow, /ci, and /goal, each with its icon and a description of one line. The Settings group shows /skills and /mcp. The app makes the dialog from the same list as the slash menu. Thus, the dialog always matches your build. The dialog does not show the skills and the MCP prompts.

Names track your config. /model and /effort validate against the models and effort levels you actually have enabled, so the exact options you see may differ from the examples here. When in doubt, run the command with no argument and read the usage hint it returns.
