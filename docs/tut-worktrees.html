Branches and worktrees: parallel sessions on one repo

Several sessions, several sub-agents, one repository. Git worktrees give each of them its own checkout on its own branch, so nobody's half-finished edit is visible to anyone else until it is deliberately merged or harvested back.

A single git repository normally has one working directory: check out a different branch and every open file changes under you. That is fine for one person working serially, but it breaks down the moment two things want to touch files in the same repo at the same time, a second chat session, a background sub-agent, or a task you want isolated until you have reviewed it. Whisper Studio solves this with git worktrees: the same shared commit history, several independent checkouts. This tutorial covers the three places worktrees show up, why they cannot step on each other, and what happens to the work when a worktree-backed task finishes.

Task branches: isolate a change, then merge it

These are ordinary tools Claude calls mid-conversation when a change touches enough files that you would rather review it as a unit than watch your working tree mutate file by file.

ToolWhat it does
ws_create_worktreeCreates a worktree at .worktrees/<name> on a new branch whisper/<name>, branched from HEAD. Auto-generates a name if you do not give one.
ws_diff_worktreeShows the diff between the worktree branch and your current branch, so you can review the change before it lands.
ws_merge_worktreeMerges the worktree branch back into your current branch with --no-ff, leaving a real merge commit. Gated by approval, since it changes your checkout.

Nothing about your open files changes while the worktree work happens; Claude reads and writes inside .worktrees/<name>, and only ws_merge_worktree touches the branch you are actually looking at.

Session worktrees: enter_worktree and exit_worktree

Separate from task branches is a lower-level mechanism for pinning an entire session, not just one change, onto its own worktree: enter_worktree and exit_worktree. These are registered as approval actions (approval category worktree), not as tool schemas offered to the model, so nothing in a normal turn instructs Claude to call them directly. The mechanism they run on, server/git/worktree_session.py, is the same one the runtime uses automatically for worktree-isolated sub-agents below, so read this section as "how a worktree gets attached to a session" and the next one as its most common, fully-automatic use.

  • Entering creates (or resumes) <repo>/.whisper/worktrees/<slug> on branch worktree-<slug>, branched from the repo's current HEAD at that moment, and pins the session to it: from then on that session's shell commands and workspace tools operate with their cwd set to the worktree, tracked per session by server/cwd_tracker.py. If the worktree path already exists, it is reused rather than recreated, so re-entering the same slug picks up where it left off instead of erroring.
  • Exiting runs git worktree remove on that path, restores the session's original cwd, and clears the session record. It refuses to remove a worktree with uncommitted changes unless forced, so exiting does not silently discard work.

Both actions sit behind their own worktree approval category, distinct from ordinary file writes, so you can trust the flow once ("Yes for all worktree operations") without widening any other write permission. The frontend can read a session's current pin at any time through GET /api/git/worktree-session, which is how the workspace terminal shows the small "in worktree" chip next to the branch name.

Why two sessions can never collide

Three separate guarantees stack up to make this safe:

One shared object store, many checkouts

A git worktree is a second working directory (its own files, its own index, its own HEAD) that still reads and writes the same .git object database as the main checkout. Nothing is duplicated or forked; a commit made in one worktree is immediately part of the one shared history.

Git itself blocks the sharp edge

Git refuses to let the same branch be checked out in two worktrees at once. Because every session's slug maps to its own branch name, two sessions can never end up pointed at the same branch, the one scenario that would actually let them stomp on each other's edits.

Slugs are validated before they touch a path

A slug becomes both a directory name and a branch name, so it is validated first: letters, digits, dots, underscores, and dashes only, no leading dash or slash, no .. segments, capped length. That rules out path traversal and branch-name injection from a crafted name, the same guard ws_create_worktree uses.

State is tracked per session id

Which session owns which worktree is recorded in memory keyed by session id (namespaced agent:<id> for sub-agents so an agent's entry can never collide with a user session of the same name). A session can only ever exit the worktree it entered.

Persistence across restarts

The session-to-worktree mapping is written to ~/.whisper_cache/worktree-sessions.json every time it changes, and read back in on startup. Restart the server while a session is mid-worktree and the mapping survives: the worktree directory, its branch, and which session owns it are all exactly as you left them. This mirrors the resume behavior of Claude Code's own worktree sessions, on purpose.

Worktree-isolated sub-agents

This is where the session-worktree mechanism actually runs today, fully wired end to end. A sub-agent spawned with isolation: 'worktree' gets its own worktree automatically, keyed to agent:<agent_id>:

  1. The runtime enters a worktree for it

    Before the agent's first turn, the runtime calls the same enter_worktree machinery with a slug of agent-<agent_id>, giving it .whisper/worktrees/agent-<agent_id> on branch worktree-agent-<agent_id>. Because a full checkout can take real time on a big repo, this happens on a dedicated worker so it does not block the event loop.

  2. It gets write access

    Isolation is precisely what unlocks writing: a detached spawn_agent is read-only by default specifically because it has no isolation, and isolation: 'worktree' is the safe way to let it write anyway, since anything it touches lands in its own worktree, not yours.

  3. The agent works normally

    Reads, writes, commands, and commits all run with the agent's cwd set to its worktree. From the agent's point of view it is just an ordinary checkout.

  4. On a clean finish, the work is harvested

    See the next section. A genuinely completed agent's changes are folded back into your working tree automatically. A turn-limited, timed-out, failed, or manually stopped agent keeps its worktree instead, so partial work is never silently discarded or silently applied.

Harvest: bringing the work back

A worktree-isolated agent may leave its work committed, uncommitted, or a mix, it has git tools and may or may not use them. Rather than requiring a clean commit history to merge, harvest (server/git/worktree_harvest.py) computes the agent's full file-level delta since the worktree's branch point and applies it directly to your working tree as uncommitted changes, the same way a normal edit would land. Nothing is committed or force-resolved on your behalf; the result just shows up in git status for you to review, diff, and commit yourself.

Non-conflicting files land

Because harvest compares each file individually against the base commit, a file the agent touched that you did not lands cleanly even if other files in the same run collide. One conflicting file does not block the rest of the change.

Real conflicts are left in the worktree

A file only counts as a conflict when your tree changed it away from the base and differently from the agent. Those files are left exactly where the agent left them; the worktree is kept (not removed) and the result note tells you which files and where to find them.

The result is one of clean (nothing to bring back), applied (everything landed), partial (some files landed, some conflicted, worktree kept for the rest), or conflict (nothing could land, worktree kept). Materialization is serialized process-wide, so if two agents finish at the same moment they apply to your tree one at a time rather than racing each other.

If you want to double-check a worktree-isolated agent's work before it touches your tree at all, run it without isolation: 'worktree' when possible (read-only agents such as explore or plan do not need it), or review the harvested, still-uncommitted diff before you commit it. Harvest never commits for you, so that review step is always available.

Where it all lives

server/git/worktree_session.py
Slug validation, the session-to-worktree mapping, enter_worktree / exit_worktree, and the persisted JSON store.
server/cwd_tracker.py
Tracks each session's current working directory, so a session pinned into a worktree runs its shell commands and workspace tools there.
GET /api/git/worktree-session
Read-only lookup of a session's current worktree pin, used by the workspace terminal's status chip.
server/git/worktree_harvest.py
Materializes a finished worktree-isolated agent's delta back into the originating working tree.
server/workspace/executors.py
ws_create_worktree, ws_diff_worktree, and ws_merge_worktree: the task-branch tools.
<repo>/.worktrees/<name>
Task-branch worktrees on branch whisper/<name>.
<repo>/.whisper/worktrees/<slug>
Session and sub-agent worktrees on branch worktree-<slug>.
~/.whisper_cache/worktree-sessions.json
The persisted session-to-worktree mapping, survives a server restart.
