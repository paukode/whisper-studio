Branches and worktrees: parallel work on one repo

Git worktrees give a task branch or a subagent its own checkout on its own branch. Your working tree does not show their edits until you merge the branch or the app harvests the work.

A git repository usually has one working folder. When you check out a different branch, all the open files change. This is a problem when two tasks change files in the same repository at the same time. Examples are a background subagent, or a change that you want to examine before it goes into your tree. Whisper Studio uses git worktrees for this: one shared commit history and many separate checkouts.

All chat sessions use the one connected workspace folder. Only task branches, subagents, and the worktrees that you make in the terminal get their own checkout. This tutorial shows the three types of worktree, why they do not collide, and what occurs to the work at the end.

The three types use the same git function, but they have different purposes. Read the table, then read the section for the type that you need.

Task branches: isolate a change, then merge it

The assistant calls these tools during a conversation when a change has many files. Then you can examine the change as one unit. Each tool takes one name.

ToolWhat it does
ws_create_worktreeMakes a worktree at .worktrees/<name> on a new branch whisper/<name> from HEAD. If you do not give a name, the tool makes one. The tool validates the name before it uses it as a path or a branch. The connected workspace can also be a linked worktree.
ws_diff_worktreeRuns git diff HEAD...<branch> in your main checkout. It shows the committed changes on the worktree branch since the branch point. It does not show changes that are not committed. Then the tool returns (no changes in worktree).
ws_merge_worktreeMerges the worktree branch into your current branch with --no-ff, and makes a merge commit. If there is a conflict, the tool reports the failure and leaves git in the conflict state. It does not abort the merge and does not remove the worktree.

Your open files do not change during the worktree work. The assistant reads and writes in .worktrees/<name>. Only ws_merge_worktree changes your current branch.

Read the diff before you ask for the merge. The merge does not show an approval card. Plan mode blocks it, but in the other modes the merge runs as a usual tool call.

The three tools keep a list of their worktrees in memory. A workspace change, a disconnect, or a server restart clears the list. The folder and the branch stay on the disk. But ws_diff_worktree and ws_merge_worktree then return Worktree '<name>' not found, and you must complete the work with git. For work that must survive a restart, use the worktree isolation of a subagent.

Subagents with worktree isolation

A subagent with isolation: 'worktree' gets its own worktree automatically:

  1. The runtime makes a worktree for the agent

    Before the first turn of the agent, the runtime makes .whisper/worktrees/agent-<agent_id> on branch worktree-agent-<agent_id>. A full checkout can take some seconds on a large repository. Thus a separate worker does this step, and the event loop does not stop.

  2. The agent gets write access

    A detached spawn_agent is read-only by default, because it has no isolation. With isolation: 'worktree', the agent can write, because all its changes go into its own worktree. If the app cannot make the worktree, the agent runs read-only for that run. Examples are a workspace that is not a git repository, or a git error.

  3. The agent operates normally

    The worktree is the root of the agent. Its workspace tools and its shell commands run there. Each agent has its own working folder, so a cd of one agent does not move the commands of a different agent.

  4. After a clean finish, the app harvests the work

    See the next section. The app applies the changes of a completed agent to your working tree. If the agent stopped at a turn limit, timed out, failed, or was stopped, the app keeps its worktree. Thus the app does not discard or apply partial work without your knowledge.

Why worktrees do not collide

One object store, many checkouts

A git worktree is a second working folder with its own files, index, and HEAD. It uses the same .git object database as the main checkout. A commit in one worktree is immediately part of the shared history.

Git blocks a shared branch

Git does not let two worktrees check out the same branch. Each agent gets its own branch name. Thus two agents cannot change the files of the same branch.

The app validates each name

A name becomes a folder name and a branch name. Thus the app validates it first. It accepts only letters, digits, dots, underscores, and dashes. A name must not start with a dash or a slash, must not contain .., and has a maximum length. This stops path traversal and branch-name injection.

The app records the owner

The app records which agent owns which worktree, with the key agent:<id>. The app writes this record to ~/.whisper_cache/worktree-sessions.json after each change and reads it at startup. Thus the record survives a server restart.

Harvest: get the work back

A worktree agent can leave its work committed, not committed, or a mix of the two. Harvest (server/git/worktree_harvest.py) does not need a clean commit history. It calculates the full change of each file since the branch point of the worktree. Then it applies the change to your working tree as uncommitted changes.

The app does not commit or resolve anything. The result shows in git status. You examine it, see the diff, and commit it yourself.

Files without a conflict go into your tree

Harvest compares each file separately with the base commit. A file that only the agent changed goes into your tree. This is also true when other files of the run have a conflict. One conflict does not block the rest of the change.

Conflicts stay in the worktree

A file is a conflict only when your tree changed it from the base and the agent changed it differently. These files stay in the worktree. The app keeps the worktree, and the result note gives the files and their location.

The result has one of five statuses:

  • clean: there is nothing to bring back.
  • applied: all the files are in your tree.
  • partial: some files are in your tree, and some have a conflict. The app keeps the worktree.
  • kept: the app applied nothing. The agent did not complete, or all files have a conflict. The app keeps the worktree.
  • error: the harvest failed.

The app removes the worktree and its branch after clean and applied, and keeps them after the other three. Thus the app keeps changed files, not the empty folder. New files arrive untracked. Run git add on them before the commit, because git commit -a does not include them. The app applies one harvest at a time. If two agents complete at the same time, they apply their changes in sequence.

The app removes a worktree with git worktree remove --force. This also deletes the gitignored files of the agent in the worktree. The app does not bring back build output and installed dependencies. It brings back only changes to tracked files.

A read-only agent, for example explore or plan, does not need isolation: 'worktree'. For an agent that writes, examine the uncommitted diff after the harvest. Harvest does not commit, so you can always examine the change before the commit.

Terminal worktrees

You can also make a worktree yourself in the terminal panel. The branch menu of the terminal has a Worktrees section.

  1. Open the Worktrees menu

    In the header of the open terminal panel, click the branch button ("Branches and worktrees"). The Worktrees section lists the worktrees of the repository.

  2. Add a worktree

    Click + Add worktree and type a branch name. To make a new branch, select New branch. Click Create. The app makes the worktree at ../<repo>-<branch>, next to the main checkout.

  3. Remove a worktree

    Click the × on the row of the worktree. The app does not remove the worktree of the active workspace.

The app does not merge a terminal worktree. Merge its branch with git.

Where it all lives

server/workspace/executors.py
ws_create_worktree, ws_diff_worktree, and ws_merge_worktree: the task-branch tools.
server/git/worktree_session.py
Name validation, the record of agent worktrees, and its JSON file.
server/agents/runtime.py
Makes the worktree of an isolated agent, or runs the agent read-only if it cannot.
server/cwd_tracker.py
Keeps the working folder of each session and each agent. The agent runtime registers the worktree of an agent here, so the tools of the agent run in its worktree.
server/git/worktree_harvest.py
Applies the changes of a completed agent to the working tree where the agent started.
server/git/router.py
The routes of the terminal Worktrees menu: list, add, and remove.
<repo>/.worktrees/<name>
Task-branch worktrees on branch whisper/<name>.
<repo>/.whisper/worktrees/agent-<id>
Subagent worktrees on branch worktree-agent-<id>.
~/.whisper_cache/worktree-sessions.json
The record of agent worktrees. It survives a server restart.
